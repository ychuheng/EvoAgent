# P3 验证 Task 费用账本合同

用户已明确恢复原计划。本批接续已交付的验证副本归档，补齐真实 Task 费用预留所需的身份与恢复合同；不开放真实 Provider，不执行付费评测，不声称 P3 已完成。

## 改动

- `LearningSpendReservationRecord` 与迁移 `20261010_0030`：在既有账本增加 dispatcher_kind、task_id、run_id、task_epoch、request_body_hash。后台维护身份与 Task 身份互斥；历史记录归为 maintenance，保留原日预算、上界、状态与未知账项，不猜测历史任务归属。有 Task 费用证据时拒绝破坏性降级。
- `learning/task_budget_guard.py::ValidationTaskBudgetGuard`：校验真实 Task/Run 租约、取消标志和既有个人验证请求/来源/绑定权限，不把 Task UUID 塞入 MaintenanceJob 外键。预算事务先锁执行 Task→Run，再进入原来源 Run/工作区、全局预算锁、请求和账项；后续租约复查复用已经取得的 Task/Run 锁。事务不跨模型网络调用。
- `LearningBudgetService`：复用原日/请求/总预算校验、价格冻结、发送意图和幂等结算，增加 Task 绑定与真实执行费用归属。重试不改成另一条执行身份，未发送预留可交给新的租约代次，已有发送意图不能再次派发。
- `reconcile_stale`：除原维护 Job 外，还检查真实 Task 的状态、取消、代次、租约到期和 Run 状态。有效 Task 不因缺少 MaintenanceJob 被误判；失效执行的已发送预留变 unknown，未发送变 released。保留有界扫描，不新增轮询系统。
- `runtime/budget.py::evaluate_budget`：Task 上界按真实执行 Task 汇总，历史 maintenance 仍按来源 Task；合计限定当前 scope/legacy。`settle` 的 skill_validation 收据归到实际验证 Run/Task，reservation_id 保证不重复记账，不给来源 Run 伪造验证支出。
- `ModelRequest.runtime_iteration` 是宿主循环设置、从 wire 序列化中排除的步骤信息；AgentLoop 在真实派发与恢复时沿用当前迭代编号。原序列化/hash 不因新增元信息改变，ContextStore 改写消息仍保留步骤。
- `LearningBudgetedProvider` 的 Task 分支使用 request/Run/步骤身份，正文 hash 单独保存：同一步正文变化是 identity_conflict，同一步已发送则禁止重发；不同步骤即使正文完全相同也有不同预留。原维护提炼调用身份不变。

未知 usage 保留上界；有发送意图但未冻结模型响应的恢复不能据此重发。账本不是响应缓存，不承诺复原已丢失的模型响应。普通任务的原 BudgetedProvider 还没有全部转成预留模型，因此不能宣称所有付费组件具备全局并发硬封顶。
