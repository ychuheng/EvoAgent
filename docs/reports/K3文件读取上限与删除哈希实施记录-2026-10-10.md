# K3 文件读取上限与删除哈希（2026-10-10）

## 变化

项目 `file_read` 原先先 sniff 头部，再 `Path.read_bytes()` 整读文件，行/字符范围只限制返回大小，不能限制读取内存。现在同一个描述符最多读取 8 MiB + 1 字节，超限拒绝。测试可注入更小限额，但不能提升默认硬上限；文件在读取前后增长也不能绕过读取长度。头部二进制检查、UTF-8 拒绝、路径限制、行范围保持原语义。

读取结果增加原文件 SHA-256；空文件也提供哈希。该哈希对应磁盘字节，不对应后续脱敏或加行号的模型视图，方便采用原文一致性前置条件。

`delete_file.expected_sha256` 改成必填 64 位小写十六进制；缺省、错误格式拒绝。实际删除和 dry_run 均核对原文哈希，不匹配时 edit_conflict，不能无条件删除。核对读取同样限制 8 MiB + 1 字节，超限需人工处理。目录删除与既有 read_write 授权/审批/ToolEffect 约束保持生效。

## 验证与边界

定向测试 44 passed / 2 skipped（Windows 无符号链接权限）；覆盖行范围不能绕过字节限额、禁止调用不受限 read_bytes、空文件/CRLF 原文哈希、dry_run/删除、缺省和非法哈希及改动冲突。冻结产品树 `17b0f64dc2559024261a606ec0165fcbff623bee` 首轮 Linux 全量 1264 passed / 18 skipped / 1 failed：旧并发反馈用例在 asyncpg 建连阶段 60 秒超时，没有返回业务断言失败。同树重新建立隔离数据库的 Linux 定向诊断（该并发用例两后端 + K3）9 passed。保留首轮失败证据；第二轮同一冻结树 Linux/Python 3.13/PostgreSQL/Redis 全量 1265 passed / 18 skipped（586.70s），Ruff check / format 441 files 通过。两轮之间没有改产品代码或放宽测试；远端 CI 待推送后核对。

本次是对已登记 K3 的资源/一致性前置条件修复。哈希检查不是操作系统提供的原子 compare-and-unlink；具有写权限的外部进程仍可能在检查到 unlink 的窗口并发替换。项目目录隔离/可信本机约束仍须成立。K2 的 Linux pids/cgroup 强制进程配额与逃逸验证不在此提交内，仍未完成。

兼容影响：删除工具参数 schema 变更会改变新工具目录 hash；历史 Skill 若缺 expected_sha256，不自动重写正文，重新静态校验时应拒绝，须显式修订并验证。旧持久 Run 不能把新目录当成旧目录继续执行。
