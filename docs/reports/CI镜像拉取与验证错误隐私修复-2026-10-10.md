## 问题与修复

`72a31281fb08b93e6c626b7697506be38957b6b4` 的 CI 两次在测试前遇到 Docker Hub 429，详见[启动记录](P3显式验证启动实施记录-2026-10-10.md)。不删测试、不屏蔽失败，不再盲目重试。工作流保留 frontend、两个 Python、sandbox、container 五个作业；将自动 services 改为 checkout 后创建的作业专属容器，以便先配置官方 Docker Hub 缓存。PostgreSQL 固定为本地验证所用镜像 digest；测试、演示及实际容器限制检查保持运行。

`scripts/ci_docker.py` 只允许 GitHub-hosted Linux、默认 Docker endpoint 及完整作业身份。配置合并保留已有 daemon 设置，在临时 CI runner 配置 [Google 官方 mirror.gcr.io 缓存](https://docs.cloud.google.com/artifact-registry/docs/pull-cached-dockerhub-images)。该缓存不保证所有镜像命中；缺失会回退 Docker Hub，仍可能限流，不能将其描述为已消除所有网络依赖。只对该临时 runner 重启 Docker，不配置本机或自托管宿主。服务绑定 localhost；清理同时核对所有权 label 和名称前缀，仅删除本作业容器。PostgreSQL 启动检查有 120 秒期限，Redis 必须返回 PONG；任何失败直接使 CI 失败。构建前拉取基镜像，避免构建阶段再次直接获取 Docker Hub 元数据。

个人验证冻结案例、验证结果和 Skill 定义的解析错误曾可能通过异常链带回原始值。相应入口改为稳定领域错误并抑制原异常链；回归用例检查完整 traceback 不含私有 marker，而不是只检查错误标题。不会改变成功解析和运行契约。
