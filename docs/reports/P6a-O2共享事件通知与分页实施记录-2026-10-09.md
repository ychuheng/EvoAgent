## 实现合同

`RunEventRepository.page_for_run` 按已提交 sequence 补读，每页最多 200；原 `list_for_run` 保留给 Trace/恢复。启用后 SSE 先登记本 Run 的共享监听，再取得 generation、查库；有积压立即读下一页，不每页 sleep。等待使用查库前的 generation，查完到等待之间的提示不会丢失。数据库仍是唯一事件来源，未提交序号不会进入 SSE；终态且积压清空才关闭，Last-Event-ID 和前端去重不变。

`RunEventNotifier` 在 API 进程共享一个 Redis 订阅；同 Run 的连接共享 condition/generation。没有事件正文、授权缓存或全局事件历史。活跃 Run 协调器最多 1024，提交提示待发送集合最多 1024，队列满合并/丢提示并累计 dropped_hints；超限连接仍从数据库补读。最后一个读者离开后删除协调器，进程退出清理订阅与发布任务。订阅失败、丢消息、发布失败与无 Redis 时按 2 秒间隔兜底补读；短 SSE heartbeat 配置会提前唤醒，不声称所有配置都固定 2 秒。

提交 helper 接在 SQLAlchemy Session 的 flush/outer-commit/rollback 生命周期，覆盖 UnitOfWork、直接 Session.commit 和 session.begin 上下文三种写入方式。Repository flush 只登记 Run ID；最外层事务成功后才发布。savepoint commit 只合并到父事务，rollback 丢弃相应集合。通知是 best-effort，失败不把已提交事实改成失败或重放。批量进度、审批、工具结果、来源门禁、任务终态等事件生产者通过同一 session factory 获得该 helper，没有各自再写一套提交回调。

装配位置包括 API、普通 Worker、维护 Worker、评测 Worker/CLI/演示入口。后四个复用 `Database.configured(settings)` 并清理拥有的 Redis/通知资源。sandbox controller 不生产 RunEvent，不为它增加通知连接。API 订阅建立后再接受请求；提示只携带 Run UUID，跨进程提示也只触发权威查询。

页面连续 MODEL_DELTA 折叠成一个进度状态项，只更新最近展示；审批、工具和模型完成边界仍各自保留。每个已提交事件仍推进 lastSequence，重连不会跳过事实。完整 Trace 和最终答复不受展示折叠影响。
