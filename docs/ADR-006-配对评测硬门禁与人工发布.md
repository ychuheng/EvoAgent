# ADR-006：配对评测、硬门禁与人工发布

- 状态：已接受
- 日期：2026-09-08
- 范围：阶段三模块 7～12

## 背景

阶段三前半段已经能从通过验证的 TRAIN Run 提炼 DRAFT Skill，也能检索人工准备的 ACTIVE 版本。但“模型生成了候选”和“候选值得进入默认运行路径”是两个完全不同的结论。如果缺少独立留出评测、不可变证据和人工决定，一个偶然成功、发生安全回退或只对训练样本有效的候选都可能被自动发布。

## 决策

### 1. 使用成对实验

每个 HOLDOUT Case 和 repeat 都创建一组 BASELINE/PINNED_SKILL Run。两边共享 Provider、模型、系统提示、工具清单与代码版本，只允许 Skill 相关字段不同。每对交替先后顺序，第一条完成后才释放第二条，减少固定顺序与并发资源竞争带来的偏差。

### 2. 实验协调和普通执行分离

`EvalCoordinator` 只创建占位、持有实验租约、释放配对任务、调用 Validator 和收尾。真正的 Agent Task 仍由普通 `JobWorker` 执行。实验租约到期后可以由另一 Eval Worker 接管；已经完成验证的 EvalRun 不会重复计入。

### 3. 缺失值保持未知

Provider 没有报告 Usage 时，Token 指标保存为 `null`，不使用零代替。只有配置可比较、两边均通过且 Usage 已知时才计算 Token 差；失败样本仍保留在正确性统计中，避免幸存者偏差。

### 4. 正确性和安全是硬门禁

静态定义、来源资格、Validator 支持、配对可比较性、总体正确性、任务族正确性和安全回退必须全部通过。效率属于辅助信息：Token 更少或延迟更低不能抵消正确性下降与安全退化，也不会因为没有效率收益而自动拒绝一个正确候选。

### 5. 报告和决定使用内容哈希固定

评测报告写入不可变 Artifact，并把报告哈希和门禁报告哈希写入 Experiment 与 SkillVersion。发布前重新验证 GateReport 的版本、实验、通过结果和内容哈希；已经绑定的报告引用不能被替换。

### 6. 自动门禁不拥有发布权限

通过门禁只把版本推进到 `REVIEW_REQUIRED`。人工 `approve` 才能在一个事务内退休旧 ACTIVE、激活新版本、更新聚合指针，并记录 PromotionDecision 与 SkillEvent。发布、禁用和回滚都要求 `expected_lock_version`，防止两个页面基于同一旧状态同时提交。

### 7. 回滚也是一次受约束的人工发布

回滚目标必须属于同一 Skill、处于 RETIRED、保留已通过门禁的哈希，并仍与当前工具目录和 Schema 兼容。回滚不会绕过校验，也不是把数据库指针任意改回旧 ID。

## 后果

积极后果：

- 每次发布都能追溯到来源、留出实验、报告哈希和人工理由；
- 评测 Worker 崩溃后可以继续，不会悄悄重复样本；
- 负面结果和未知指标被保留，简历指标可以由真实报告支持；
- 普通 API 无法借用 PINNED_SKILL 绕过发布状态。

代价与限制：

- 小样本报告只陈述均值、中位数和明细，不宣称统计显著性；
- Artifact 文件系统和数据库不是分布式事务，数据库提交失败可能留下不可达孤儿文件；
- 当前 reviewer 只是本地审计标签，没有认证、RBAC 或多人审批语义；
- 当前前端是 Skill/Eval 管理面，不是完整聊天产品；
- PostgreSQL 是并发发布和租约语义的正式事实来源，SQLite 只用于快速测试。

## 被否决的替代方案

- 用单个加权总分决定发布：会让效率收益掩盖正确性或安全回退。
- 候选生成后直接 ACTIVE：生成器既当作者又当审批者，无法建立信任边界。
- 只跑 Skill、不跑 baseline：无法区分 Skill 改善与模型、工具、提示变化。
- 恢复时重新创建实验行：会重复样本并污染统计。
- 让 GET 报告接口顺便执行门禁：只读请求不应产生状态迁移，因此使用显式 finalize 写操作。
