# Agent 运行模式与显式任务验收（2026-09-26）

本增量解决两种易混淆的状态：网页显示有回复不代表正在使用真实模型，Task `completed` 也不代表用户目标已经被独立核验。默认 `docker-compose.yml` 仍是确定性 Mock 演示；真实模型需按[网页对话运行说明](网页对话与真实模型运行说明.md)配置 API 和 Worker。页面的模式提示来自 `GET /api/v1/runtime-info`，只暴露 Provider 类型、模型名、搜索模式、记忆开关及代码版本，不暴露密钥和 Base URL，也不以就绪探针消耗模型额度。真实模式表示 API 配置有效；远端连通性只能由实际请求确认。Worker 执行前比较已排队 Run 的 Provider/模型与自身配置，不一致以 `provider_configuration_mismatch` 失败，防止真实模型任务被 Mock Worker 静默执行。

## 升级顺序

新增迁移 `20260926_0014` 在 Task 表加入可空 JSON 验收条件，不改变旧 Task。升级时先停止旧 API/Worker，执行 `alembic upgrade head`，再同时启动同一版本的 API 与 Worker；不要在有旧 Worker 消费新任务时开放验收输入。原有 Run 的空验收字段按旧语义继续执行。已配置真实模型的部署保持 API/Worker 两侧相同 Provider 与模型；API 的模式提示不替 Worker 健康证明。

## 可检查条件

网页“设置可核对的验收条件”支持以下三项，可只填一项或组合；API 也支持多个条件及文件 SHA-256。条件不会自动注入模型提示，用户应在任务文字中说明要求；条件只承担独立核对。无条件的任务仍能完成，但页面显示“未独立核验”。

```json
{
  "session_id": "<现有 Session UUID>",
  "goal": "搜索资料并生成 report.md，回答中写出结论 391",
  "acceptance": {
    "answer_contains": ["391"],
    "required_tools": ["web_search", "file_write"],
    "required_files": [{"path": "report.md"}]
  }
}
```

该 JSON 提交至 `POST /api/v1/tasks`。回答文本按不区分大小写的字面包含检查；工具条件要求同一 Run 中对应 `ToolCall` 为 `succeeded`；文件条件要求当前 Run 的受控目录里存在不超过 16 MB 的普通文件，可选 `sha256` 必须是小写 64 位十六进制并与内容匹配。文件路径只接受相对路径，不接受 `..`、绝对路径、盘符或冒号。每类最多 10 项；空对象和非法条件在创建任务时返回 422。

模型正常结束后，Worker 写入 `acceptance.checked` Trace 事件，逐项记录条件类型、目标和布尔结果。任一条件不满足时 Task/Run 进入 `failed`，错误码为 `acceptance_failed`；文件读取或冻结条件解析无法完成时以 `acceptance_check_error` 失败，而不当成通过。Trace 的 `final_answer` 保留模型原答，网页可展开检查。最终提交还要求存在 `passed=true` 的验收事件；若有验收条件却无该事件，就以 `acceptance_evidence_missing` 失败，避免仅凭模型终答绕过核验。条件通过只证明**这些显式条件**，不证明回答其余内容、资料真实性或开放式目标质量。工具执行错误仍会反馈给模型，允许其在迭代限额内自行修正；最终验收失败不会伪装为成功。
