> **可下载产物**的页面流程，以及项目外读取、网络、符号链接、文件权限、命令审批与资源限制的复查。

## 1. 逐结论引用核对（从"引用过"到"读过正文"）

原来的评测只检查"搜了几次、读了几篇、答复里的 URL 有没有记录"，并把"网页是否支持结论"整个
留给人工。本轮补上中间那一层：

| 交付 | 位置 | 说明 |
| --- | --- | --- |
| 逐结论判定 | `src/evoagent/evals/citations.py` | 按列表项/句末标点拆结论，逐条给出引用级别与判定：`backed_by_read_text` / `cited_without_reading` / `uncited` / `unknown_source` |
| 命令 | `scripts/check_answer_citations.py` | `--trace` 读已保存 RunTrace，输出核对表（`--markdown`）与机器可读结果（`--json`）；不通过时退出码 1 |
| 并入评测 | `scripts/personal_research_eval.py` | 新增自动检查 `conclusions_backed_by_read_text` 与 `per_conclusion` 报告字段（失败结论逐条列出） |
| 人工位 | [逐结论引用核对表](逐结论引用核对表-2026-09-28.md) | 四个冻结样本的空模板：机械判定 + "来源是否支持该结论"的人工判定列 |

**边界写清楚**：机械判定只回答"引用的来源是否真读过正文"，**不回答"网页是否支持该结论"**；
后者的结论、反例与不确定项必须由人填。测试见 `tests/unit/test_citations.py`（8 项）与
`tests/unit/test_personal_research_eval.py`（3 项，含"只引摘要/无引用一律不通过"）。

**未关闭**：四个冻结样本仍**没有真实模型运行**（需要费用授权），所以模板是空的——
不能把机械检查通过当成调研质量通过。

## 2. 文件任务 → 可下载产物（编码 / PDF / 目录整理）

`tests/integration/test_file_task_acceptance.py` 用持久化运行时跑完整链路（脚本化 Provider、
fixture 副本，`organize-lab`）：

| 环节 | 实测结果 |
| --- | --- |
| 非 UTF-8 文本 | `extract_text(encoding="gb18030")` 读出真实内容（含"历史资料""编码"） |
| 文本型 PDF | `extract_text("inbox/summary.pdf")` 返回正文 |
| 损坏 PDF | 工具调用 `failed`，错误码是**具体原因**（如 `pdf_unreadable`），不是笼统的 `tool_execution_error`；没有编造内容 |
| 目录整理（计划） | `organize_files(dry_run=true)`：`ready=2`、`conflicts=1`（目标 `reports/taken.pdf` 已存在），计划阶段不动文件 |
| 目录整理（执行） | `dry_run=false`：两个文件移动到 `notes/`，冲突目标**保持原样** |
| 产物出口 | `notes/summary.md` 登记为产物；预览内容 == 下载字节 == 磁盘字节，且 `sha256:` 与登记哈希一致 |

**顺带修好的缺陷**：`ToolExecutionError` 之前只带一个笼统错误码，`extract_text` 的
`pdf_unreadable` / `unsupported_text_encoding` 等具体原因被埋在消息文本里。现在工具可以把具体
原因作为错误码透出（`ToolExecutionError(..., code=...)`），页面与账本都能直接显示它。

## 3. 安全边界复查

### 3.1 命令隔离与"离线"是真的（Linux 容器内实测）

| 检查 | 命令 | 实测 |
| --- | --- | --- |
| 离线阻断 | `scripts/check_project_command_isolation.py` | 直连网络、项目外文件、`/proc/1/environ` 全部 `blocked`，项目内写入允许 |
| 放行开关是真的 | `scripts/check_project_command_limits.py` | `allow_network=true` 时 `socket.socket(AF_INET)` **成功**（否则"离线被阻断"可能只是网络永远不通） |
| 内存上限 | 同上 | 2 GiB 分配在 1 GiB 上限下失败（`rc=1`），不会把 Worker 拖死 |
| 时间上限 | 同上 | `while True: pass` 忙循环在 3 秒超时被终止（`timed_out=True`） |

### 3.2 符号链接、路径与权限（Windows 上跳过，Linux 里实跑）

Windows 宿主没有创建符号链接的权限，相关三条测试平时是 skipped。本轮在应用镜像里实跑
`tests/unit/test_project_tools.py`、`test_project_schema.py`、`test_project_editing.py`：
**40 passed / 1 skipped**（只有 Windows 专有的 junction 用例跳过）。覆盖：

- 项目内符号链接指向外部文件时，`file_read` 拒绝；
- 项目根本身是符号链接时，登记被拒绝（根与实际可见目录必须一致）；
- `edit_file`/`apply_edits` 拒绝通过符号链接写到项目外。

### 3.3 边界清单（本轮确认过的口径）

| 边界 | 口径 |
| --- | --- |
| 项目外读取 | 相对路径逃逸、绝对路径越界、符号链接指向外部一律拒绝（M1/M2 负向测试 + 上述 Linux 实跑） |
| 网络 | 命令默认 seccomp 阻断非 Unix socket；`allow_network=true` 需显式参数 + 逐次审批，实测放行 |
| 符号链接 | 读、写、登记三类入口都拒绝指向根外；Windows 无法验证的部分改为在 Linux 容器内验证 |
| 文件权限 | 编辑保留编码/BOM/行尾与权限位（M2 契约与单测）；POSIX 模式的实跑同样在 Linux 容器内 |
| 命令审批 | 按 argv 分类：可识别的离线检查自动放行，构建/安装/通用解释器逐次审批，`git push`/`npm publish` 直接拒绝 |
| 资源限制 | 单进程 CPU/内存 + 墙钟超时杀进程组 + **进程树级进程数配额**（`EVOAGENT_PROJECT_COMMAND_MAX_PROCESSES`，默认 256；父进程按会话统计，超限 `SIGKILL` 整组并置 `process_limit_exceeded`） |
| 容器命令 vs Windows 宿主 | `run_command` **只在 Linux 容器内执行**；Windows 宿主直接拒绝（`tool_execution_error`），不存在"宿主裸跑"的退化路径。宿主侧 Windows 工具链要另经 MCP/沙箱组件，不在本工具范围内 |

### 3.4 进程树级资源配额（2026-09-28 补做，Linux 容器实测）

原登记为"未做"，本轮补上并实测。做法是父进程按**会话**统计命令子进程树的进程数（命令子进程是
`setsid` 后的会话首进程，double-fork 也甩不掉统计），超过 `EVOAGENT_PROJECT_COMMAND_MAX_PROCESSES`
即 `SIGKILL` 整组，`run_command` 结果里如实返回 `process_limit_exceeded=true`、`return_code=-9`。

**否掉的替代方案**：内核 `RLIMIT_NPROC`。它的计数是**整个 user namespace 里该 UID 的进程数**，
不是某棵进程树、也不是某个容器：本机实测同一个应用镜像里 PID 命名空间内只有 1 个进程时，
上限 **40 连第一次 `fork` 都拒绝**（EAGAIN，要到 80 才放行），差额来自同机其它以同一 UID 运行的容器。
它做不了 per-command 配额，还会连带让命令自己的沙箱初始化失败——`ctypes.util.find_library("seccomp")`
在 Linux 上要去跑 `ldconfig`，也就是"沙箱初始化需要 fork"。因此顺带把初始化改成先 `dlopen`
已知 soname（`libseccomp.so.2`），不再依赖 fork。

| 检查（容器内 `scripts/check_project_command_limits.py`） | 结果 |
| --- | --- |
| 200 次 fork 的失控循环，上限 16 | **0.718 s 内整组被杀**（`rc=-9`、`timed_out=false`、`process_limit_exceeded=true`），随后扫 `/proc` 确认**无存活子进程** |
| 正常 4 进程并行命令，上限 16 | 照常完成（`children:4`），`process_limit_exceeded=false`——配额不误伤 |
| 紧配额（16）下的离线网络 | 仍被 seccomp 阻断（`network:BLOCKED`），说明初始化不再依赖 fork |
| 上限低于下限（8） | 启动前拒绝：`项目命令进程数上限不能低于 8` |

代价如实记录：**有界超杀**——最多多跑一个轮询间隔（50 ms）的进程，随后整组被杀。
