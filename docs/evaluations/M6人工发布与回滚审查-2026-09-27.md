# M6 人工发布与回滚审查（S-04，2026-09-27）

> 范围：计划 §11 的 **S-04 人工发布与回滚**。本文记录的是**人工审查这一层**的落地方式：
> 审查记录要绑定来源、diff、评测与安全影响四项证据，并回答"它学到了什么、帮了什么、
> 失败在哪里"。
>
> **当前没有任何 Skill 走完这条路径**：真实模型运行尚未执行（见
> [冻结对照实验路径](M6冻结对照实验路径-2026-09-27.md)第 4 节），因此"发布并监测"、
> "效果退化后禁用/回滚"都还没有真实案例。本文只声称机制完整、可核对。

## 1. 已有机制与本路径的分工

| 层 | 已有实现 | 本路径补的部分 |
| --- | --- | --- |
| 状态机 | `skills/lifecycle.py`：`draft → evaluating → review_required → active → retired`，非法迁移直接报错 | — |
| 发布/禁用/回滚 | `skills/service.py`：`approve`（要求 GateReport 通过）、`reject`、`set_status`、`rollback`（要求目标版本已 retired 且有已接受的报告哈希），每次都写审计决策行与事件 | 调用它们**之前**的人工审查记录与闸门 |
| 评测门禁 | `evals/gates.py`：静态、来源、正确性、安全四层 `GateCheck`，效率只作信息 | 审查记录必须绑定该报告的哈希与判定 |
| 人工审查 | 只有 `reviewer`/`reason` 两个自由文本字段 | 结构化审查记录 + 可核对的检查项 + 给人读的审查页 |

实现位置：

- `src/evoagent/skills/review.py`：审查记录模型、静态安全扫描、检查项与渲染。
- `scripts/m6_skill_review.py`：`template` / `scan` / `validate` / `render` 四个子命令。
- `tests/unit/test_skill_review.py`：24 项，覆盖三类动作、结论强度与安全发现处置。

## 2. 审查必须回答的三件事（计划 S-04 的完成判据）

| 问题 | 记录字段 | 检查 |
| --- | --- | --- |
| 它学到了什么 | `learned` | 至少 20 字且不是占位符（`todo`/`待填`/`略`…） |
| 它帮了什么 | `helped` | 同上，并且结论强度必须与评测判定一致 |
| 它在哪里失败 | `failed` | 同上；只写正面收益不算完成 |

四个审查维度各要附证据（写清看了哪些运行、哪些文件/哈希）：

| 维度 | 要审的内容 | 例子 |
| --- | --- | --- |
| `sources` | 提炼来源属于 dev/日常真实任务、可追溯到 `source_run_id`、敏感数据已脱敏或排除 | `run dev-001（dev 任务，人工确认成功证据）` |
| `diff` | 这次版本相对上一版改了什么 | `definition_json 仅新增 stop_conditions 与 counterexamples` |
| `evaluation` | 评测判定、门禁结论、报告哈希 | `配对实验 m6-exp-001，p=0.004，报告哈希 sha256:abc` |
| `security` | 风险等级、可用工具、是否需要审批、有无未缓解风险 | `只读工具；无写入、无网络、无凭据` |

## 3. 三条硬约束（代码判定，不是建议）

1. **结论强度不得高于评测证据**：`claim_scope` 必须与配对实验判定一致
   （`positive_confirmed → confirmed_benefit`、`exploratory_only → exploratory_only`、
   `inconclusive`/`not_claimable → no_effect_claim`、`negative_confirmed → regression`）。
   写错就报"不得让审查结论强于证据"。
2. **较强收益结论必须有第三方复核**：`claim_scope="confirmed_benefit"` 时
   `reviewer_role` 必须是 `third_party`；自审只能报告带自评限制的探索性结果
   （与计划 §5.4 的 ≥20% 预留一致，见[第三方复核记录](第三方复核记录.md)）。
3. **安全发现必须逐条处置**：静态扫描 Skill 文本，发现凭据样式、私有绝对路径
   （`C:\Users\…`、`/home/…`）或 holdout 数据集/夹具名时登记为发现项；
   未在 `acknowledged_findings` 里处置即不得发布。

另外，发布另有监测计划与回滚方案两项必填；评测判定为显著退步时应禁用/回滚，
检查项 `claim_is_not_regression` 会直接拦住"退步还发布"。禁用与回滚各有独立前置条件
（禁用要原因；回滚要求目标版本已 retired 且带已接受的报告哈希），与 `SkillService.rollback`
的前置检查保持一致，避免审查闸门与产品代码脱节。

## 4. 本次实测（2026-09-27）

用空模板实跑，确认闸门真的会拦：

```
python scripts/m6_skill_review.py template --skill-id ledger-summary-anchors \
    --version-id 11111111-1111-1111-1111-111111111111 --action publish --out tmp/review-template.json
python scripts/m6_skill_review.py validate --record tmp/review-template.json
```

结果：**8 项未通过**（三段解释未写、四个维度无证据、评测证据未绑定、风险等级未声明、
监测计划与回滚方案缺失），`scan` 预检无安全发现。空模板不会被当成通过。

`tests/unit/test_skill_review.py` 用合成记录覆盖了通过路径与各自的拒绝路径
（含"探索性结果被写成已确认收益"、"自审想支撑已确认收益"、"未处置凭据发现"、
"回滚目标未 retired"、"退步仍发布"）。**这些是机制测试，不是发布证据。**

## 6. 与计划条款的对照

| 计划 §11 S-04 | 落地 |
| --- | --- |
| 审查来源、diff、评测与安全影响 | 四个维度各自必须附证据，否则 `review_dimensions_present` 不通过 |
| 发布版本并监测 | 发布必须写监测计划；记录在审查页的"处置与回滚"一节 |
| 效果退化可禁用/回滚 | 禁用要原因；回滚要求目标已 retired 且有已接受的报告哈希；显著退步时禁止发布 |
| 用户能解释"学到了什么、帮了什么、失败在哪里" | 三段解释是必填且非占位符，并直接渲染成审查页的前三节 |
