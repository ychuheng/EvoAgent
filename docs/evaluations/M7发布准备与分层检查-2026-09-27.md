| 付费闸门（未填额度） | 拒绝且不联网 | `failed`，消息 `persistent runtime failed: BudgetExceededError`，`tool_calls=[]`（确实没发出请求） |

两个**需要记录的观察**（不是通过项）：

1. Redis 故障被报成 `rate_limited`（限流）而不是"依赖不可用"。行为是**安全的**
   （不发出外部请求、可自行恢复），但错误码会误导排障；建议后续区分"配额"与"依赖不可用"。
2. 预算闸门的拒绝同样以通用码 `persistent_runtime_error` 呈现（消息里才有
   `BudgetExceededError`）。拒绝本身正确，但错误码不足以让运维一眼看出是额度问题。

### 2.4 本轮演练发现的真实缺陷：真实模型路径完全不可用（已修 + 复测）

第 3 层虽未执行，但降级演练要求真实 Provider 路径可用，于是立刻暴露出一个**发布阻断级缺陷**：

- **现象**：任何走真实 Provider 的任务都在第一次模型调用时 `failed`，
  `model.failed` 事件是 `internal_provider_error` / `error_type=ImportError`，
  最终 `persistent_runtime_error`。离线 Mock 任务正常，因此此前所有"真实模型"证据都来自更早的镜像。
- **根因**：`workers/rate_limit.py` 的 `BudgetedProvider.stream`（只在**非 Mock**路径上包装）
  写成 `from evoagent.providers.base import ProviderEventType`，而该名字定义在
  `evoagent.core.models`。这条 `ImportError` 在发出 HTTP 请求之前就抛出。
- **修复**：改成从 `core.models` 导入，并加注释说明为什么只有真实 Provider 会踩到。
- **复测**：新增两项回归测试（`tests/unit/test_worker_services.py`）——
  "带 usage 的流能被预算包装层正常转发并记账"与"未填额度时拒绝且不发出请求"；
  把导入改回错误写法后前者**确实失败**（ImportError），修复后通过。
  容器内复测：不可达模型现在报 `provider_network_error`（修复前同一个场景报
  `persistent_runtime_error`/ImportError）。

## 5. 发布决定

**结论：候选版（candidate），不放行 `v0.4`。**

理由：四层里通过了两层（契约/单元、集成），一层只做了部分替代（干净环境演练，且已发现并
修掉一个真实阻断缺陷），两层完全没做（真实模型任务、人工审查）。按计划"到 M7 若核心项目闭环
或边界门槛仍不过，明确停在候选版并列出未达成目标"，现在的状态正好落在这里。

**放行前必须完成**（按依赖顺序）：

1. 冻结 M0c 的**正式**额度、价格假设与 M6/M7 样本预算（试跑额度已在 2026-09-28 用掉，正式 scope 仍关闭）；
2. 用真实模型跑 M7 的 24 条正常样本与 8 条故障/越权样本（先修掉或明确接受第 3 节的未修缺陷），
   计算正常整体成功率、核心项目任务成功率与越权成功数；
3. 按 `rubric-1` 完成人评并写明自评限制；如要提出较强收益结论，先指定未参与实现的第三方复核者；
4. M6 至少一个 Skill 在未暴露 holdout 上达到预注册门槛（当前库存 4/78，须先补样本并实测失配率）；
5. 在新装 Windows + Docker 环境上重跑第 2.3 节全部演练（这是"干净环境"的原意），
   并补 Linux Docker 沙箱层与命令进程树配额；
6. 把当次数字写进[当前状态](../当前状态.md)并推进漂移基准。

**当前可以对外说的**：机制完整、受控测试与集成测试通过、干净卷部署与备份恢复演练通过、
32 条发布样本已登记、真实模型在 **dev 样本**上完成了项目地图/失败修正/运行中介入/搜索摘录等单个任务；
**不能说的**：发布集的真实模型通过率、Skill 收益、或"可以在新机器上直接发布"。
