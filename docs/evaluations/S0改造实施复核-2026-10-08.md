## 结论

S0a/S0b 的多数基础代码已经落地，新增 14 个提交涉及共享脱敏、配置保护、artifact 读取门禁、检查元数据迁移、工具视图、编辑保护、隔离复核与命令可观测性。不过，不能将“七项功能都有代码”直接等同于整个 S0 已验收：本轮补充复现确认了四个边界问题，且 Memory 门禁、受限扫描和若干发布证据仍未补齐。

## 已复现的问题

### F1（P1）：部分覆盖敏感命中区间仍允许写盘

位置：[projects/editing.py](../../src/evoagent/projects/editing.py)，`check_sensitive_edit` 第 198 行；写前调用约第 337 行。

当前只对 `located_span` 再次运行正则，不判断编辑区间是否与**完整原文**中的敏感区间相交。合成文件中 `password: FAKE_ONLY_FOR_REVIEW` 会被当前规则隐藏；old_text 只选 `FAKE_ONLY_FOR_REVIEW` 时，片段不含 password 前缀，检查通过，磁盘被修改。跨行私钥的中间行同样存在片段规则上下文丢失问题（本轮具体运行复现的是密码值子串）。

建议在原始全文上取得命中区间，_locate 返回 start/end，以区间相交判断。现有 RedactionHit 坐标属于逐规则替换后的中间文本，不可直接当成原始文件坐标；需增加原文坐标专用检测接口。保留邻近正常编辑与整个批次零写入测试。

### F2（P1）：读取期间已擦除的 artifact 仍返回正文

位置：[privacy/artifact_access.py](../../src/evoagent/privacy/artifact_access.py)，`read_verified_text` 第 151 行及 `mark_verified`。

最初查询检查 erased/来源状态后释放会话，再读取/扫描；复用检查结果的分支直接返回，扫描通过分支也没有最终状态复验。`mark_verified` 只核对 ID/Run/hash，还可能将扫描期间新隔离的状态覆盖为 verified。

本轮用受控存储包装器复现：读取 bytes 后、返回 Guard 前，在临时 SQLite 中把同 artifact 的 `attributes.erased` 标记为 true，Guard 仍成功返回 CLEAN_TEXT。这个复现模拟并发擦除状态提交，不声称已测所有来源撤销/隔离竞争。

建议两条返回分支都在短事务中复验授权、擦除、quarantine、hash/版本；mark_verified 不得覆盖并发 quarantine。明确提交/返回的线性化点，缓存不能取代最后门禁。新增擦除/撤销/隔离发生在读取和扫描之间的用例。

### F3（P1）：扫描预算不是硬限制，且在限尺寸前已整读

位置：[privacy/artifact_access.py](../../src/evoagent/privacy/artifact_access.py)，`_rescan` 第 266 行、`_scan`；[trace/artifacts.py](../../src/evoagent/trace/artifacts.py) 的 LocalArtifactStore._read。

`_rescan` 同步调用 redact_text_result，调用结束后才比较耗时。它在 async 调用链上阻塞事件循环，500 ms 只代表“之后拒绝结果”，不代表“500 ms 内停止扫描”。存储 read_bytes/UTF-8 decode 完成后才做尺寸限制，超大文件已进入内存；已验证缓存分支还绕过扫描大小判断。

合成慢检测器复现：配置 5 ms，检测耗时约 80.9 ms 后才返回 scan_timeout。该数字仅验证超时语义，不是真实规则吞吐数据。计划中的有界读取、可终止扫描执行器、并发/队列上限与离线扫描尚未落实。

建议先提供 bounded read；把 CPU 密集检测移出事件循环，使用可终止的受限执行器。尺寸常量由 8 MiB 调整为 10 MiB 本身不必视为错误，但需要当前 v2 规则的基线和明确批准的参数合同；不能用旧版本合成吞吐报告证明硬超时已实现。

### F4（P2）：复核幂等回放没有绑定 artifact

位置：[privacy/artifact_access.py](../../src/evoagent/privacy/artifact_access.py)，`_find_review` 第 493 行。

事件查询按同 Run + event_type，循环只比较 client_request_id，不比较 payload.artifact_id；同 Run 的 A、B 使用同 ID 时，B 得到 A 的 cleared 回放，但 B 实际仍 quarantined。本轮临时数据库已复现：API 核心方法报告 cleared/replayed=true，B 状态 quarantined。

此外成功事件没有保存 checked_hash，第二次成功回放的 checked_hash 为 null；只查最近 200 条事件也不能构成长期稳定的幂等保证。回放入口在复核条件检查之前，应重新确认当前访问权限，区分历史结果与当前状态。

建议用 `(artifact_id, client_request_id)` 与规范请求 hash 收口，完整保存响应所需字段；同 ID 改条件/理由应有明确冲突语义。通过精确数据库条件查历史，避免跨资源串结果与截断窗口；并发重复提交需有 DB 唯一约束或锁内校验。
