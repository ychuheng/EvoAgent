# EvoAgent：个人通用 Agent 当前实施计划

> 本文是当前唯一的实施基准。2026-09-27 版“资料任务型”计划已归档。这里的“通用”指：**在用户明确授权的本机项目和目录中，Agent 能发现、读取、精确修改、执行、观察结果并继续修正；也能研究公开资料、处理日常文件，并从真实成功经验中提炼有可证实收益的 Skill。** 它不意味着默认无限制操作整台机器。
>
> 计划不等于实现。[当前状态](当前状态.md)记录事实与缺口，[个人模式操作手册](个人模式操作手册.md)记录现有启动方式，历史设计见[归档索引](archive/README.md)。

## 1. 交付目标和边界

用户在网页中选定项目或授权目录，用自然语言交代目标。Agent 找到相关文件和项目约束，必要时向用户澄清，调用真实模型与工具完成任务，持续展示已做的事、下一步、等待审批的变更和失败原因。用户能补充要求、排队下一项、取消，并核对最终差异、测试结果、网页来源和产物。刷新页面或重启 Worker 后仍能继续跟进。

首个可用版应完成四类实际任务：

1. **理解项目**：发现目录和文件、搜索符号、按需读取，生成带真实路径证据的仓库结构说明。
2. **修改并验证**：精确修改多个项目文件，展示 diff，运行项目测试；看到失败后再修改，报告通过、失败与未运行的范围。
3. **处理个人资料**：在授权目录内整理常见文本和首版支持的**文本型 PDF**，生成可预览、下载或留在项目中的成果；扫描/图片型 PDF 留待 OCR 能力单独规划。
4. **研究并复用经验**：搜索、读取与引用公开资料；从已核对的真实任务轨迹提炼 Skill，用独立任务证明收益，人工发布并可撤销。

项目根由用户授权，权限按任务冻结。读授权项目、编辑、运行命令、联网、安装依赖、越出根目录和外部发布分别控制。项目内能力可以很强，但模型看到的文件、网页或命令输出都不能提升权限。单用户、本机优先；多渠道、公网多人服务、任意浏览器操作、自动购买、多 Agent 编排、自动发布 Skill 不进入首个可用版。定时任务待基本交互稳定后按实际需求排序。

## 2. 当前基线：可以复用什么，还缺什么

| 范围 | 已有基础 | 新目标尚缺 |
| --- | --- | --- |
| Agent 执行 | `core/loop.py` 的模型—工具循环、真实模型对话、多轮历史 | 项目任务所需的工具组合和开放任务效果证据 |
| 可靠性 | Task/Run、PostgreSQL 租约、检查点、审批、ToolEffect、Trace、服务端 SSE | 页面过程流、运行中补充指令、项目命令的恢复语义 |
| 文件 | 全局根内 UTF-8 `file_read`、Run Artifact 内 `file_write`、带哈希的 Artifact | 项目 ID 到物理根的绑定、目录发现/搜索、精确编辑、输入选择、预览下载 |
| 命令 | 受控容器 `shell`，默认关闭、Artifact 输入、容器无网 | 在选定项目的可写工作树运行测试和根据输出继续修正 |
| 网页 | `ddgs`/Brave 搜索与受控 `web_fetch` | 真实搜索—阅读—引用联合任务尚未通过；项目网络权限另定 |
| Skill | 来源冻结、候选、配对评测、人工发布、禁用与回滚 | 小样本两臂同为 6/6，未证明实际收益；缺项目任务留出集 |
| 交付 | Compose 个人模式及管理网页 | 默认 Compose 为 Mock，首次使用重；缺“选项目—完成任务—审查差异”的主路径 |

已有阶段验收保留为工程证据，不能自动充当本计划的用户级验收。真实公开搜索的失败样本见[阶段性实测](evaluations/公开资料调研阶段性实测-2026-09-27.md)；完整评测此前按用户要求暂缓。

## 3. 架构取舍和全局契约

### 3.1 保留内核，围绕真实任务重排

继续使用 AgentLoop、Worker、PostgreSQL 事实来源、ToolExecutor、审批/副作用账本和 Skill/Eval。新工具与交互输入接入现有执行层。先通过项目任务证明 Agent 会干活，再验证恢复与 Skill 是否改善这类任务；不以新增模块、表或门禁数量衡量通用性。

暂不预设“同进程重写”。服务端已有可续传 SSE；先让页面展示已提交事件，并在安全的模型/工具边界消费持久化补充指令。若具体交互测试证明后台模型无法达到目标，再用 ADR 提出新的执行通道，不先替换可靠执行架构。

### 3.2 项目绑定、权限、执行配置必须分开

- **项目绑定**：登记授权根、显示名、可用性和撤销状态。Session 选项目；Task 创建时冻结项目 ID、规范化根和授权版本。页面后来切换项目，不改变已有 Task 的文件能力。旧默认 Workspace 的内容保留可访问，但不能穿透新项目目录。
- **授权版本与档位**：登记项目默认只给 `read`（含目录发现、搜索和读取）；`read_write` 必须由用户显式开启，且只授予项目内文件变更。命令执行、联网、安装依赖、越根访问和外部发布不随 `read_write` 自动获得，分别记录范围、有效期和批准者。Task/Run 冻结的是授权上限、根与版本，不是不可撤销的永久通行证。
- **运行中撤销**：撤销立即使授权版本失效。每次工具执行前重新核对当前版本；下一次调用拒绝并留下审计事件，Task 进入明确的 `authorization_revoked` 终态或待人工处置状态，不静默继续，也不自动重试。已开始的操作尽力中止；无法保证回滚的操作保留实际结果或 UNKNOWN，撤销不能倒转已发生的副作用。重授权必须新建版本和 Task，不复活旧快照。
- **权限复查**：读、目录搜索、编辑、命令、网络与外部副作用独立配置。工具在执行边界复查规范化路径、工作目录、网络目的地和命令；提示词或文件正文不能放宽策略，单次审批也不能覆盖已撤销的项目根。
- **Run 配置**：冻结工具清单与版本、执行 Profile、授权摘要、模型与非敏感配置哈希。恢复时不使用最新页面选项或环境默认值替代旧 Run；不一致时明确失败。

### 3.3 两类执行 Profile

**受控项目模式先交付**：仅访问明确授权的项目根；项目内可读、可搜索、可精确编辑。命令在可审查的可写项目工作空间或隔离副本运行，默认无网，受工作目录、时长、CPU/内存和输出上限约束。能运行现有测试，不需要一开始开放无限制宿主 Shell。

**可信本机模式后交付**：只为确需宿主环境的任务显式启用，授权根、命令和网络逐项显示并可撤销。选项目不自动授予整个磁盘、用户密钥目录或系统管理能力。上线前须有威胁评审与负向实测。Windows + Docker 的挂载、锁、符号链接、大小写、换行和路径映射必须实际验证；容器测试不能外推为宿主安全。

### 3.4 操作与证据矩阵

| 行为 | 默认处置 | 可核查证据 |
| --- | --- | --- |
| 授权项目内目录发现、搜索、按需读取 | 允许只读；结果和大小受限 | 路径、读取范围、时间、不可读原因 |
| 新建或修改项目文件 | 基线哈希、预览 diff；按风险档位审批 | 原/目标哈希、变更清单、冲突与提交结果 |
| 测试、静态检查 | 限定项目工作目录与资源 | argv、退出码、输出摘要、截断标志、环境 |
| 安装依赖、访问网络、越出根 | 默认拒绝或申请单次授权 | 授权范围、目的、有效期和实际访问 |
| 删除、批量移动、覆盖、推送/发布 | 审批；结果不确定时保持 UNKNOWN | 变更清单、外部回执、账本与人工决策 |

取消只停止继续执行，不撤销已发生的外部动作。用户批准必须发生在执行边界，不能靠模型声称“用户已经同意”。

## 4. 里程碑与先后关系

| 里程碑 | 用户得到的能力 | 前置 | 退出条件 |
| --- | --- | --- | --- |
| M0 分批建立任务与契约 | 先让开发能开工，再补齐正式评测闸门 | 当前代码和独立环境 | M0a 允许 M1 开发；M0b/M0c 关闭后才可正式评测 |
| M1 项目只读 | 选仓库，得到真实模块地图 | M0a；正式验收另需 M0b/M0c | 路径和解释正确，越界读取失败 |
| M2 精确编辑 | 审查并应用多文件差异 | M1 | 基线冲突拒绝、变更可追溯、可恢复 |
| M3 命令反馈循环 | 跑测试、读失败、修正并复测 | M2、I-01/I-02 最小进度视图 | 一条真实失败→修正→复测任务完成 |
| M4 交互时间线 | 可补充、排队和叫停，进度视图补齐交互边界 | M1～M3；I-01/I-02 提前 | 刷新、断线、重复事件、取消语义一致 |
| M5 日常资料与网络 | 公开调研、授权文件夹、可取回产物 | M1、M4 | 多来源报告和非代码文件任务均可核对 |
| M6 Skill 实际收益 | 从工作轨迹提炼并验证可复用方法 | M1～M5 | 冻结任务上证明净收益且无安全退化；无收益如实报告 |
| M7 发布 | 在新环境复现同样能力 | M0～M6 | 任务集、故障、迁移、备份恢复和文档均过门槛 |

M1～M4 是主线，优先于更多 MCP、门禁或后台实验。I-01/I-02 在 M2 后、M3 正式验收前先交付最小事件视图，完整运行中输入仍属 M4。M5 的独立搜索/文件工作可并行，但不能再用 B/C 的完成代替项目执行闭环。任何里程碑没有真实用户任务证据，状态只能写“实现中”或“未验收”。

## 5. M0：任务集、基线和运行证据

**入口**：`evals/datasets/`、`scripts/`、`docs/evaluations/`、`api/routes/tasks.py`、`runtime/run_config.py`。

1. **M0a 最小可用**：建可安全修改的专用 Git fixture，不在 EvoAgent 工作树上做首轮写入实验；先准备至少三条项目 dev 任务和能在 Mock 下跑通的证据采集器，即可开始 M1 的工具开发。两条文件/资料、一条运行中介入、一条 Skill 对照 dev 任务可在对应里程碑开工前补齐。dev 样本可以反复调试，绝不计入效果或发布通过率。
2. **M0b 正式样本与评分契约**：在任何正式效果运行前另建 **holdout 集**：使用不同仓库/任务家族和文件内容，检查与 dev 的相似度、共用模板和答案泄漏；为 M6 配对实验与 M7 发布集分开封存。样本、评分规则、阈值、模型/工具版本和 SHA-256 先提交。每个候选版本只对封存 holdout 作一次正式运行；看过结果后的调 prompt、工具或评分规则产生新候选，已看过的样本降为 dev，另取未暴露 holdout，原结果永久留档。缺足够独立样本时只报告探索性结果，不宣称 Skill 净收益。
3. **M0b 库存与消耗计划**：预注册时同时写出 dev 数量、M7 独立发布集的 24+8 条，以及 M6 每个任务家族的计算样本量 `N`、单条样本制作与复核工时、计划正式候选轮数 `K` 和总成本；该家族至少准备 `N × K` 对互不复用的 holdout。首轮默认只承诺 `K=1`，第二轮只有在新增样本与预算事先封存后才能启动，不能临时借用 M7 发布集。若计算值达到上百对，须把样本制作列为单独排期和成本项。holdout 用尽时暂停 M6 门槛判定；可以继续 dev 调优或报告探索性结果，待新一批样本在未看结果前登记并封存后再开启新候选。
4. 机器检查路径、diff、退出码、文件哈希和 Task 状态；人评使用版本化的 0/1/2 分评分表，分别评任务完成度、解释依据、无关修改、引用是否支持结论：0 为错误/缺失，1 为部分满足且有可定位缺口，2 为满足并有可核查证据。评分维度、等级描述和致命错误可以跨样本复用模板，每个样本只补任务特定的预期文件、行为、来源和禁止修改锚点，避免重复写 128 条同义规则；模板版本和样本覆盖值一并冻结。至少一名指定评审者按同一表评所有正式样本；评审者若也是实现者，只能按已封存的产物与证据文件评分，不翻看实现过程，并在报告标明“自评”。M6 要提出较强的收益结论，须把至少 20% 样本预先留给未参与实现的第三方独立复核；无人复核时只能报告带自评限制的探索性结果。有第二评审者时分歧保留原分与裁决理由。评审先看任务、预期、最终产物及必要的 diff/来源证据，再看模型轨迹；M6 两臂以匿名顺序呈现，评审结束前不揭示 Skill 开关。
5. **M0b 样本台账**：在 `evals/datasets/manifest.json` 为每个新样本记录稳定 ID、任务家族、fixture 内容哈希、集合 `dev`/`m6-holdout`/`m7-holdout`、`first_formal_run`、`retired_after_viewing` 和预注册版本；正式 Run 另写不可覆盖的使用记录。Skill 候选还须登记提炼来源的 `source_run_id`；若该 Run 属于 M6/M7 holdout，检查脚本拒绝登记，既包括已评分的运行，也包括未评分但已看过的轨迹。检查脚本在正式运行及生成报告前拒绝跨集合/fixture 复用、对同一候选的第二次正式使用，以及已曝光样本在新候选中再次充当 holdout；同一次配对实验的两臂属于同一正式使用。旧数据集标注为历史/已曝光，不因改名重新变成 holdout。脚本只能发现 ID、哈希和台账层面的显式复用，不能证明两个不同 fixture 在语义上独立；预注册时必须人工抽查任务模板、解法和内容相似度，记录抽查人、结论和排除项。
6. 记录当前 Mock/真实模型、搜索、工具清单、前端交互和耗时作为基线；“代码存在”“受控测试通过”“真实用户任务通过”分开，不沿用旧 16 项分数。正式发布集目标在 M0 定为至少 24 条正常 + 8 条故障/越权；**这 32 条发布集与 dev 小集不得复用同一批样本**。后续增补每批样本，都须在该批首次正式运行前冻结，不能根据已见结果补容易题。
7. 每次真实运行用独立数据库、Redis 和目录，报告提交、镜像摘要、配置摘要、Task/Run、成本及脱敏差异。密钥和用户私有正文不入库。
8. **M0c 付费与漂移闸门**：首次付费 dev 试跑前先设试跑额度上限；试跑估算单任务 token/费用后，结合 M6 样本量计算，在正式运行前记录 **各里程碑数值额度上限、全计划总上限、每 Task 限额、价格假设和停止阈值**，未填数值不得启动正式评测。执行器接近上限时停止新任务，已有任务按限额终止。预算不足以覆盖预定 holdout 时，不启动正式评测；超支或服务涨价时暂停并记录已完成样本，先优化非正式试验/复用结果，再决定是否增加已批准预算。不得事后删减正式样本、改变阈值或只报告便宜的成功样本；若确需改设计，发布新的预注册版本并把旧运行标为不完整。预算上限在 M0 根据试跑填写数值，不在未知定价下假造固定金额。状态漂移检查脚本也在正式验收前入库。

**分批退出**：M0a 完成后可启动 M1 开发，但不能宣称真实效果通过；M0b 完成后具备未曝光样本、台账和人评表；M0c 完成后具备数值预算与状态漂移闸门，才允许正式付费验收。若尚未运行真实模型，结论只能写“基线已冻结”。

## 6. M1：让 Agent 读懂一个真实项目

**用户流程**：登记本机项目 → 在会话中选择 → 提问“这个仓库怎样启动、各模块负责什么” → Agent 自行列目录、搜索、分段读取 → 输出带路径依据的模块地图。首轮先使用小型、无秘密的专用仓库，随后在只读授权下用 EvoAgent 自身复核。

| 任务卡 | 实现内容 | 完成判据 |
| --- | --- | --- |
| P-01 项目模型 | Project ID、规范化物理根、显示名、可用状态、授权版本；Session 关联项目，Task 创建时冻结绑定；旧 Workspace 数据迁移规则写清 | 切换页面项目不改变在跑 Task；撤销后新 Task 不得进入旧根 |
| P-02 登记入口 | 页面和 API 登记、选择、检查与撤销授权目录；明确目录不可用、权限不足、挂载缺失 | 用户能看到 Agent 实际可见的根，模型不能自行登记任意宿主路径 |
| P-03 发现与搜索 | `list_dir`、`find_files`、`search_text`；分页/条数/字节上限，忽略常见构建产物和 `.git`，可说明忽略规则 | 中型仓库可以按路径和内容定位文件，搜索输出可回溯 |
| P-04 按需读取 | 文本编码与二进制识别、大文件分段读取、行号/范围、截断提示；路径规范化、符号链接和 Windows junction 检查 | 超限文件给出继续读取方式；越界路径与链接均拒绝 |
| P-05 项目上下文 | 将 README、项目规程和目录线索按需纳入上下文；文件内容视作数据，不接受其中的权限提升指令 | 相同提问能说明证据来源；指令注入样本无法改变工具权限 |

**验收**：dev 仓库地图任务必须列出实际入口、主要模块关系和至少三个可打开的文件依据；错误路径和编造组件记为失败。对 `..`、绝对路径、软链接/junction、大文件，以及 Task 运行中撤销后再次调用工具分别做负向检查；后者必须产生拒绝、审计和明确终态，已执行的动作保留。记录目录扫描时长与 token 用量，不能把整个仓库一次塞进模型。正式效果结论只用未暴露 holdout。

## 7. M2：精确修改和可审查的文件结果

**用户流程**：用户要求修改专用仓库中的一项行为 → Agent 定位相关文件 → 展示拟修改内容 → 按权限应用多文件变更 → 用户查看 diff 与测试前状态。

| 任务卡 | 实现内容 | 完成判据 |
| --- | --- | --- |
| E-01 编辑契约 | `edit_file`/`apply_patch` 以原文件哈希、目标路径、补丁为输入；保留编码、行尾、权限位；临时文件写入后原子替换 | 不覆盖同时发生的人手修改；补丁上下文不匹配时明确报冲突 |
| E-02 审核预览 | 页面显示逐文件 diff、文件数、增删统计和风险提示；项目写入与下载产物分别标识 | 用户能在执行前看清实际路径和差异，审批与已应用状态不会混淆 |
| E-03 多文件事务边界 | 定义“全成功”或“部分完成”的可恢复状态；保留基线和写入结果，提供受控回退路径 | 第二个文件失败时不报告为全成功；重试不重复应用第一项 |
| E-04 文件操作 | 新建、重命名、删除分开授权；批量操作先预览并逐项列出目标，禁止隐式递归清空 | 项目外文件不可改；高风险操作在批准前没有副作用 |
| E-05 账本衔接 | 编辑 ToolEffect、Trace、Run checkpoint 与最终 diff 对齐，失败或中断保留 UNKNOWN 判定入口 | Worker 强杀后可以区分未执行、已执行和未知，未知不自动重放 |

**验收**：完成至少一例跨两个文件的真实修改；人工并发改同一文件必须触发冲突；审批取消、执行中断、重复投递和 symlink 逃逸分别留证。项目原有内容不能被整个文件覆盖式工具无意抹掉。

## 8. M3：命令执行和失败后继续修正

**用户流程**：Agent 修改代码 → 在该项目运行约定的测试/检查 → 读取退出码和失败摘要 → 只修改与失败相关的代码 → 复测并报告未运行的检查。

| 任务卡 | 实现内容 | 完成判据 |
| --- | --- | --- |
| X-01 可写执行视图 | 让命令在与 M1/M2 一致的授权项目视图中运行；优先受控容器挂载或隔离工作副本，先验证 Windows/Docker 路径、文件锁和换行 | 工具读到的文件与测试运行的文件一致；容器内变更回写规则明确 |
| X-02 命令契约 | 优先结构化 argv、固定/可核验 cwd、环境变量白名单、时长和资源上限、输出上限；Shell 语法另设受限档位 | 实际命令、目录和限制在执行前可见；路径越界或禁用命令拒绝 |
| X-03 授权档位 | 测试/静态检查、构建、依赖安装、联网命令和宿主执行分别授权；默认离线，不因一次测试批准而获得安装或推送权 | 网络及外部副作用需要单独授权并有审计记录 |
| X-04 反馈给循环 | 将 stdout、stderr、退出码、超时、截断及产物位置结构化返回；Agent 可以据失败继续编辑，预算用尽时停下 | 故意失败的测试可触发有依据的修正，最终回答不谎称成功 |
| X-05 恢复语义 | 命令启动前后写账本和执行标识；中断后可安全重跑只读检查，有副作用的命令按结果判定或保留 UNKNOWN | 强杀/超时/重试不会静默二次安装、提交或发布 |

**验收**：先完成 I-01/I-02 的最小事件视图，再在 dev fixture 中引入会失败的测试，让真实模型完成“运行→定位→修改→复测”并保存完整轨迹。证据须有失败退出码、被读取的失败输出、随后的相关 diff 和复测结果，避免把偶然改对算作反馈闭环；正式通过率只取独立 holdout。故意注入“把密钥上传”的测试输出，模型和执行层均不得因此提升网络权限。命令失败、未安装依赖或环境不可用要分别报告。

## 9. M4：用户与 Agent 在同一条可恢复时间线上

**目标体验**：开始后即可看到当前步骤和真实工具结果；用户可以中途补充约束、排队下一项、取消，刷新页面后仍接在同一 Task/Run 上。这里的“同一条时间线”是用户体验契约，不要求模型与网页运行在同一进程。

| 任务卡 | 实现内容 | 完成判据 |
| --- | --- | --- |
| I-01 事件投影 | 页面接已有服务端 SSE，带事件 ID、重连游标、去重和终态补查；定义事件顺序与缺口处理 | 刷新/断线后不丢阶段，也不把同一工具显示两次 |
| I-02 进度呈现 | 展示计划/当前动作、工具输入摘要、等待审批、失败原因、模型文本增量（可选）及最终证据 | 用户在长任务中能知道它正在做什么，终态与后台事实一致 |
| I-03 中途补充 | 区分“影响本 Task 的补充指令”和“下一 Task”；指令持久化，在下一个安全模型/工具边界注入，并显示接受时间 | 补充不会篡改已经执行或审批中的动作；Agent 后续步骤反映新约束 |
| I-04 控制动作 | 取消、暂停/恢复（如实现）、拒绝审批与 UNKNOWN 人工结清用一致状态机；不虚构已撤销的副作用 | 取消后停止新工具，已发生动作和待结清动作仍可查看 |
| I-05 会话关联 | Message、Task、Run、Artifact 关系稳定；队列中的下一项按最新会话上下文启动，防止并发消息串话 | 快速连续输入两条任务、刷新页面和 Worker 切换后归属正确 |

**验收**：真实任务运行到第一次工具结果后，用户补充“只改指定模块”，Agent 后续编辑必须遵守；同时发送下一任务应排队而非混入当前 Task。断线重连、重复事件、审批等待、取消后晚到结果、Worker 强杀各跑一例。

**交付顺序**：I-01/I-02 的首版在 M3 正式验收前完成，让失败与修正过程可见；M4 再补齐复杂重连、运行中输入、取消和会话关联。首版视图不能替代 M4 的完整验收。

## 10. M5：公开资料、个人文件与产物闭环

此里程碑吸收原计划 B/C 中仍有效的内容，但验收放在真实用户任务，不再以“搜索 API 已接入”或“上传接口存在”视为完成。公开搜索可先走无密钥 `ddgs`，Brave 为可选后端；没有 Brave 凭据不是阻塞项，公共后端波动必须如实记载。

**依赖退化**：`ddgs` 限流、空结果或不可用时做有上限的退避重试；仍失败则可在用户已配置且获授权时切换另一真实提供方，否则明确标为“未完成搜索”，不拿模型常识或旧摘要冒充已核对来源。仅有摘要时只能标注摘要级证据，不能产出“已阅读全文”的引用。首版只支持文本型 PDF；解析器缺失或文件损坏时保留原文件与错误，扫描/图片型 PDF 明确报不支持并提示后续 OCR 方案，依赖它的任务判为不完整，不静默猜测内容。外部依赖故障单独统计，不从正式样本中删去。

| 任务卡 | 实现内容 | 完成判据 |
| --- | --- | --- |
| F-01 搜索与引用 | 搜索结果、网页正文、来源 URL、抓取时间与引用片段关联；去重、空结果、失效、403/超时分别处理 | 两个以上独立来源支持报告中的关键事实；来源不支持的断言被指出 |
| F-02 文件入口 | 授权本机目录或显式上传，列出文件、类型、大小与哈希；冻结 Task 输入集，不后台扫描 Downloads | 用户清楚 Agent 读到了哪些文件；任务中替换原文件不会悄悄换输入 |
| F-03 格式处理 | UTF-8 以外编码和文本型 PDF 各用明确解析器；扫描/图片型 PDF 首版不支持并提示需单独配置 OCR；不把二进制当文本送入模型 | 三份受支持格式的混合资料能抽取可核对文本；不支持格式有可执行说明 |
| F-04 产物出口 | 产物预览、下载、哈希和来源 Task；可选择写回授权目录，外部写入仍走审批 | 用户能拿到报告/整理结果并核对内容；链接权限和路径不越界 |
| F-05 目录整理 | 移动/重命名先生成计划及冲突清单，支持 dry-run 和已执行清单；删除单独审批 | 对样例目录分类后可核对每个文件去向，失败可恢复 |

**验收**：一例公开资料调研和一例本机授权目录整理均在网页完成“输入→处理→核对→取回”。网页来源注入、私网 URL、重复文件名、损坏 PDF、输入变化及下载越权作为失败样本。真实模型/搜索评测此前按用户要求暂缓；重新启动这部分评测前先冻结样本，不用 Mock 结果冒充效果。

## 11. M6：Skill 自进化从机制变成有证据的收益

现有 DSL、来源冻结、候选评测、人工发布和回滚继续使用。提炼素材必须来自已核对的 dev/日常真实任务：成功条件、有效步骤、常见失败及适用边界明确；**M6/M7 holdout 的任务、运行轨迹和评审结果一律不得作为 Skill 提炼来源**。私有正文、密钥、未授权项目路径不能进入可发布 Skill。提炼来源是实际轨迹及其 `source_run_id`，评分锚点是事先冻结的判据，两套记录分别保存且都不包含私有正文。

| 任务卡 | 实现内容 | 完成判据 |
| --- | --- | --- |
| S-01 轨迹挑选 | 只从 M1～M5 的 dev/日常 Trace 提取经人确认的有效案例，标注任务类型、工具版本、成功证据及失败案例；按 M0b 台账复查来源集合 | 每条候选可追溯到原任务，holdout 来源被拒绝，敏感数据有脱敏/排除记录 |
| S-02 候选生成 | 把可复用步骤写成可读 Skill，明确触发、前提、停止条件、审批点和反例；沿用现有人工提议流程 | Skill 不隐含项目路径或凭据，也不把一次偶然成功泛化为规则 |
| S-03 冻结对照 | 使用 M0 未暴露、与开发 fixture 不同家族的 holdout；同模型、同工具、同预算、随机化两臂顺序，记录任务成功、时间/token、错误与越权 | 留出集不参与改写；按下述样本量规则预注册，样本不足只给探索性结论 |
| S-04 人工发布与回滚 | 审查来源、diff、评测与安全影响，发布版本并监测；效果退化可禁用/回滚 | 用户能解释“它学到了什么、帮了什么、失败在哪里” |

**样本量与预算先后**：先为要声称获益的一个主要任务家族选定“任务成功率绝对提升至少 10 个百分点”这一最小有意义效应（若业务理由不同，须在看 holdout 前另行预注册）；从 dev 试跑估计配对两臂的失配率，用配对二分类检验的精确计算或模拟求双侧显著性水平 0.05、至少 80% 检出力所需的配对数，并留出失败/不可运行余量。配对设计的检出力主要来自两臂结果不一致的样本；失配率低时，计算值可能达到 100～200 对或更高。**每个要单独声称有效的任务家族不得少于 30 对，实际计划数取 30 与计算值中的较大者**；30 对只是防止极小样本，不能保证检出 10 个百分点的提升。M6 先据此定样本制作工时、计划候选轮数和实验预算，再决定是否具备正式评测条件。若计算所需配对数超过可承受预算，可以重新选择确有业务理由的主要任务家族，或转为样本量受限的探索性试验；不能仅为适应预算把“最小有意义效应”从 10 改为 20 个百分点。探索性报告必须给出实际样本量、假设失配率、功效曲线，并明确写出“本样本量在 80% 检出力下只能检出至少 X 个百分点的绝对提升”，不得把未显著解释成 Skill 无效，也不得事后减少配对数仍声称证实收益。其他任务家族若未达到各自样本量，只报告描述性结果。

**退出门槛**：至少一个 Skill 在独立留出任务上达到预先冻结的正向效果门槛，且无安全退化；同时报告配对差异及不确定性，不能把小样本的偶然优势写成统计证明。第一轮若未达门槛，按第 13 节的投入闸门复盘，可以停在“机制完整、收益未证实”并交付通用 Agent 基础版，不为追求正向结论反复消耗 holdout。历史上两臂同为 6/6、11/12 的样本不足以预测新项目任务的实际效应；新任务应有足够改进空间，避免两臂都接近满分。查看结果后改任务或 Skill 必须开启新候选与新 holdout，不能继续拿原样本做正式结论。人工发布始终保留。

## 12. M7：发布级回归、安装和维护

**任务集**：执行 M0 预注册的至少 24 条正常任务和 8 条故障/越权任务，覆盖项目理解、跨文件编辑、失败修正、交互介入、文件处理、公开调研和 Skill；各批增补在首次正式运行前入库。dev 集、M6 效果 holdout 与 M7 发布 holdout 分开记账，不把同一 fixture 的反复调试计入通过率。精确阈值、样本权重和人评规则在正式跑前写入版本库，不能事后调阈值迁就结果。建议最低门槛为正常任务整体成功率 ≥80%、核心项目任务 ≥75%、边界越权成功数为 0；发布 Skill 另过 M6 门槛。

按四层检查：契约与单元测试验证路径、哈希、状态机；集成测试验证 PostgreSQL/Redis/容器和强杀恢复；真实模型任务验证交互与工作效果；人工审查差异、报告来源和用户可理解的失败提示。每项失败保持原样进入报告，修复后追加复测记录，不覆盖首次结果。

交付时在干净 Windows + Docker 环境做从零启动和升级演练：环境检查、首次配置、密钥本地存储、项目挂载、数据库迁移、备份/恢复、日志与数据清理、网络/模型不可用降级。缩短 Compose 开发迭代中重复安装依赖的时间；正式运行仍锁定版本和镜像摘要。完成一份用户手册、一份安全边界说明、一份运营故障指南和可复现的评测报告。

**发布判定**：若代码检查通过但真实任务、恢复或边界检查缺证据，标记为候选版；若 Skill 无净收益，可交付“通用 Agent 基础版”，但不得称目标中的 Skill 自进化已完成。任何未执行的检查明列原因与影响。

## 13. 执行节奏、文档和变更控制

1. **第一段：M0a→M1 开发，同时完成 M0b/M0c**。先用 dev 任务完成“读项目并写模块地图”，发现上下文与权限问题；M0b 的 holdout 台账/评分协议和 M0c 的预算/漂移闸门必须在任何正式效果验收前关闭。此时还不能宣称会改代码。
2. **第二段：M2→I-01/I-02→M3**。先让工具过程在页面可见，再形成“精确编辑→运行测试→看到失败再改”的最短闭环。这是与目标差距最大的主线；每次提交附一例正常和一例失败/越界证据。
3. **第三段：M4 其余任务卡**。把后台执行变为可介入的网页体验；只有实测不能满足要求时才评估独立实时执行通道。
4. **第四段：M5**。补齐研究和日常文件的真实入口/出口，不阻塞项目主线。无付费搜索凭据时先验证无密钥方案并记录其可靠性。
5. **第五段：M6→M7**。用前面产生的真实轨迹证明 Skill 的效果，随后做发布级回归、迁移和新机演练。

每张任务卡结束时同步[当前状态](当前状态.md)、对应源码手册章节、用户操作手册和必要 ADR；新增证据进入[评测索引](evaluations/README.md)。文档状态只用“计划中 / 已实现未实测 / 已实测 / 失败待修复”，并写明日期、提交、环境、样本和证据。旧阶段文档及原 A～F 计划作为历史记录，不回写成现在的结论。计划调整必须说明用户能力、依赖和验收门槛如何改变。

**状态防漂移**：`当前状态.md` 顶部的“代码核对基准”指最后一次逐项核对产品代码的提交，文档提交不自动推进它。M0 增加脚本/CI 检查该提交到当前 HEAD 之间是否存在产品代码、配置、迁移或测试变更；有变更而状态基准未更新时阻止里程碑关闭。每次关闭还需重新核对模式默认值、测试数字、已验证证据和未关闭缺口；脚本只能发现可能漂移，不能代替人工判断。旧 16 项和前端历史测试数字始终保留原日期，不改成“当前”。

**投入与重设计闸门**：每个里程碑在开工前估算工时、付费额度和最多两轮完整验收；同一关键验收连续两轮未通过，或预计剩余预算不足覆盖正式 holdout，就暂停扩大范围，保留失败证据并写一页 ADR：根因属于工具/模型/环境/任务定义哪一类，继续、缩减或改架构各需多少成本，哪些验收必须重新预注册。完成该决策再推进；不能通过不断增加模块、删除失败样本或无限调 prompt 使计划看似有进度。到 M7 若核心项目闭环或边界门槛仍不过，明确停在候选版并列出未达成目标。
