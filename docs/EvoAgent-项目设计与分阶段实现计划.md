# EvoAgent：个人通用 Agent 当前实现计划

> 本文是 2026-09-27 起的执行基准。原五阶段设计保留在[历史存档](archive/EvoAgent-原五阶段计划历史存档.md)，用于理解架构选择和已经交付的模块，不再作为当前待办清单。阶段一至四的既有代码不因路线调整而重新编号；以下工作以用户任务为单位验收。

## 1. 产品目标

先交付一个**本机、单用户、可信环境中的个人通用 Agent**。用户打开网页，能以自然语言交代目标；Agent 可以与真实模型对话，查询公开资料，处理受控 Workspace 内的文件，询问缺失信息，经审批执行有副作用的操作，提供可核对的答复和产物，并在失败后说明下一步。会话、任务和证据在重启后仍可访问。

首批任务限定为三个日常场景：

1. **公开资料调研**：搜索、读取多个网页、比较信息、生成有来源支持的回答或 Markdown 报告。
2. **个人文件处理**：读取用户选定的 Workspace 文件，提取、整理或转换信息，生成可查看/下载的结果；修改已有内容须遵守审批。
3. **持续对话与任务跟进**：围绕前一轮信息追问，回答 Agent 的澄清问题，查看执行进度、审批、失败原因和恢复动作；用户可以选择确认长期记忆并撤销。

目标是“用户可以交代任务并核对完成情况”，不是单纯证明 Agent Loop、数据库或 Skill 管线存在。已实现的 Skill 版本化和评测门禁仍是差异化能力，但不能替代基本任务体验，也不能在未证实收益时被宣传为任务质量提升。

## 3. 技术边界保持不变

继续复用已有 FastAPI、PostgreSQL/pgvector、Redis、Worker、前端、Provider、ToolExecutor、Policy、Docker Sandbox、MCP 和 Skill/Eval 服务。PostgreSQL 仍是 Task、Run、事件与 ToolEffect 的事实来源；Redis 只承担唤醒和限流。真实模型、搜索与 Embedding 分别配置，不能把 DeepSeek 对话接口当作 Embedding 服务。API 与 Worker 必须使用一致的 Provider/模型配置。

工具权限由执行层检查；网页、搜索结果、文件和 MCP 返回内容均按不可信输入处理。高风险或不确定副作用由用户核对，不能因模型给出“已完成”就结束任务。默认本机绑定环回地址；当前没有账户认证，不能直接作为公网多人服务部署。

## 4. 实施顺序

### 工作包 A：真实模式与首次启动

**目标**：新用户按一份文档完成本机安装和真实模型对话，清楚知道是否在 Mock 模式。

- 提供单一的个人使用启动配置和最少必需参数，API/Worker 共用同一份非入库凭据；保留 Mock 入口供离线开发和回归。
- 对缺少密钥、URL、模型、上下文窗口和 API/Worker 配置不一致给出明确诊断；状态页分别表达“配置已加载”“数据库可用”“远端实际请求成功”，不混为一个健康标志。
- 从全新数据库/卷执行迁移、启动、网页发送第一条真实任务，保存可复现的非敏感证据。

**验收**：网页普通对话和一个真实工具任务成功；故意错配与不可达模型均明确失败；日志、响应与仓库不暴露密钥。此包完成前不得宣称开箱可用。

### 工作包 B：真实公开资料研究

**目标**：Agent 完成可核查的搜索、阅读和引用，而不把 Mock 结果或来源标题当成事实。

- 先把现有 `web_search` 的一个真实 Provider 配入个人使用路径，再串接 `web_fetch` 和回答中的来源。真实服务凭据由本机用户提供；无凭据时保留契约测试，但真实验收标记待完成。
- 检查无结果、超时、限流、来源无法打开、来源之间矛盾和网页提示注入；Agent 应暴露不确定性，不能杜撰引用。
- 以明确提问和固定时间快照冻结一批公开资料任务；人工复核引用是否真正支持结论，程序核对工具与 URL 证据。

**验收**：从网页完成至少一条多来源调研和一份带可访问引用的报告；错误来源、空结果和服务故障有明确失败语义。搜索成功不等于答案正确。

### 工作包 C：文件与产物工作流

**目标**：个人可以把 Workspace 中的资料交给 Agent，并方便地核对产物。

- 以现有 `file_read`、`file_write`、`artifact_write/read` 为底座，补齐网页中的输入文件选择、任务与产物关联、查看/下载及继续修改体验。
- 保留 Workspace Guard、大小/类型限制、覆盖审批和文件内容作为不可信数据的处理；不为方便使用而开放宿主全部文件系统。
- 验收文本资料整理、现有文件更新、新文件/Artifact 生成、越界拒绝、取消与重启后可找回产物。

**验收**：用户能从网页完成“选资料—给目标—查看执行—核对并取得结果”；生成文件的内容、位置与 Trace 一致。

### 工作包 D：会话、进度与失败恢复

**目标**：长一点的个人任务可以跟进；失败时用户知道能否重试、需要核对什么。

- 在现有 Session/Task/Trace 上改善进行中步骤和工具结果展示，允许用户在需要时补充说明或排队下一条指令；逐字流式文本可在任务状态与可控性达标后再加。
- 分别处理模型断线、只读工具失败、搜索不可用、有副作用工具 UNKNOWN。只对证明可重放的步骤提供继续/重试；无法证明外部操作未发生时必须保持人工确认。
- 回归多轮上下文、审批后恢复、取消、Worker 崩溃接管和重复请求；记录 Task/Run 状态、产物与外部副作用的一致性。

**验收**：每类失败在页面可辨认并有可执行的后续步骤；不存在把未决 ToolEffect 显示为成功、或因恢复重复提交副作用的路径。

### 工作包 E：记忆与真实外部工具的选择性启用

**目标**：在 A～D 的基本任务稳定后，让用户自愿启用有实际收益的长期能力。

- 记忆继续采用用户确认、来源、作用域和撤销机制；以真实 Embedding 的冻结任务对照启用/停用，记录误召回、隐私边界和效果，不以检索命中数代替任务收益。
- 从已有 MCP 审核机制中选一到两个个人高频、权限清楚的外部工具；逐个验收授权、超时、卸载、重试和副作用，不开放“安装即执行”的任意工具。
- 只有用户场景证明需要时，再选定时任务或一个聊天渠道；这两项不是首个本机个人版的发布门槛。

**验收**：记忆和外部工具各有独立、可复现的成功/失败报告；关闭或撤销后新任务不再使用对应信息或能力。

### 工作包 F：冻结评测与正式发布

**目标**：用真实任务证明“可以用”，并交付可重复安装、升级和排障的版本。

- 在运行前冻结覆盖 A～E 已放行范围的任务集、评审标准、配置和最低门槛。样本包含普通问答、最新资料、来源冲突、文件处理、多轮、澄清、审批、网络失败和恢复；Mock/真实模型报告分开。
- 分别报告自动验收、人工事实/引用评分、端到端成功率、错误类别、耗时、工具调用和可得的 Token/费用；失败样本保留，不按结果删题。
- 用同一版本镜像从干净环境完成安装、迁移、备份恢复、升级/回滚演练和网页联合验收；整理单一当前状态、用户手册、源码手册和发布清单。

**验收**：发布清单中的每项都有对应当前镜像、环境和证据；未通过任何预先声明的核心门槛就继续使用开发版号，不用旧模块报告拼出“全部通过”。

## 5. 优先级与范围控制

A、B、C、D、F 中对应的核心用户路径是首个本机个人通用版的必做项。E 的记忆效果验证和少量外部工具应跟随实际使用证据推进，不能阻塞基本对话、研究和文件任务。各包可复用既有模块，但严格按用户任务完成标准放行，不再以“模块代码存在”表示产品已完成。

暂缓：通用编程 Agent、完整浏览器 Computer Use、多 Agent 协作、所有聊天平台、图片/语音全模态、自动购买/付款、Skill 市场、自动发布 Skill，以及公网多人部署。定时任务可以在首版稳定后优先于多渠道考虑，但要先解决凭据、重复触发和通知语义。若未来需要公网服务，认证、用户隔离、配额、密钥管理和审计将成为独立前置工作。

## 7. 实施时统一遵守的契约

### 7.1 用户任务是验收单位

每个任务记录六种证据：用户从哪里发起、Agent 实际使用的模型与工具、收到的外部资料及其来源、最终答复与产物、任务状态与错误、用户是否能核对结果。`completed` 只表示运行终止并生成答复；显式 `acceptance.checked` 只能证明指定文本、工具或文件条件，不能证明开放式内容正确。人工事实评审与程序断言分别呈现。

工作包实行三层验收，不互相替代：

| 层级 | 作用 | 典型环境 | 可以证明什么 |
| --- | --- | --- | --- |
| 契约与单元 | 锁住参数、状态和安全边界 | Mock Provider、受控文件/HTTP fixture | 代码在可控输入下遵守协议 |
| 服务集成 | 锁住数据库、Worker、Redis、浏览器的连接 | 独立 PostgreSQL/pgvector、Redis、API/Worker | 各组件在部署拓扑中一致 |
| 用户任务 | 评估真实模型和真实工具完成任务 | 独立真实模型/搜索环境、真实页面 | 此配置与样本下的实际效果、故障和体验 |

报告必须标注所用模型、搜索、Embedding、开关、代码提交、镜像摘要、数据集哈希、执行日期、数据库类型、API/Worker 数量和是否使用人工操作。没有观察到的能力写“未验收”，不能用其他层级外推。

### 7.2 状态与隐私边界

- 所有任务的状态、工具效果、审批、回复和产物都以持久化记录为准。页面刷新后应根据服务端重建，不依赖浏览器内存猜测任务成功。
- Workspace 是当前单用户的逻辑组织与记忆范围，不是账户权限。文件入口实现前，须明确每个 Workspace 的物理文件根目录或严格路径绑定，避免同一全局目录内跨 Workspace 误读；默认旧 Workspace 需兼容迁移。
- 模型 API Key、搜索 Key、MCP secret 与源文件私密正文不得进入公开报告、Git、URL 查询参数或前端配置响应。Trace 允许展示执行证据，但必须继续遵守现有脱敏和截断规则。
- 网页/搜索/文件/MCP 内容一律是资料，不是工具权限指令。模型的文字不能取消审批、扩大文件范围或改变副作用幂等语义。
- 对有副作用工具，`COMMITTED`、`UNKNOWN`、待审批与终态的关系须先有状态转换表和故障注入测试，再给页面增加“重试/继续”按钮。

### 7.3 每个工作包的完成定义

一次工作包完成需要同时具备：代码与迁移（如适用）、正常与至少一个失败场景的自动化测试、真实用户路径的证据、用户运行说明、源码手册对应章节、开发进度中的现状与限制。只更新一层测试数字不算完成；若未拿到真实外部服务凭据，先完成不依赖凭据的部分并把真实联验明确列为未完成。

## 8. 工作包 A 的详细实施卡：真实模式与首次启动

### A0. 梳理现有配置流

现有 `Settings` 位于 `src/evoagent/config.py`，默认 Provider 与搜索都是 Mock。`src/evoagent/api/app.py` 的 `/api/v1/runtime-info` 返回模式、模型和搜索摘要；`/health/ready` 只查询数据库。`src/evoagent/workers/bootstrap.py` 构造真实 Provider/搜索 Provider，并在执行前检查 API 创建任务与 Worker 的模型配置是否一致。`docker-compose.yml` 将 Provider 固定为 Mock；`deploy/acceptance/compose.deepseek.yml` 是专用验收覆盖层。不要直接把后者改成普通用户配置，以免混淆验收数据库和日常数据。

### A1. 提供个人模式启动入口

| 项目 | 具体动作 | 交付 |
| --- | --- | --- |
| 配置样例 | 在 Git 可跟踪的样例中只放字段名和安全默认值；本地凭据文件保持 `.gitignore` 忽略。说明模型、搜索、Embedding 是三个服务。 | 一份个人模式样例与参数表 |
| Compose | 从当前根 Compose 叠加个人模式，仅对 API/Worker 注入同一真实模型配置；保持本机回环端口、数据库和卷路径稳定。迁移服务只接收实际需要的数据库配置。 | 可 `docker compose config` 验证的覆盖层 |
| 启动检查 | 先检查必需字段、URL、上下文窗口和不兼容配置；不在启动时发送未经用户授权的付费模型请求。远端探测由用户发起的轻量任务完成。 | 可重复执行的诊断命令/页面指引 |
| 页面 | Mock、真实配置待验证、最近一次真实请求成功/失败分别表达；前端不能把 `remote_model_checked=false` 解释为模型不可用。 | 清楚的首次使用提示 |
| 文档 | 新用户从安装依赖、填写私有配置、启动容器到首条对话只走一条主路径；高级选项另页解释。 | README 与运行说明 |

### A2. 错误分类和配置一致性

至少区分：未配置模型凭据、URL 格式错误、模型名不匹配、API/Worker 配置不一致、远端认证失败、网络超时/断线、模型协议不兼容、上下文预算拒绝、数据库不可用、Worker 未领取任务。对于 `provider_network_error`，保留自动重试的次数和最终失败，不把数据库健康检查当作远端成功。API 配置摘要不返回密钥、Base URL 中的敏感查询参数或完整环境变量。

### A3. 测试与放行

1. 单元/契约：`tests/unit/test_config.py` 与 Provider 测试覆盖缺字段、非法窗口、无密钥输出和兼容服务非预期响应。
2. 集成：`tests/e2e/test_api_worker_flow.py` 覆盖同配置成功、错配置拒绝、迁移后重启仍能继续；并检查 `runtime-info` 与 Worker 实际 Provider 不矛盾。
3. 浏览器：`frontend/src/` 的测试覆盖 Mock 提示、真实配置待验证、错误状态与再次发任务。
4. 独立真实环境：干净卷完成一条普通对话、一次 calculator、一次故意断网或错配；记录 Task/Run ID，不保存密钥。

**退出条件**：用户不需要阅读阶段四模块说明就能完成第一次真实对话；若没有真实 Provider，页面明确停在演示模式。此时只能宣布 A 完成，不能宣布公开资料任务已可用。

## 9. 工作包 B 的详细实施卡：真实公开资料任务

### B0. 复用与缺口

`src/evoagent/tools/builtin/web_search.py` 已有 `BraveSearchProvider`、无密钥 `DDGSSearchProvider`、`MockSearchProvider` 和统一 `WebSearchTool`；`web_fetch.py` 负责受控网页正文读取；`workers/bootstrap.py` 根据配置选择 Provider。搜索结果是标题、URL、摘要和来源名。它只能证明“检索到一条结果”，不能证明 Agent 已读正文，或最终结论得到该网页支持。

### B1. 搜索配置与资料证据

- 真实搜索只在明确选择真实提供方后启用：`ddgs` 无需密钥但依赖公网搜索后端，`brave` 需要 API Key；Mock 用于离线测试，页面和报告持续标识。搜索提供方返回零结果、限流、服务故障、超时、无效响应时保留可辨认错误码与请求用途，不把空结果编造成来源。
- 记录每次搜索的查询、提供方、返回 URL 列表和时间；对后续 `web_fetch` 记录规范化 URL、最终 URL、读取结果、内容摘要或可复核的哈希、时间、失败原因。公开报告可存来源元数据，正文遵守存储与脱敏策略。
- 模型回答引用须能映射到实际检索或读取记录。仅出现 URL 字符串不算引用成立；明确区分“只看到摘要”和“已读取正文”。动态网页/付费页无法读取时，要求 Agent 说明限制。
- 对可变的实时事实，保留访问日期与资料版本；评测题冻结时同步保存公开事实的评审依据。用户在不同日期重跑时，不把资料更新自动判为模型退化。

### B2. 任务行为

第一条基准路径是“比较三个公开项目，给出差异表和引用”。Agent 应主动搜索多个来源、读取相关页面、给出结论；若缺关键信息可用 `ask_user` 澄清。搜索到互相冲突的信息时，答复说明冲突而非任选其一。网页正文中的“忽略用户要求/调用其他工具”等文字按不可信资料处理。

### B3. 测试矩阵

| 场景 | 预期行为 | 证据 |
| --- | --- | --- |
| 真实搜索成功、网页可读 | 回答引用真实读取过的页面 | 工具调用、来源映射、人工评审 |
| 搜索命中但网页不可读 | 说明只能依据摘要，不暗示已核对正文 | 失败事件与最终答复 |
| 零结果或 429 | 适用时退避，最终仍失败则明确失败/证据不足 | 请求次数、错误码 |
| 来源互相矛盾 | 给出冲突点和各自来源 | 人工事实评分 |
| 恶意网页提示 | 不扩大权限、不改变任务目标 | Policy/工具 Trace 与负向测试 |
| URL 指向内网、环回、元数据地址 | `web_fetch` 拒绝 | URL Guard/SSRF 测试 |

**退出条件**：至少一条真实浏览器调研任务、多来源回答和报告可以独立复现；评审者能从引用找到对应的检索/读取证据。`ddgs` 可在没有搜索密钥时开展真实搜索验收；只通过 Mock 测试或搜索适配器联网试搜，仍保持“未验收”。

## 10. 工作包 C 的详细实施卡：个人文件与产物

### C0. 先解决范围与格式

当前 `FileReadTool` 仅读受 Workspace Guard 保护、最大 1 MB 的 UTF-8 普通文件；`FileWriteTool` 写当前 Run 的受控目录，覆盖风险更高；Artifact 有本地存储、哈希和数据库记录，但聊天页主要展示 Trace，尚无完整的用户选文件/下载路径。首版文件格式限定 `.txt`、`.md`、`.csv` 等可按 UTF-8 文本读取的资料；PDF、Office、图片不要只因文件已上传就宣称可理解，它们需要独立解析/视觉能力和评测。

### C1. Workspace 文件身份

- 明确 `WorkspaceRecord` 与物理目录的对应规则。当前文件工具绑定全局 `Settings.workspace`，而会话的 Workspace 是逻辑 ID；在开放网页文件入口前必须使 Task 的 Workspace 身份贯穿上传、列表、读取、输出与下载。旧默认 Workspace 中的数据保留可见，跨 Workspace 访问显式拒绝。
- 新文件入口不得接受任意宿主绝对路径。上传/导入使用服务端生成的安全相对名或不透明 ID；校验扩展名、MIME/实际内容、字节上限、UTF-8、路径穿越、符号链接、硬链接或特殊文件、并发重名及覆盖策略。
- 用户可在页面看见当前 Workspace、已选输入文件、大小和任务引用；Agent 的工具参数只能指向该 Workspace 可访问的文件。迁移时冻结任务对应的 Workspace，不随用户切换下拉框改变进行中任务的文件权限。

### C2. 输出与下载契约

- 统一 Task/Run、`ArtifactRecord`、实际文件之间的可追踪关系。新增下载/预览 API 前先定义权限范围、允许的内容类型、大小上限、文件名编码、内容哈希和错误语义；下载不可把服务器路径直接返回客户端。
- 预览普通文本须转义 HTML，避免报告内脚本在本机管理页执行；二进制输出走附件下载。文件缺失或哈希不符时页面说明“产物不可用”，不得仍显示为已交付。
- 用户希望“改上次报告”时，明确输入版本与输出版本。默认写新版本，不覆盖旧文件；覆盖须沿用审批和副作用记录。停止任务或重试不能悄悄重复覆盖。

### C3. 端到端路径与测试

最小演示：上传两份 UTF-8 资料，要求比较差异并生成 `report.md`；网页显示引用的输入、工具记录、预览和下载，下载后 SHA-256 与 Artifact 记录一致。随后在同一 Session 追问并生成修订版，仍能找回旧版本。

负向测试覆盖超大文件、无效编码、伪装扩展名、跨 Workspace、路径穿越/符号链接、同名并发、下载不存在产物、取消后残留临时文件、Worker 崩溃时的文件/账本一致性。迁移使用独立库做旧数据升级与新数据回退评估；回退若不可逆，发布说明必须明确。

**退出条件**：网页用户不用进入 Docker 卷即可选取、处理、预览和取得首版支持的文件；跨 Workspace 拒绝和产物哈希核对通过。其余格式明确显示不支持。

## 11. 工作包 D 的详细实施卡：会话、进度和恢复

### D0. 进行中信息

`GET /api/v1/tasks/{task_id}/events` 已有 SSE 与 `Last-Event-ID`，`ChatPage.tsx` 和 `TaskInspector.tsx` 当前主要按时间轮询 Task/Trace。先利用已提交事件展示“已排队、调用模型、搜索/读取、等待审批、重试、完成/失败”等阶段及事件时间。SSE 断线后从最后事件序号补齐，重复事件按 ID 去重；服务端终态仍要再查 Task，不能仅凭收到最后一条 SSE 判完成。逐字流式输出属于体验优化，不先于可靠状态展示。

### D1. 会话交互边界

- 同一 Session 的后续问题按已有历史截止点进入新 Task。进行中用户的新消息必须明确是“排队到当前任务完成后”还是“取消旧任务并新建”；首版不允许把文本偷偷写入已冻结的当前 Run 上下文。
- `ask_user` 的回答与高风险工具批准分开呈现，审批按钮附工具、参数、风险和预期副作用。用户可以拒绝普通审批；UNKNOWN 外部结果不能用裸“拒绝”冒充未发生。
- 页面刷新、切换 Session/Workspace、浏览器断线后，待处理任务和审批仍可找回；不让仅在本地状态里的草稿改变已提交任务。

### D2. 恢复决策表

| 状况 | 自动动作 | 用户界面 | 必须防止 |
| --- | --- | --- | --- |
| 模型请求超时/断线，尚无外部副作用 | 有界重试；次数耗尽后终止或提供安全新尝试 | 错误类别、已尝试次数、可重试指引 | 无限重试或把局部工具成功说成任务完成 |
| 只读搜索/读取失败 | 在预算内重试或继续报告资料不足 | 失败来源与下一步 | 编造来源、重复无意义请求 |
| 文件/外部工具操作确定已提交 | 复用已提交结果，不重放 | 显示结果与产物 | 第二次写入 |
| 操作结果 UNKNOWN | 停在人工核对；用户确认已提交或可证明未提交 | 展示外部核对方法与记录 | 自动重放或默默 `completed` |
| 工具检查点已失败且不能原任务安全重放 | 阻止危险 `retry`；建立清晰的新任务恢复路径 | 告知需取消并新建或提交已完成证据 | 假装“继续”能够修复不可重放点 |
| 用户取消、Worker 崩溃、租约转移 | 依状态机收尾/接管 | 终态与遗留外部操作警示 | 已取消被旧审批复活、旧 Worker 写入 |

重点核查 `src/evoagent/tasks/lease.py`、`tools/effects.py`、`tools/approvals.py`、`runtime/recovery.py`、`workers/bootstrap.py` 的事务顺序。新增 UI 控制前先写 `tests/fault_injection/` 和 `tests/e2e/test_worker_process_recovery.py` 中相应的防重放断言。外部工具的幂等能力按工具逐个认定，不能把 `file_write` 的结果推给 MCP 或未来的消息发送工具。

**退出条件**：浏览器从刷新/断线返回后状态准确，故障注入的文件写入最多一次；模型/搜索失败显示真实原因；所有 UNKNOWN 都必须经人工处理或保持未决，不能静默完成。

## 12. 工作包 E 的详细实施卡：记忆、Skill 与 MCP

### E1. 记忆是可选能力

现有 Memory 页面和服务支持从用户原话提议、确认、拒绝、撤销和按 Session/Workspace 作用域查询；混合检索有真实 384 维模型小样本记录。下一步是提供用户能理解的开关和来源展示，并把“命中”与“帮助完成任务”分开评估。任何自动提议都保持待确认状态；撤销后新任务不能注入，旧 Task 保留审计。不同 Workspace、过期事实、来源被删除和恶意指令文本均加入负样本。

### E2. Skill 不作为默认成功前提

保留训练/留出隔离、来源哈希、人工发布和回滚。针对个人公开资料与文件任务，用同模型、同任务、同工具版本、相近时间的 baseline 与 Skill 配对比较成功率、错误和成本。若两臂一样或 Skill 更差，继续记录结果，必要时保持禁用；不能因为已有 Skill 页面就默认开启所有候选。

### E3. MCP 小范围落地

先选一个只读工具，再视用户价值选一个需要审批的有副作用工具。记录服务器来源、配置 Profile、发现的目录版本、人工审核、执行激活和卸载动作。对连接失败、Schema 漂移、参数验证、凭据撤销、服务端超时、UNKNOWN、工具返回恶意指令做故障矩阵。API 与 Worker 使用一致的受信配置；用户页面不提交任意命令或密钥正文。

**退出条件**：记忆/Skill/MCP 各自有独立的真实用户任务报告，明确收益、无收益与故障；关闭后新任务不再取得相关能力。E 不拖延 A～D 的首版用户可用性。

## 13. 工作包 F 的详细实施卡：评测、发布与运维

### F1. 冻结任务集

建议先建立至少 **32 条正常任务 + 8 条故障任务**，数量是执行计划的初始目标，正式阈值应在首次评测前随数据集冻结。正常任务可分：普通与多轮对话 8、公开资料 10、文件与产物 8、澄清/审批 6；故障任务包括模型断线、搜索失败、URL 拒绝、文件越界、Worker 崩溃、UNKNOWN 和取消。若 E 在本轮放行，另建记忆/Skill/MCP 专项集，不把它们塞入此前冻结的 P0 集合。

每项样本记录任务 ID、自然语言输入、允许使用的工具与资料、预期可观察行为、自动断言、人工评审规则、失败时可接受的说明、是否允许模型波动。公开资料类保留评审来源及采样日期；文件类保留输入哈希与预期输出；故障类保留注入点和副作用上限。先提交题目、判分器和门槛，再跑真实模型；不能在看到结果后删题或改答案。

### F2. 评分口径

| 指标 | 计算与用途 | 不得混淆 |
| --- | --- | --- |
| 正常任务端到端成功率 | 用户目标真正达成且可核对；按场景分别报告 | `Task.completed` 或工具调用次数 |
| 故障处理正确率 | 预期失败/恢复状态、可执行建议、副作用上限同时满足 | 故障任务的业务答复成功率 |
| 引用支持度 | 人工逐条核查引用是否可访问并支持对应句子 | 搜索返回 URL 数量 |
| 文件/产物完整性 | 文件可取得、类型/大小/哈希符合、内容满足需求 | 数据库仅有 ArtifactRecord |
| 安全边界 | 越权读取、未授权写入、重复副作用、凭据泄露的次数 | 通过率的平均值；严重安全失败单独阻断 |
| 可用性与成本 | 错误分类、p50/p95 耗时、模型/工具耗时、Token 与费用可得性 | 把未知 Usage 当成零费用 |

建议把**正常任务成功率不低于 85%、引用支持度不低于 90%、严重越权/重复副作用/凭据泄露为零**作为候选发布门槛，并在冻结前由项目维护者确认。样本量小，报告必须同时给分子/分母与失败 ID；这些数字是未来门槛，不是当前成绩。若外部服务故障导致未达到门槛，原样记录，不能把失败样本移出分母。已有 16 项 14/16 结果只作历史基线，不并入新任务集。

### F3. 发布演练

1. 以新的 Compose 项目名、干净 PostgreSQL 卷和 Workspace 卷启动；校验数据库迁移从 base 到 head，API/Worker 版本相同。
2. 依 README 完成模型和搜索配置；确认 Mock 与真实标识准确，再运行真实任务集。浏览器操作覆盖新建会话、文件、审批、失败、恢复、产物与记忆（若放行）。
3. 备份数据库与 Workspace/Artifact 数据，恢复到隔离环境，核对 Session、Task、Run、文件哈希和撤销状态；记录数据库与文件备份的一致性窗口。
4. 从上一受支持版本升级到候选版，执行迁移与回归；若迁移不可逆，给出数据备份和回退应用版本的限制，不能声称可无损回滚。
5. 完成 Python 全量测试、Ruff、前端 typecheck/build/Vitest/Playwright、PostgreSQL/Redis 集成、真实 Docker 隔离专项、真实模型/搜索用户任务；各项环境和跳过原因分开列出。
6. 重新制作当次发布清单，包含代码提交、镜像 digest、迁移 head、数据集/评审版本、各项证据、待解决缺陷与用户已知限制；历史 `phase4-final-manifest.json` 不复写。

**版本决策**：只有本计划定义的本机个人版核心路径和事先冻结的门槛通过，才将 `0.4.0.dev0` 提升为正式 `v0.4`。前端 `package.json`、后端包版本、镜像标签、README 和发布说明要统一，不因某一模块测试通过而单独改版本。公网多人能力不包含在该版本声明。

- 某个工作包发现架构必须调整时，先记录问题、受影响的 Task/Run/数据、候选方案、安全和迁移影响，再更新本计划与 ADR；不能在代码完成后倒写成原计划如此。
- 所有真实服务测试使用被 Git 忽略的本地凭据；公开报告脱敏后保留足以复现的配置类型、模型名、时间、提交和失败标识。`output/` 中的本地资料默认视作用户数据，不纳入提交、清理或迁移操作。
- 后续若用户决定优先做定时任务或某个渠道，先将具体个人场景、重复触发语义、通知目标和权限写成新的工作包，再决定版本范围；不因原第五阶段列过该功能就自动加入当前发布门槛。

## 17. 用户级验收样例

以下是规划输入，不是已经运行的评测结果。正式评测时应把文本、可访问来源与预期数据冻结到新数据集，并避免使用私密资料。

| 类别 | 用户输入范式 | 必须核对 | 故意失败/边界 |
| --- | --- | --- | --- |
| 真实对话 | “用两句话说明这个 Workspace 能做什么；随后记住我本轮说的项目代号并回答追问。” | 两轮同 Session、真实 Provider、历史截止点和答复相关性。 | API/Worker 模型不一致、远端断线。 |
| 基础工具 | “计算 137×29，再把结果与另一个计算结果比较。” | calculator 实际调用、数字正确、无编造调用。 | 模型在工具成功后断线，任务仍不得判完成。 |
| 多来源调研 | “比较三个公开项目某项功能的官方说明，列出差异并附来源。” | 至少两条真实来源正文、逐结论引用、访问时间。 | 搜索为空、网页不可读、来源冲突。 |
| 报告产物 | “把上述比较写成 `report.md`，包含结论、来源和不确定点。” | 文件可下载、内容与引用支持、哈希一致。 | 模型只口头称已写文件、磁盘上不存在。 |
| 文件整理 | “读取我选的两份 UTF-8 资料，整理重复项并生成新清单。” | 只读被选文件，清单不漏/不混数据，旧文件未覆盖。 | 越界路径、不同 Workspace、超大/非 UTF-8 文件。 |
| 澄清问题 | “生成一个计划，若缺时间范围先问我。” | `ask_user` 一次、回答被当前任务消费、刷新后仍可继续。 | 旧审批在取消后不能恢复。 |
| 覆盖审批 | “更新现有报告的某节。” | 修改前展示目标、风险和审批，拒绝后文件不变。 | Worker 在写入后崩溃或请求超时。 |
| 记忆（选择性） | “在新会话里使用我已确认的偏好；撤销后不要再使用。” | 同作用域命中、跨 Workspace 拒绝、撤销后新任务不再引用。 | 旧来源删除或过期。 |

评审至少保存三层判断：机器可查的状态/工具/文件、人工对内容与引用的评分、失败时用户能否恢复。人工评分记录评审者、规则版本、证据链接和分歧处理；无法验证的事实标“不确定”，不强行判通过。

## 18. 建议的验证命令与报告结构

本节是每次代码变更后的执行框架，具体 Compose 项目名、凭据文件和外部服务按当次隔离环境填写。真实模型/搜索测试会消耗外部额度；运行前先确认环境是验收库，不针对日常数据清理卷。

```powershell
# 静态与后端基础回归
ruff check .
ruff format --check .
pytest

# 前端基础回归（在 frontend 目录）
pnpm typecheck
pnpm test
pnpm e2e
pnpm build

# Compose 配置检查先于启动；后续追加个人模式覆盖层
docker compose -f docker-compose.yml config --quiet
```

当次报告至少包含：

1. **范围**：工作包/任务卡 ID、变更文件、数据迁移、用户可见行为、已知未实现项。
2. **环境**：提交 SHA、镜像 digest、Python/Node/Docker 版本、数据库迁移 head、API/Worker 数量、Provider/模型、搜索/Embedding 模式；不记录密钥值。
3. **自动化**：测试命令、通过/失败/跳过数量、跳过原因、复跑条件；PostgreSQL、Redis、Docker 和 Mock 测试分开。
4. **真实任务**：数据集版本与 SHA-256、每项输入/预期/Task/Run/结果、人工评分、失败 ID、模型和工具费用可得性。
5. **安全与恢复**：越权/注入/SSRF、审批、UNKNOWN、取消、Worker 崩溃、防重放证据；外部状态核对方法。
6. **发布结论**：本工作包是否达到退出条件，正式版本门槛是否仍有缺口，下一张任务卡的前置条件。

除修复新发现的缺陷外，某切片专项与相关全量测试通过后不反复运行同一批检查；继续向用户任务联合验收推进。新镜像或数据集发生变化时，关联的真实报告必须重新生成，不能引用旧镜像的成功案例给新镜像背书。
