> - 本页更新日期：2026-09-28。第 1～3 节区分代码、自动化与真实任务证据；第 3.1～3.2 节是按日期累积的缺陷和基准推进记录，历史数字不代表最新运行结果。

> - Windows 可信本机模式已实现首个可用切片：本机 API/Worker、Windows 目录登记、会话绑定或单任务授权、逐次审批的本机项目命令。启动见[操作说明](可信本机模式.md)，证据见[开发验证](evaluations/Windows可信本机模式开发验证-2026-09-28.md)。该模式不提供 Windows OS 级文件/网络沙箱或桌面控制，不能替代 M6/M7 正式验收。

> - 默认 `docker-compose.yml` 仍是 Mock Provider、Mock 搜索、记忆关闭。Docker 真实模式与 Windows 本机模式分别按各自操作手册启动；正式评测预算尚未冻结，**正式评测**会被预算闸门拒绝。历史 dev 试跑的账本数字分别见[原试跑预算](evaluations/DeepSeek开发试跑预算-2026-09-28.md)与[补齐试跑](evaluations/个人Agent补齐试跑-2026-09-28.md)，不能相加当作同一部署的实时账户余额。

**当前判断**：已具备项目读改测、网页交互、可恢复任务与受控 Skill 生命周期的实现；Windows 本机模式已完成一次真实模型命令审批链路。开发样本不能推出跨项目可靠性，Skill 的净收益仍未证实，M7 真实发布集与人工审查尚未完成，因此 `v0.4` 不放行。

### 3.2 状态漂移闸门：基准已重新核对并推进（2026-09-27）

随后按"推进基准前必须先重新核对"的要求完成了一次复核，依据是：

**脚本语义（2026-09-27 修正）**：旧版 `--update` 以"检测到产品改动"为由拒绝推进基准，而"有改动"
恰恰是它存在的理由，于是基准永远推不动、闸门变成永久红灯。现在改为：`--update` 本身就是
"这些改动已核对"的声明，唯一守住的边界是**工作树必须干净**（否则记下的提交并不包含被核对的内容），
推进时打印完整的 `旧..新` 范围与产品文件数作为留痕。不带 `--update` 的 `check` 行为不变：
有漂移即非零退出、阻断里程碑关闭。

需要注意：脚本只能发现"哪些文件变了"，**不能**判断新改动是否已经过验收。推进的边界是
"代码与文档、测试一致且未验证项已如实登记"，**不等于**这些能力已经通过真实模型验收
——那次核对时真实模型端到端仍未执行，彼时结论上限只是"机制完整、受控测试通过"；后续 dev 试跑见第 2 节。
