### 3.1 已知缺陷（2026-09-27 校对源码与 CI 时发现）

### 3.2 状态漂移闸门：基准已重新核对并推进（2026-09-27）

M0c 的漂移检查脚本 `scripts/check_state_drift.py` 的作用是：**基准提交之后只要产品代码变过就报警，
阻断里程碑关闭**。这个闸门在 M1 落地时第一次拦到真实漂移（基准 `78674c3` 之后出现产品代码改动），
当时按规则保持基准不动并把结论写在本节。

随后按"推进基准前必须先重新核对"的要求完成了一次复核，依据是：

| 复核项 | 结果 |
| --- | --- |
| 第 2 节的真实环境证据是否仍然成立 | 成立；M1 只有受控（Mock）证据，其限制已如实写在[M1 验收](evaluations/M1项目只读验收-2026-09-27.md) |
| 产品代码改动是否都有对应文档与测试 | 有：M1～M4、M5 的 F-02/F-04 各自有验收或进度文档与专项测试 |
| 全量自动化结果 | 后端 **693 passed、34 skipped**；`ruff check`/`format` 通过；文档断链 0 条；另有真实 PostgreSQL+Redis 集成 **195 passed、12 skipped**（详见 [M7 报告](evaluations/M7发布准备与分层检查-2026-09-27.md)） |
| 尚未验证的项是否已登记 | 已登记在第 3 节与各里程碑验收报告的"仍未验证"小节 |

因此把基准提交从 `78674c3` 推进到复核时的 HEAD（改动规模：产品 100+ 个文件，其中 M0c 部分是
预算闸门与残留记录补全）。推进后 `check_state_drift.py` 通过；**此后任何产品代码改动都会重新报漂移**，
这正是它应有的行为。

**脚本语义（2026-09-27 修正）**：旧版 `--update` 以"检测到产品改动"为由拒绝推进基准，而"有改动"
恰恰是它存在的理由，于是基准永远推不动、闸门变成永久红灯。现在改为：`--update` 本身就是
"这些改动已核对"的声明，唯一守住的边界是**工作树必须干净**（否则记下的提交并不包含被核对的内容），
推进时打印完整的 `旧..新` 范围与产品文件数作为留痕。不带 `--update` 的 `check` 行为不变：
有漂移即非零退出、阻断里程碑关闭。

需要注意：脚本只能发现"哪些文件变了"，**不能**判断新改动是否已经过验收。推进的边界是
"代码与文档、测试一致且未验证项已如实登记"，**不等于**这些能力已经通过真实模型验收
——真实模型端到端仍未执行，结论上限仍是"机制完整、受控测试通过"。

**2026-09-27 第二次推进（M5 F-03/F-05、M6 S-01～S-04、M7 发布集与演练）**：复核依据是
[M5 交付进度](evaluations/M5交付进度-2026-09-27.md)、[M6 冻结对照实验路径](evaluations/M6冻结对照实验路径-2026-09-27.md)、
[M6 人工发布与回滚审查](evaluations/M6人工发布与回滚审查-2026-09-27.md) 与
[M7 发布准备与分层检查](evaluations/M7发布准备与分层检查-2026-09-27.md)：产品改动都有对应文档与测试，
未验证项（真实模型、人工审查、干净机器、付费额度）已逐条登记，且本轮演练发现并修复了
一个真实模型路径的阻断缺陷。基准随本次提交一起推进。
