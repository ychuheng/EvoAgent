# 第三部分：工具、项目与安全边界

前两册解释了任务如何创建、运行和恢复。本册回到最实在的问题：Agent 能读什么、改什么、跑什么，用户如何拿到结果？请始终区分**模型收到的工具定义**、**工具自身的路径检查**、**执行环境的操作系统权限**。三个层次共同决定能力边界，任何一层的“已授权”都不能代替另两层。

## 1. 工具清单是每个 Run 装配出来的

[ConfiguredTaskHandler._project_tools()](../../src/evoagent/workers/bootstrap.py) 根据已冻结的 Project 装配工具。[ToolRegistry](../../src/evoagent/tools/registry.py) 把本 Run 的工具定义交给模型；若 Provider 返回未注册的工具名，执行层仍须拒绝。无项目时仍有计算、搜索、网页读取、向用户提问及 Run 产物等非项目工具，但没有项目目录、编辑和命令工具。`read` 项目提供 `list_dir`、`find_files`、`search_text`、分段 `file_read` 和文本抽取；`read_write` 再增加编辑、移动/删除、目录整理和白名单命令。

工具描述是给模型看的使用提示；真正的边界在 [参数契约](../../src/evoagent/core/models.py)、[工具执行层](../../src/evoagent/tools/executor.py)、[项目授权复查](../../src/evoagent/projects/boundaries.py) 与具体工具函数中。模型可以被仓库文件、网页或测试输出诱导，但这些文字不能修改 ToolRegistry、项目授权或审批记录。

## 2. 路径不是一串字符串

[项目登记](../../src/evoagent/projects/service.py) 要求目录存在且可用；[路径契约](../../src/evoagent/projects/schema.py) 同时处理词法路径、规范化的物理路径和符号链接/junction。只检查 `..` 不够：一个看似位于根内的路径可能经链接跳出；只检查物理路径也不够：某些操作会在检查之后创建新目标。内置项目文件工具在各自的读取/写入点继续校验，工具结果返回相对根的可说明路径。

目录发现与内容搜索不是一次“读取整个仓库”。[list_dir](../../src/evoagent/tools/builtin/list_dir.py) 展示可见目录项；[find_files](../../src/evoagent/tools/builtin/find_files.py) 按路径模式定位文件；[search_text](../../src/evoagent/tools/builtin/search_text.py) 给出命中位置；[项目 file_read](../../src/evoagent/tools/builtin/project_file_read.py) 才按范围取正文。忽略规则、条数和字节上限使模型能逐步缩小目标。若要证明它真的理解项目，最终模块地图应能回到这些已读取文件，而不能只看模型自述“我检查过”。

输入文件还可以在创建 Task 时作为 [冻结输入](../../src/evoagent/projects/inputs.py) 记录哈希。之后每次工具动作前复查；文件被替换就产生 `input_changed`，让用户知道这次任务的输入条件已经变化。它与通用的目录读取不同：冻结输入表达的是“请针对这一批字节工作”。

## 3. 精确编辑的保证与边界

[edit_file / apply_patch](../../src/evoagent/tools/builtin/project_edit.py) 把路径、旧内容或行范围、替换文本和可选 `expected_sha256` 转成 [编辑请求](../../src/evoagent/projects/editing.py)。实现先读取文件快照、识别文本编码和行尾，验证前置条件，生成 diff；`dry_run` 可在不写盘时预览。写入时每个文件使用同目录临时文件加 `os.replace`，避免读者看到半个文件；原有权限位尽量保留。多文件批次先准备所有变更，写入中遇错会尝试按原快照回滚已写文件。

必须准确理解其边界：**单文件替换是原子可见的，多文件批次不是数据库式原子事务**。准备之后到逐文件写入之间仍有并发窗口；`expected_sha256` 会在快照阶段发现已变化的内容，但不能把整批操作变成跨进程锁定的工作树事务。回滚也可能因外部修改或磁盘故障失败。审查时同时看原哈希、diff、实际结果和 Trace；不能仅凭“工具返回成功”推断 Git 工作树只发生了预期改动。待审批的编辑有服务端重算的 diff；自动放行的 R1 编辑没有执行前人工审查。这些限制在[当前状态](../当前状态.md)中仍列明。

`delete_file` 不做隐式递归清空；`move_file` 要求目标不存在。[organize_files](../../src/evoagent/tools/builtin/project_organize.py) 使用 [整理计划](../../src/evoagent/projects/organize.py) 先生成去向和冲突清单，再应用。把“建议怎样整理”和“已经移动了什么”分开，是让用户能审查目录操作的关键。

## 4. 同一个 `run_command`，两种操作系统语义

[ProjectCommandTool](../../src/evoagent/tools/builtin/project_command.py) 接受结构化 `argv`、项目内 `cwd` 与 `allow_network`。 [commands.py](../../src/evoagent/projects/commands.py) 校验参数数目、可执行文件白名单、工作目录、部分看起来像路径的参数，并把 stdout、stderr、退出码、时长、超时及截断状态作为结果返回。退出码非零是模型应观察的测试证据，不被抹成通用工具异常。相同 argv 在修复前后可以运行两次：命令工具的两次调用不按参数合并 ToolEffect。

| 层面 | Docker 个人模式 | Windows 可信本机模式 |
| --- | --- | --- |
| 进程位置 | Linux Worker 容器 | 启动 `host_mode.py` 的 Windows 用户会话 |
| 项目目录 | 宿主父目录挂到 `/app/projects`，页面登记容器路径 | 页面登记 Windows 绝对路径 |
| 命令授权 | 白名单；可识别离线检查可按 R1 执行，构建/安装/通用解释器与联网命令逐次审批 | 白名单且每次强制 R2 审批；必须显式 `allow_network=true` |
| 文件/网络隔离 | 子进程需成功建立 Landlock 文件视图；离线命令另用 seccomp 阻断网络；有单进程资源、超时、输出和进程树数量限制 | 工作目录受项目根约束；获批程序有当前用户权限，可访问根外文件和网络；没有等价 OS 沙箱或进程树资源隔离 |

Docker 子进程建立隔离失败时命令直接失败，不会无声退回不隔离执行。[command_runner.py](../../src/evoagent/projects/command_runner.py) 安装 Linux 侧约束；[commands.py](../../src/evoagent/projects/commands.py) 管父进程侧超时和进程树计数。Windows 分支逐次审批，但审批是一种**用户信任决定**，不是给获批程序加 OS 文件沙箱。模型可提议 PowerShell；用户必须看完整脚本正文。校验器能拒绝直接的 `git push`、`npm publish` 等 argv，**不能识别获批解释器脚本内部的等价操作**；Windows 获批进程又没有网络隔离，因此不能把这项校验写成普遍的“禁止外部发布”保证。

独立 [shell 工具](../../src/evoagent/tools/builtin/shell.py) 是另一条默认关闭的路径，走 [sandbox-controller](../../src/evoagent/sandbox/controller.py) 的固定规格容器；它不是项目 `run_command` 的别名。把两条路径混起来，会错误推断某个任务实际操作的文件树和网络边界。

## 5. 普通文件、项目文件和产物为什么分开

项目 `edit_file` 改的是用户授权的工作树；Run `file_write` 写的是本次运行的输出空间，并通过 [ArtifactService](../../src/evoagent/trace/artifacts.py) 登记为可下载产物。`file_write` 可以按相对路径创建 `reports/summary.md`，同名覆盖会更新登记记录；`artifact_write` 创建不可覆盖的产物。它们的分工在 [file_write](../../src/evoagent/tools/builtin/file_write.py) 与 [artifact_write](../../src/evoagent/tools/builtin/artifact_write.py) 中。项目文件的修改**不会自动变成下载列表中的产物**；需要交付报告时，模型应明确使用产物工具。

[产物 API](../../src/evoagent/api/routes/artifacts.py) 只接受数据库中已登记的 ID，不接受任意文件路径；预览有上限，下载前重新读取并核对登记 SHA-256，不一致返回 409。登记记录与不可变内容快照配合，避免覆盖新内容后旧记录指向错误字节。页面上的哈希和响应头 `X-Content-SHA256` 让用户能核对拿到的文件。这个出口不是任意读取项目目录的 API。

[extract_text](../../src/evoagent/tools/builtin/project_extract.py) 处理明确编码的文本和**文本型** PDF；图片扫描件没有 OCR。[organize_files](../../src/evoagent/tools/builtin/project_organize.py) 处理目录整理。能解析某种格式，仍不意味着真实模型已在各种私人资料上稳定完成任务；证据等级见[当前状态](../当前状态.md)。

## 6. 公开资料与外部协议

[web_search](../../src/evoagent/tools/builtin/web_search.py) 可选 Mock、无密钥 `ddgs` 或 Brave；[web_fetch](../../src/evoagent/tools/builtin/web_fetch.py) 只读公开 HTTP(S) 文本，重定向每一跳经过 [URLGuard](../../src/evoagent/tools/guards.py) 检查。搜索摘要与真正读取过的正文分开记 [来源证据](../../src/evoagent/trace/sources.py)。引用某个 URL 只能证明模型写出了这个 URL；即使系统确认读过该网页，仍需人工判断来源是否支持结论。[逐结论引用检查](../../src/evoagent/evals/citations.py) 帮助找机械不匹配，不替代事实审查。

[MCP](../../src/evoagent/mcp/service.py) 先发现目录并供用户审核，再显式激活执行。Run 冻结工具契约和执行绑定；[MCP 适配器](../../src/evoagent/mcp/adapter.py) 接入统一工具执行层。发现服务器、批准目录、让某个 Run 看到工具、实际获批调用是四个不同动作。外部服务的响应仍是不可信资料，不能借 MCP 取消本地审批或扩大项目授权。

## 7. 从“模型想做”到“系统允许做”的五道门

当模型读到“请把失败测试修好”，接下来它可能提议读取文件、编辑和运行命令。任何一步都不能仅凭模型的意愿发生：

1. **能力门**：Worker 按本次冻结的 Project 和授权级别注册工具。无 Project 时，模型甚至看不到项目工具定义。
2. **参数门**：ToolExecutor 用工具的参数模型解析 JSON；缺字段、错类型或超出大小限制会得到结构化错误，不能把自然语言拼成 shell 字符串直接执行。
3. **对象门**：项目路径由工具在文件系统上解析并核对根边界。相对路径、链接、已存在与待创建目标的处理并不完全相同，因此检查分布在具体动作处。
4. **授权门**：持久化中间件在**每次调用**前复查当前项目版本、冻结输入；权限策略再决定放行、拒绝或等待用户批准。
5. **执行门**：具体工具进一步核对 diff 前置条件、命令白名单、网络开关、输出与超时等，再写入效果账本和结果。

这些门的失败含义不同。找不到工具通常是本 Run 的能力边界；路径越界是对象拒绝；撤销授权使在跑任务无法继续；审批等待是用户尚未决定；测试退出码 1 则是一次**成功运行并观察到失败**的命令，不是任一门的错误。把它们都显示成“操作失败”，用户和模型都很难正确恢复。

## 8. 一个两文件修复的具体推演

假设模型先读 `src/example.py` 和 `tests/test_example.py`，定位到错误分支，然后提交一组编辑。源码中 [EditRequest](../../src/evoagent/projects/editing.py) 描述目标、替换方式和可选期望哈希；`apply_edits()` 会准备原始快照、应用文本变换、生成统一 diff，再尝试写入。跟读这段代码时看以下四类值：

| 值 | 用途 | 不能保证的事 |
| --- | --- | --- |
| `FileSnapshot.raw` / SHA-256 | 记录当前字节及并发前置条件 | 准备后到写入前没有其他进程修改 |
| 编码、行尾与权限位 | 尽量保持文件原样式 | 任意二进制文件都可安全编辑 |
| 统一 diff | 给模型、用户和审计者看预期改变 | diff 已经落盘或只发生这些改变 |
| `EditOutcome` / `PatchOutcome` | 汇总每个文件的操作结果 | 整个 Git 工作树是数据库事务 |

单个文件的临时文件加 `os.replace` 解决“读者看见半截文件”的问题。两文件先后替换期间，另一个程序仍可能看见“一新一旧”；第二次替换失败时实现会尝试回滚第一次，但回滚本身也可能失败。因此 Agent 在复测前应该读取工具结果与实际 diff，不能只因工具返回“补丁已应用”就断言代码库完全一致。若外部编辑器同时改了同一文件，`expected_sha256` 可以让**准备阶段**拒绝旧前提；它并非整段执行时间的锁。

然后模型运行 `python -m pytest -q`。命令工具把退出码、stdout、stderr 单独带回模型。它可以根据失败再修改并运行**同一条 argv**；第二次调用在可靠性账本里必须是新效果。最终若用户要“给我一份报告”，对项目 README 的编辑并不等于交付产物；应调用 `file_write` 或 `artifact_write`，取得 Artifact ID，页面才能预览/下载并做哈希复核。一次任务因此横跨**项目工作树**和**Run 产物空间**，两者的权限与生命周期不同。

## 9. 安全边界要按执行模式表述

威胁模型中最容易混淆的是**工具验证**与**操作系统隔离**。`run_command` 对 argv、cwd 和网络标志做校验，能拒绝不符合接口契约的直接请求；一旦允许通用解释器执行脚本，脚本内部行为仍可能超出这些静态检查。在 Windows 可信本机模式，获批程序在当前用户权限下运行；因此“项目根约束”主要覆盖**内置文件工具的目标**，不是获批进程能读写的全部路径。用户选择该模式，实质是在每次命令前作信任决定。

Docker 个人模式的 Linux Worker 给子进程附加 Landlock 文件视图和离线 seccomp 网络约束，隔离建立失败时拒绝执行。隔离保护的是命令路径，不代表所有外部协议都运行在同一个隔离层；例如 `web_fetch` 是专门的只读公开网页工具，靠 URL 守卫逐跳处理重定向。另一方面，MCP 服务由外部进程或网络端点实现，批准其目录与调用要另算风险。读一个任务的 Trace 时要指出**具体哪个工具、在哪种模式、由哪个执行者**做了动作，不能笼统说“系统有沙箱，所以安全”。

可用下表判断一些看似相近的需求究竟由哪条路径承担：

| 用户需求 | 优先工具 | 主要限制 |
| --- | --- | --- |
| 找到仓库里的定义 | `find_files`、`search_text`、`project_file_read` | 仅授权项目根内，按范围读取 |
| 改两处代码 | `edit_file` / `apply_patch` | 需要 `read_write`，比较快照与 diff，多文件非原子 |
| 跑测试或构建 | `run_command` | 项目授权、白名单、网络标志及对应模式审批 |
| 交付可下载说明 | `file_write` / `artifact_write` | Run 输出空间，须登记产物；不自动写进项目 |
| 引用公开页面 | `web_search` → `web_fetch` | 公开地址检查；搜索摘要不等于正文证据 |
| 调外部服务 | 已审核并激活的 MCP 工具 | 绑定冻结，外部结果仍视作不可信资料 |

## 10. 用一条任务检查能力边界

设任务为“读取项目测试，修复错误，运行测试，交付一份报告”。先在 [Worker 装配](../../src/evoagent/workers/bootstrap.py) 指出这次 Run 真正拥有的工具；再在 `projects/schema.py` 判断路径是否留在授权根内；到 `projects/editing.py` 找 diff 和写入；到 `projects/commands.py` 判断命令实际在哪个操作系统运行；最后到产物 API 找报告的哈希验证。若任何一步只能靠模型一句“已完成”来证明，就还没有走完证据链。

[第四部分](04-知识进化与质量验证.md) 接着说明一次任务的轨迹何时可以变为记忆、何时可以提炼为 Skill，以及为何这两个机制不能自动证明能力提升。

## 11. 源码精读：项目根的三种“路径”

在 [projects/schema.py](../../src/evoagent/projects/schema.py)，`normalize_root()` 处理用户登记的根：要求非空、绝对路径、真实存在且是目录，`resolve(strict=True)` 后还比较规范化前后是否相同。若用户登记的是指向别处的 symlink/junction，服务拒绝并让他直接登记物理目标。这避免页面显示的授权根与 Worker 实际访问的目录不一致。

每次工具拿到相对路径时，`resolve_inside_root()` 返回**词法目标**与**物理目标**。先把相对路径接在根下，规范化 `..` 并确认词法上仍在根内；目标存在时再解析真实路径，确认物理上也在根内，并检查链接是否逃逸。目标尚不存在时，只能返回词法路径让具体写工具继续处理，不能假装“物理检查已经完成”。所以读文件、创建新文件、移动文件、遍历目录的后续检查不同。任何声称“只要字符串没有 `..` 就安全”的解释都漏了链接和路径前缀问题。

`ProjectRecord.root` 保存的是已登记的物理根，但目录可能被卸载、替换或撤销。Task 创建时检查一次，Worker 装配和每次项目工具动作仍要验证；这是为了避免“昨天授权的 D:\work，今天被换成另一个目录”仍被静默使用。对系统边界的核对要分**身份冻结**、**当前授权**、**实际文件系统状态**三步。

## 12. 源码精读：发现、搜索、读取是三个不同操作

用户说“读整个项目”时，模型通常不该先把所有文件一次塞进上下文。`ListDirTool` 查看目录项，`FindFilesTool` 按模式找路径，`SearchTextTool` 搜正文并给出位置，`ProjectFileReadTool` 才读取具体范围。四个工具的输出都有限额，目的是让模型先缩小候选，再读证据。`find_files` 回答“可能在哪些文件”，`search_text` 回答“哪行出现过这个词”，但两者都不等于理解命中的函数；写模块地图时应进一步读取相关正文。

跟读时可以用一个仓库问题做练习：“Task 在哪里创建？”先搜 `create_task`，从路径与命中定位 `tasks/service.py`；读函数签名和事务体；再从调用者追到 `api/routes/tasks.py`。最后写出“HTTP 路由不执行模型、Task Service 不领取租约、Worker 不替用户登记项目”的三条边界。这样才把搜索结果变成了架构知识。

## 13. 源码精读：编辑请求怎样变成真实字节

[projects/editing.py](../../src/evoagent/projects/editing.py) 的 `apply_edits()` 分两轮：第一轮对每个 `EditRequest` 找目标、读 `FileSnapshot`、检查 `expected_sha256`、定位旧文本或行范围、计算替换后的文本/编码/行尾、生成 diff 与新 SHA-256；若某个文件前置条件失败，整批都不会写盘。`dry_run` 在这里返回准备结果。第二轮对准备好的每个文件执行 `_atomic_write()`，发生异常则倒序尝试恢复已写文件。

源码中值得亲自核对三个限制：同一批次不能重复指定同一路径；编码器必须能把新文本按原文件可用方式写回，结果还有大小上限；原内容与替换内容相同的无效编辑会被拒。`FileSnapshot` 包含原始字节和权限位，回滚用原始字节而不是根据 diff 逆推，这能减少编码与行尾失真。

```text
请求 A、B → 准备 A（读原字节、算新字节）→ 准备 B → dry_run 可在此结束
                                      ↓
                         写 A → 写 B → 返回每文件结果
                           └─ B 写失败 → 尝试回滚 A
```

这里的“先准备后写”只是失败时尽量减少半成品；文件系统不存在跨文件事务。尤其源码中的注释容易让人误以为 `expected_sha256` 锁住了准备到写盘的整个窗口，实际上它只在 `_check_precondition()` 时比较快照。项目外编辑器之后仍可能修改同一目标。手册故意把这个差距写明，审阅真实项目修改时要看最终工作树状态。

## 14. 源码精读：命令从参数到子进程

[ProjectCommandTool](../../src/evoagent/tools/builtin/project_command.py) 接收结构化 `argv`、`cwd`、`allow_network`，而不是一条任意拼接的 shell 字符串。真正执行前，[projects/commands.py](../../src/evoagent/projects/commands.py) 的 `validate_argv()` 按白名单与命令类别拒绝不合规程序，`validate_cwd()` 解析项目内真实工作目录，`validate_arguments_inside_root()` 额外检查“看起来像路径”的参数。这个参数扫描不是通用命令语义解析器：`-c` 后的脚本、运行时读取的配置文件和程序内部行为，不能靠它完全约束。

Linux 路径中，父进程构造最小环境，创建临时目录，再启动 `python -m evoagent.projects.command_runner ... -- <argv>`。子进程负责建立 Landlock 文件视图、离线时的 seccomp 网络限制与资源限制；父进程观察墙钟、输出与进程树数量。若隔离安装失败，命令不能退化成不隔离执行。Windows 可信本机路径则进入 `_run_trusted_windows_command()`；虽然也验证 cwd 与白名单、强制人工审批，但获批程序以用户权限运行。尤其 PowerShell 的脚本正文可包含路径和其他命令，因此源码特意不对可信本机解释器的整段参数做同样的词法路径判断；边界落在**用户审查完整脚本**。

一个值得在源码中找的对照是：Linux 离线命令并非只设置 `EVOAGENT_COMMAND_NETWORK=isolated`，还在子进程安装过滤；环境变量只是给任务自检。Windows 的 `allow_network=true` 也不是目的地白名单或网络沙箱，它明确承认当前无法可靠对获批子进程断网。文档若只写“allow_network=false 所以安全”，就是把配置标志误当 OS 保证。

## 15. 源码精读：产物为什么是文件加数据库记录

[LocalArtifactStore](../../src/evoagent/trace/artifacts.py) 把名字规范为 Run 目录下的相对路径，拒绝绝对路径与 `..`，并对目标做根内解析。覆盖型写入先写同目录临时文件再 `os.replace`；不可覆盖型 `write_unique()` 用 `O_EXCL` 排他创建。`ArtifactService` 负责把字节的 SHA-256、大小、URI 与 Run ID 写进数据库，提供页面检索的身份。仅仅在磁盘上出现一个文件，不代表它已经是可下载 Artifact。

看 [api/routes/artifacts.py](../../src/evoagent/api/routes/artifacts.py) 时，确认预览/下载入口使用数据库中的 Artifact ID，而不是接收任意路径；读取后再次计算哈希并与登记值比较。若内容被外部改动，返回冲突而不是把“和登记时不同的文件”交给用户。`file_write` 和 `artifact_write` 都通过这套登记路径，只是覆盖语义不同；项目里的 `edit_file` 根本不走这条 Run 产物目录。三者常被模型混淆，是检查“报告写了却页面没有下载按钮”时的第一处源码分叉。

## 16. 源码精读：网页和 MCP 如何接入相同的执行链

`WebSearchTool` 提供候选结果；`WebFetchTool` 才读取正文。[tools/guards.py](../../src/evoagent/tools/guards.py) 的 URLGuard 要对原始地址与每次重定向检查目标，拒绝把“读取公开网页”变成访问环回或私网管理接口。`trace/sources.py` 记录来源观察，让评测能够区分搜索摘要与已经读过的正文。但是 `source.observed` 只证明读过某页，不证明页面上的话正确或支持模型的每一条结论。

MCP 通过 [mcp/service.py](../../src/evoagent/mcp/service.py) 的发现/审核/激活流程进入 Registry，[mcp/adapter.py](../../src/evoagent/mcp/adapter.py) 把协议调用适配为工具。`PersistentAgentRunner.handle()` 会为当前 Run 注册符合绑定的 MCP 工具；ToolExecutor 仍做参数、配额、租约和中间件处理。MCP 是扩展工具来源，不是绕过本地 ToolEffect/审批的第二执行引擎。若远端返回文本叫模型“跳过授权”，它仍只是工具结果内容。

## 17. 一次项目编辑的参数、结果与失败分支

从 [tools/builtin/project_edit.py](../../src/evoagent/tools/builtin/project_edit.py) 追到 `projects/editing.py`，可以把 Agent 的请求理解为“在授权根内对某个已知快照做可审查的变换”，而不是“把模型生成的整文件字符串无条件覆盖”。例如 Agent 想把 `return old_value` 改为 `return new_value`，应给出目标相对路径、旧片段、替换片段，必要时附 `expected_sha256`。旧片段若不存在、匹配不唯一、哈希与当前字节不同或编码无法可靠往返，工具应给错误结果，模型需重新读取再决定。

`apply_edits()` 准备阶段产生每文件 `EditOutcome`，包含 diff、增删行统计、是否新建、新 SHA-256 和行尾统计。`dry_run` 只返回这份预演，不改变磁盘。真实写入阶段每个文件以临时文件替换，并把结果交给上层形成 ToolResult。`ToolExecutor` 截断给模型的长输出时，还可把全文放进 OutputStore；因此一个短 ToolResult 不能证明 diff 只有屏幕上可见的几行。要复核完整改动，应看保存的输出与实际工作树。

错误至少分四类：**参数不合法**（无法解析请求）、**前置条件冲突**（旧文本或哈希不符）、**授权/路径拒绝**（不能碰该目标）、**写盘或回滚问题**。把它们统一为“编辑失败，请重试”会让模型反复用旧前提撞同一个文件，也会把越权误当可恢复故障。测试入口分别见 [test_project_schema.py](../../tests/unit/test_project_schema.py)、[test_project_editing.py](../../tests/unit/test_project_editing.py) 和 [test_project_edit_ledger.py](../../tests/integration/test_project_edit_ledger.py)。

## 18. 一个命令调用的结构化证据长什么样

在 [projects/commands.py](../../src/evoagent/projects/commands.py)，`CommandSpec` 固定 `argv/cwd/allow_network`，`CommandOutcome` 固定 `return_code/stdout/stderr/截断标记/时长/超时/cwd/program/进程数超限标记`。argv 由 ToolCall 及 Trace 保留，结果与调用合看才是完整证据。成功启动的测试即使退出码为 1，也不能只留一个布尔 `success=false`；模型需读断言失败，评审者需确认“修复后复测”的命令和修复前是同一条。

```text
调用一：argv=["python", "-m", "pytest", "-q"]，cwd="."
        → exit_code=1，stderr/输出包含失败断言
模型读取失败、编辑目标文件
调用二：argv=["python", "-m", "pytest", "-q"]，cwd="."
        → exit_code=0，输出包含通过统计
```

若命令被超时、隔离初始化失败、进程数超限或用户拒绝，证据结构与“测试正常运行但断言失败”不同。审查时要核对 `cwd` 实际物理根，Docker 个人模式下它是容器挂载的路径；Windows 本机模式下是当前 Windows 用户可访问的目录。若前端把两条路径都显示为“本机项目”，用户可能误以为命令在 Windows 上用了同一套依赖。

批准命令的时间点也要读对：`PersistentToolMiddleware.before()` 先以规范参数和执行绑定生成/查询 Approval，用户批准后 Task 重新排队；下一次 Worker 仍要重新检查授权与输入，不能因有旧批准就跳过这些边界。命令的审批通常一次调用一次决定；把两次相同 argv 合并会让第二次复测失去独立证据。

## 19. 产物写入与项目写入的生命周期对照

| 维度 | 项目 `edit_file` | Run `file_write` | Run `artifact_write` |
| --- | --- | --- | --- |
| 目标 | 用户授权项目的文件树 | 本 Run 输出目录内相对路径 | 本 Run 输出目录内相对路径 |
| 典型用途 | 改代码、配置、资料 | 可更新报告、导出文件 | 不可覆盖的结果快照 |
| 覆盖语义 | 依据旧内容/哈希前置条件 | 显式 `overwrite=true` 时同名可更新登记 | 同名排他创建，拒绝覆盖 |
| 页面下载 | 不自动出现在产物列表 | 登记成功后可预览/下载 | 登记成功后可预览/下载 |
| 恢复核对 | 项目 diff 与 ToolEffect | ArtifactRecord、URI、内容哈希 | ArtifactRecord、URI、内容哈希 |

这张表还解释了一类历史故障：磁盘文件已写入，但登记失败，页面却无产物。源码用路径规范化、内容快照与数据库登记把这两步尽量收紧；但文件存储与 PostgreSQL 仍不是同一个原子事务。失败时要按 Artifact ID 和内容哈希核查，而不能只问“文件在不在目录里”。对应测试可从 [test_artifact_service.py](../../tests/unit/test_artifact_service.py)、[test_artifact_export.py](../../tests/integration/test_artifact_export.py) 和 [test_task_artifacts.py](../../tests/e2e/test_task_artifacts.py) 开始。

## 20. 代码实验：对同一根目录试五种路径

用 [projects/schema.py](../../src/evoagent/projects/schema.py) 的 `resolve_inside_root(root, requested)` 做一个临时目录实验。先建 `root/src/a.py`，再在 `root` 外建 `secret.txt`，最后在 `root` 里建一个指向外部的符号链接；Windows junction 的具体创建方式另按宿主权限。依次传入：

| 输入 | 期望判断 | 理由 |
| --- | --- | --- |
| `src/a.py` | 允许、返回根内物理文件 | 正常相对路径 |
| `src/../src/a.py` | 允许且规范化 | `..` 本身不必一概拒绝，关键是规范化后仍在根内 |
| `../secret.txt` | 拒绝 | 词法目标越根 |
| `link/secret.txt`（link 指向外部） | 拒绝 | 词法根内，物理目标越根 |
| `new/report.md`（不存在） | 返回待创建词法目标，具体写工具继续检查 | 尚无物理目标可解析 |

这个实验说明项目边界不等于字符串黑名单。也提醒：对尚不存在的新目标，检查到的只是当前路径状态；父目录后来若被替换成链接，仍存在竞态。因此项目文件工具在动作点重复核对，真实系统也不能宣称具有对所有并发文件系统变化的事务级隔离。若想确认 Linux 命令子进程是否受同样根约束，还要继续看 Landlock 装配；Python 内置工具的路径函数与外部进程隔离是两套机制。

## 21. 代码实验：在同一文件上比较 `dry_run` 和真实编辑

准备带 CRLF 行尾的 `src/demo.py`，先用 `apply_edits(..., dry_run=True)` 改一行。记录原文件哈希、返回的 diff 与新哈希；此时磁盘哈希应不变。再用相同请求真实执行，磁盘新哈希应等于预演结果，同时行尾统计和权限位应按源码约定处理。接着用**原哈希**再请求一次预演，应因前置条件冲突拒绝，而不是覆盖刚才的新版本。

最后准备两个文件，让第二个写入失败，观察工具是否尝试按原始字节回滚第一个。这里不要把“回滚尝试”写成“绝对恢复原状”：若另一个进程刚好改了文件或回滚本身失败，必须以实际 Git diff 和目录内容为准。[test_project_editing.py](../../tests/unit/test_project_editing.py) 已覆盖多种准备、编码、冲突与回滚路径；真实项目验证还要考虑文件锁和平台行尾。
