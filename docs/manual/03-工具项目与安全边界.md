# 第三部分：工具、项目与安全边界

前两册解释了任务如何创建、运行和恢复。本册回到最实在的问题：Agent 能读什么、改什么、跑什么，用户如何拿到结果？请始终区分**模型收到的工具定义**、**工具自身的路径检查**、**执行环境的操作系统权限**。三个层次共同决定能力边界，任何一层的“已授权”都不能代替另两层。

## 1. 工具清单是每个 Run 装配出来的

[ConfiguredTaskHandler._project_tools()](../../src/evoagent/workers/bootstrap.py) 根据已冻结的 Project 装配工具。[ToolRegistry](../../src/evoagent/tools/registry.py) 把本 Run 的工具定义交给模型；若 Provider 返回未注册的工具名，执行层仍须拒绝。无项目时仍有计算、搜索、网页读取、向用户提问及 Run 产物等非项目工具，但没有项目目录、编辑和命令工具。`read` 项目提供 `list_dir`、`find_files`、`search_text`、分段 `file_read` 和文本抽取；`read_write` 再增加编辑、移动/删除、目录整理和白名单命令。

工具描述是给模型看的使用提示；真正的边界在 [参数契约](../../src/evoagent/core/models.py)、[工具执行层](../../src/evoagent/tools/executor.py)、[项目授权复查](../../src/evoagent/projects/boundaries.py) 与具体工具函数中。模型可以被仓库文件、网页或测试输出诱导，但这些文字不能修改 ToolRegistry、项目授权或审批记录。

## 2. 路径不是一串字符串

[项目登记](../../src/evoagent/projects/service.py) 要求目录存在且可用；[路径契约](../../src/evoagent/projects/schema.py) 同时处理词法路径、规范化的物理路径和符号链接/junction。只检查 `..` 不够：一个看似位于根内的路径可能经链接跳出；只检查物理路径也不够：某些操作会在检查之后创建新目标。内置项目文件工具在各自的读取/写入点继续校验，工具结果返回相对根的可说明路径。

目录发现与内容搜索不是一次“读取整个仓库”。[list_dir](../../src/evoagent/tools/builtin/list_dir.py) 展示可见目录项；[find_files](../../src/evoagent/tools/builtin/find_files.py) 按路径模式定位文件；[search_text](../../src/evoagent/tools/builtin/search_text.py) 给出命中位置；[项目 file_read](../../src/evoagent/tools/builtin/project_file_read.py) 才按范围取正文。忽略规则、条数和字节上限使模型能逐步缩小目标。若要证明它真的理解项目，最终模块地图应能回到这些已读取文件，而不能只看模型自述“我检查过”。

输入文件还可以在创建 Task 时作为 [冻结输入](../../src/evoagent/projects/inputs.py) 记录哈希。之后每次工具动作前复查；文件被替换就产生 `input_changed`，让用户知道这次任务的输入条件已经变化。它与通用的目录读取不同：冻结输入表达的是“请针对这一批字节工作”。

## 3. 精确编辑的保证与边界

[edit_file / apply_patch](../../src/evoagent/tools/builtin/project_edit.py) 把路径、旧内容或行范围、替换文本和可选 `expected_sha256` 转成 [编辑请求](../../src/evoagent/projects/editing.py)。实现先读取文件快照、识别文本编码和行尾，验证前置条件，生成 diff；`dry_run` 可在不写盘时预览。写入时每个文件使用同目录临时文件加 `os.replace`，避免读者看到半个文件；原有权限位尽量保留。多文件批次先准备所有变更，写入中遇错会尝试按原快照回滚已写文件。

必须准确理解其边界：**单文件替换是原子可见的，多文件批次不是数据库式原子事务**。准备之后到逐文件写入之间仍有并发窗口；`expected_sha256` 会在快照阶段发现已变化的内容，但不能把整批操作变成跨进程锁定的工作树事务。回滚也可能因外部修改或磁盘故障失败。审查时同时看原哈希、diff、实际结果和 Trace；不能仅凭“工具返回成功”推断 Git 工作树只发生了预期改动。待审批的编辑有服务端重算的 diff；自动放行的 R1 编辑没有执行前人工审查。这些限制在[当前状态](../当前状态.md)中仍列明。

`delete_file` 不做隐式递归清空；`move_file` 要求目标不存在。[organize_files](../../src/evoagent/tools/builtin/project_organize.py) 使用 [整理计划](../../src/evoagent/projects/organize.py) 先生成去向和冲突清单，再应用。把“建议怎样整理”和“已经移动了什么”分开，是让用户能审查目录操作的关键。

## 4. 同一个 `run_command`，两种操作系统语义

[ProjectCommandTool](../../src/evoagent/tools/builtin/project_command.py) 接受结构化 `argv`、项目内 `cwd` 与 `allow_network`。 [commands.py](../../src/evoagent/projects/commands.py) 校验参数数目、可执行文件白名单、工作目录、部分看起来像路径的参数，并把 stdout、stderr、退出码、时长、超时及截断状态作为结果返回。退出码非零是模型应观察的测试证据，不被抹成通用工具异常。相同 argv 在修复前后可以运行两次：命令工具的两次调用不按参数合并 ToolEffect。

| 层面 | Docker 个人模式 | Windows 可信本机模式 |
| --- | --- | --- |
| 进程位置 | Linux Worker 容器 | 启动 `host_mode.py` 的 Windows 用户会话 |
| 项目目录 | 宿主父目录挂到 `/app/projects`，页面登记容器路径 | 页面登记 Windows 绝对路径 |
| 命令授权 | 白名单；可识别离线检查可按 R1 执行，构建/安装/通用解释器与联网命令逐次审批 | 白名单且每次强制 R2 审批；必须显式 `allow_network=true` |
| 文件/网络隔离 | 子进程需成功建立 Landlock 文件视图；离线命令另用 seccomp 阻断网络；有单进程资源、超时、输出和进程树数量限制 | 工作目录受项目根约束；获批程序有当前用户权限，可访问根外文件和网络；没有等价 OS 沙箱或进程树资源隔离 |

Docker 子进程建立隔离失败时命令直接失败，不会无声退回不隔离执行。[command_runner.py](../../src/evoagent/projects/command_runner.py) 安装 Linux 侧约束；[commands.py](../../src/evoagent/projects/commands.py) 管父进程侧超时和进程树计数。Windows 分支逐次审批，但审批是一种**用户信任决定**，不是给获批程序加 OS 文件沙箱。模型可提议 PowerShell；用户必须看完整脚本正文。校验器能拒绝直接的 `git push`、`npm publish` 等 argv，**不能识别获批解释器脚本内部的等价操作**；Windows 获批进程又没有网络隔离，因此不能把这项校验写成普遍的“禁止外部发布”保证。

独立 [shell 工具](../../src/evoagent/tools/builtin/shell.py) 是另一条默认关闭的路径，走 [sandbox-controller](../../src/evoagent/sandbox/controller.py) 的固定规格容器；它不是项目 `run_command` 的别名。把两条路径混起来，会错误推断某个任务实际操作的文件树和网络边界。

## 5. 普通文件、项目文件和产物为什么分开

项目 `edit_file` 改的是用户授权的工作树；Run `file_write` 写的是本次运行的输出空间，并通过 [ArtifactService](../../src/evoagent/trace/artifacts.py) 登记为可下载产物。`file_write` 可以按相对路径创建 `reports/summary.md`，同名覆盖会更新登记记录；`artifact_write` 创建不可覆盖的产物。它们的分工在 [file_write](../../src/evoagent/tools/builtin/file_write.py) 与 [artifact_write](../../src/evoagent/tools/builtin/artifact_write.py) 中。项目文件的修改**不会自动变成下载列表中的产物**；需要交付报告时，模型应明确使用产物工具。

[产物 API](../../src/evoagent/api/routes/artifacts.py) 只接受数据库中已登记的 ID，不接受任意文件路径；预览有上限，下载前重新读取并核对登记 SHA-256，不一致返回 409。登记记录与不可变内容快照配合，避免覆盖新内容后旧记录指向错误字节。页面上的哈希和响应头 `X-Content-SHA256` 让用户能核对拿到的文件。这个出口不是任意读取项目目录的 API。

[extract_text](../../src/evoagent/tools/builtin/project_extract.py) 处理明确编码的文本和**文本型** PDF；图片扫描件没有 OCR。[organize_files](../../src/evoagent/tools/builtin/project_organize.py) 处理目录整理。能解析某种格式，仍不意味着真实模型已在各种私人资料上稳定完成任务；证据等级见[当前状态](../当前状态.md)。

## 6. 公开资料与外部协议

[web_search](../../src/evoagent/tools/builtin/web_search.py) 可选 Mock、无密钥 `ddgs` 或 Brave；[web_fetch](../../src/evoagent/tools/builtin/web_fetch.py) 只读公开 HTTP(S) 文本，重定向每一跳经过 [URLGuard](../../src/evoagent/tools/guards.py) 检查。搜索摘要与真正读取过的正文分开记 [来源证据](../../src/evoagent/trace/sources.py)。引用某个 URL 只能证明模型写出了这个 URL；即使系统确认读过该网页，仍需人工判断来源是否支持结论。[逐结论引用检查](../../src/evoagent/evals/citations.py) 帮助找机械不匹配，不替代事实审查。

[MCP](../../src/evoagent/mcp/service.py) 先发现目录并供用户审核，再显式激活执行。Run 冻结工具契约和执行绑定；[MCP 适配器](../../src/evoagent/mcp/adapter.py) 接入统一工具执行层。发现服务器、批准目录、让某个 Run 看到工具、实际获批调用是四个不同动作。外部服务的响应仍是不可信资料，不能借 MCP 取消本地审批或扩大项目授权。

## 7. 从“模型想做”到“系统允许做”的五道门

当模型读到“请把失败测试修好”，接下来它可能提议读取文件、编辑和运行命令。任何一步都不能仅凭模型的意愿发生：

1. **能力门**：Worker 按本次冻结的 Project 和授权级别注册工具。无 Project 时，模型甚至看不到项目工具定义。
2. **参数门**：ToolExecutor 用工具的参数模型解析 JSON；缺字段、错类型或超出大小限制会得到结构化错误，不能把自然语言拼成 shell 字符串直接执行。
3. **对象门**：项目路径由工具在文件系统上解析并核对根边界。相对路径、链接、已存在与待创建目标的处理并不完全相同，因此检查分布在具体动作处。
4. **授权门**：持久化中间件在**每次调用**前复查当前项目版本、冻结输入；权限策略再决定放行、拒绝或等待用户批准。
5. **执行门**：具体工具进一步核对 diff 前置条件、命令白名单、网络开关、输出与超时等，再写入效果账本和结果。

这些门的失败含义不同。找不到工具通常是本 Run 的能力边界；路径越界是对象拒绝；撤销授权使在跑任务无法继续；审批等待是用户尚未决定；测试退出码 1 则是一次**成功运行并观察到失败**的命令，不是任一门的错误。把它们都显示成“操作失败”，用户和模型都很难正确恢复。

## 8. 一个两文件修复的具体推演

假设模型先读 `src/example.py` 和 `tests/test_example.py`，定位到错误分支，然后提交一组编辑。源码中 [EditRequest](../../src/evoagent/projects/editing.py) 描述目标、替换方式和可选期望哈希；`apply_edits()` 会准备原始快照、应用文本变换、生成统一 diff，再尝试写入。跟读这段代码时看以下四类值：

| 值 | 用途 | 不能保证的事 |
| --- | --- | --- |
| `FileSnapshot.raw` / SHA-256 | 记录当前字节及并发前置条件 | 准备后到写入前没有其他进程修改 |
| 编码、行尾与权限位 | 尽量保持文件原样式 | 任意二进制文件都可安全编辑 |
| 统一 diff | 给模型、用户和审计者看预期改变 | diff 已经落盘或只发生这些改变 |
| `EditOutcome` / `PatchOutcome` | 汇总每个文件的操作结果 | 整个 Git 工作树是数据库事务 |

单个文件的临时文件加 `os.replace` 解决“读者看见半截文件”的问题。两文件先后替换期间，另一个程序仍可能看见“一新一旧”；第二次替换失败时实现会尝试回滚第一次，但回滚本身也可能失败。因此 Agent 在复测前应该读取工具结果与实际 diff，不能只因工具返回“补丁已应用”就断言代码库完全一致。若外部编辑器同时改了同一文件，`expected_sha256` 可以让**准备阶段**拒绝旧前提；它并非整段执行时间的锁。

然后模型运行 `python -m pytest -q`。命令工具把退出码、stdout、stderr 单独带回模型。它可以根据失败再修改并运行**同一条 argv**；第二次调用在可靠性账本里必须是新效果。最终若用户要“给我一份报告”，对项目 README 的编辑并不等于交付产物；应调用 `file_write` 或 `artifact_write`，取得 Artifact ID，页面才能预览/下载并做哈希复核。一次任务因此横跨**项目工作树**和**Run 产物空间**，两者的权限与生命周期不同。

## 9. 安全边界要按执行模式表述

威胁模型中最容易混淆的是**工具验证**与**操作系统隔离**。`run_command` 对 argv、cwd 和网络标志做校验，能拒绝不符合接口契约的直接请求；一旦允许通用解释器执行脚本，脚本内部行为仍可能超出这些静态检查。在 Windows 可信本机模式，获批程序在当前用户权限下运行；因此“项目根约束”主要覆盖**内置文件工具的目标**，不是获批进程能读写的全部路径。用户选择该模式，实质是在每次命令前作信任决定。

Docker 个人模式的 Linux Worker 给子进程附加 Landlock 文件视图和离线 seccomp 网络约束，隔离建立失败时拒绝执行。隔离保护的是命令路径，不代表所有外部协议都运行在同一个隔离层；例如 `web_fetch` 是专门的只读公开网页工具，靠 URL 守卫逐跳处理重定向。另一方面，MCP 服务由外部进程或网络端点实现，批准其目录与调用要另算风险。读一个任务的 Trace 时要指出**具体哪个工具、在哪种模式、由哪个执行者**做了动作，不能笼统说“系统有沙箱，所以安全”。

可用下表判断一些看似相近的需求究竟由哪条路径承担：

| 用户需求 | 优先工具 | 主要限制 |
| --- | --- | --- |
| 找到仓库里的定义 | `find_files`、`search_text`、`project_file_read` | 仅授权项目根内，按范围读取 |
| 改两处代码 | `edit_file` / `apply_patch` | 需要 `read_write`，比较快照与 diff，多文件非原子 |
| 跑测试或构建 | `run_command` | 项目授权、白名单、网络标志及对应模式审批 |
| 交付可下载说明 | `file_write` / `artifact_write` | Run 输出空间，须登记产物；不自动写进项目 |
| 引用公开页面 | `web_search` → `web_fetch` | 公开地址检查；搜索摘要不等于正文证据 |
| 调外部服务 | 已审核并激活的 MCP 工具 | 绑定冻结，外部结果仍视作不可信资料 |

## 10. 用一条任务检查能力边界

设任务为“读取项目测试，修复错误，运行测试，交付一份报告”。先在 [Worker 装配](../../src/evoagent/workers/bootstrap.py) 指出这次 Run 真正拥有的工具；再在 `projects/schema.py` 判断路径是否留在授权根内；到 `projects/editing.py` 找 diff 和写入；到 `projects/commands.py` 判断命令实际在哪个操作系统运行；最后到产物 API 找报告的哈希验证。若任何一步只能靠模型一句“已完成”来证明，就还没有走完证据链。
