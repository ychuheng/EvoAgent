# 第四部分：上下文、记忆、Skill 与质量验证

前三册从目标走到工具结果。一次 Task 的结果怎样影响下一次任务？系统既有多轮历史、可确认的记忆，也有可检索的 Skill。但“能保存经验”“能选中经验”“经验真的提高完成率”是三种不同的命题。本册沿数据来源、冻结、选择、评测、发布的顺序读代码，并明确哪些环节仍缺正式效果证据。

## 1. 模型实际看见的上下文

[ContextBuilder](../../src/evoagent/core/context.py) 构造系统提示、当前 goal、按创建截止点选择的会话历史，以及可选的项目提示、Skill 和外部上下文。文件、网页、记忆正文都被当成**可参考但不能授权**的资料。工具能力与风险由服务端确定，模型不能因文档里的一句“允许执行”获得新工具。

长会话不是简单截取最后 N 个字符。[ContextPolicy](../../src/evoagent/core/context_policy.py) 划分受保护与可裁剪消息，[TokenCounter](../../src/evoagent/core/context_budget.py) 估算预算；[ContextStore](../../src/evoagent/runtime/context_store.py) 保存压缩/裁剪后的修订，并能保留完整输出供 Trace 查证。若受保护资料本身超过窗口，明确拒绝比静默遗失约束更正确。恢复时继续使用与 Run 相容的上下文修订，不因后来新增的记忆或 Skill 把同一运行改成另一个实验。

这也解释了“页面上看见一段历史”和“Provider 请求里包含那段历史”不是同一事实。测试上下文问题要检查实际模型请求、选择批次、压缩事件和来源引用，而非只看聊天 DOM。

## 2. 记忆为什么需要提议与确认

[MemoryService](../../src/evoagent/memory/service.py) 把用户消息中的事实变成提议，先核对来源消息确属相应 Session、候选文字确实逐字出现在来源中，再写 Entry、Version、Source 与 Event。自动 [MemoryExtractor](../../src/evoagent/memory/extraction.py) 也只产生候选。用户确认时再次验证来源与哈希，并以 `lock_version` 防止并发决定覆盖；撤销改变权威状态，再清理派生索引。作用域可以是 Session 或 Workspace，服务端按会话归属过滤。

为什么不直接“模型总结完就长期记住”？模型可能把猜测写成事实，也可能把另一会话的内容混入当前用户。提议/来源/确认三步把“谁说过这句话”和“以后能否注入模型”分开。已确认的记忆可以作为事实参考，但记忆正文仍不能给工具授权。Run 在请求前复验所选来源；旧记忆被撤销后，新请求不能继续拿它当当前有效来源。

数据库权威记录与 pgvector 索引不是一回事。[IndexService](../../src/evoagent/retrieval/indexing.py) 以来源变化安排派生索引，索引失败不能凭空改变记忆的确认状态。索引 generation、Profile 的模型/维度/预处理方式需要一致；Embedding 服务是对话模型以外的独立依赖。没有真实 Embedding 配置时，不应把“检索代码存在”描述成真实语义召回已启用。

## 3. 检索把来源变成冻结选择

小规模 Skill 默认可通过 [BM25Retriever](../../src/evoagent/skills/retrieval.py) 检索：先筛活动版本和工具兼容性，再按任务目标打分、选择。若启用混合检索，[ContextResolver](../../src/evoagent/runtime/context_resolver.py) 将词法结果与 [向量距离](../../src/evoagent/retrieval/vector.py) 交给 [RRF 排序](../../src/evoagent/retrieval/hybrid.py) 合并，并按 Skill、记忆和归档各自预算选择注入文本。外部 Embedding 调用放在短数据库事务之外，返回后复查来源、索引代次和权限，再冻结实际选择。

“没有命中”也是结果。Run 首次明确无选中之后，恢复时不能因为别人发布了一个新 Skill，就悄悄把旧 Run 的上下文改掉。[RunSkillSelectionRecord](../../src/evoagent/db/models.py) 与检索批次保留这个决定。模型是否真的按 Skill 做事仍要看工具轨迹和最终产物；`skill.selected` 只证明该版本进入了上下文。

## 4. Skill 自进化是一条带门槛的流水线

```mermaid
flowchart LR
    T[已核对的 dev / TRAIN 轨迹] --> P[来源资格与脱敏]
    P --> D[候选 Skill DRAFT]
    D --> V[Schema / 静态校验]
    V --> E[冻结 holdout 配对实验]
    E --> H[人工审核]
    H --> A[发布 / 禁用 / 回滚]
    A --> R[新 Run 检索]
```

入口有两个层次。产品中的 [SkillExtractionService](../../src/evoagent/skills/extraction.py) 接受符合资格的 TRAIN EvalRun，经 [ProvenanceService](../../src/evoagent/skills/provenance.py) 冻结来源，再由生成器提出 [SkillDefinition](../../src/evoagent/skills/schema.py) 草稿。M6 的个人项目候选另用 [sourcing.py](../../src/evoagent/skills/sourcing.py) 与 `evals/datasets/dev_runs.jsonl` 复查真实 dev 运行来源；未登记或属于 M6/M7 holdout 的运行不能当提炼材料。两条路径都要保留来源和内容哈希，防止“看到正式试卷答案再提炼 Skill”。

Skill 不是可任意执行的脚本。[Schema](../../src/evoagent/skills/schema.py) 约束触发、输入、步骤、工具和风险；[Validator](../../src/evoagent/skills/validation.py) 做静态检查，M6 候选还要求停止条件、审批点与反例。模型最多创建 DRAFT，不能自行声称“已发布”。[SkillService](../../src/evoagent/skills/service.py) 管版本及发布、禁用、回滚；普通 Run 只会检索符合条件的活动版本。撤销后新 Run 不再选中，旧 Run 的冻结证据仍可审计。

这些机制解决的是**经验如何安全进入运行时**。它们不证明经验有益：一个写得漂亮、通过 Schema、被模型选中的 Skill，仍可能增加 Token 消耗、误导修复或在新仓库上失效。

## 5. 评测要隔离“是否做对”和“为什么做对”

[DatasetService](../../src/evoagent/evals/datasets.py) 冻结样本与校验器；[EvalCoordinator](../../src/evoagent/evals/coordinator.py) 组织 baseline 与 pinned Skill 的成对运行；[MetricsCollector](../../src/evoagent/evals/metrics.py) 汇总任务成功、成本、耗时和错误；[QualityGate](../../src/evoagent/evals/gates.py) 依据固定规则给出门槛结论。`Run=completed` 不是样本成功，机械 Validator 和人工判分要看文件、diff、退出码、来源与用户目标。

配对设计要求两臂用同一冻结任务、模型、工具与预算，并记录顺序和可比性。若两臂都在简单题上满分，即使 Skill 臂全部通过，也无法证明净收益。统计上真正提供信息的是**两臂结果不同的配对**；30 对不天然有 80% 的检出力。[power.py](../../src/evoagent/skills/power.py) 依据 dev 失配率估算所需样本和可检出效应，[experiment.py](../../src/evoagent/skills/experiment.py) 校验冻结条件与重复使用。无法准备足够独立 holdout 时，诚实结果是“探索性、收益未证实”，不能把不显著写成 Skill 无效，也不能把门禁形式上的通过写成统计证实。

项目的样本台账在 `evals/datasets/manifest.json`；`scripts/check_sample_ledger.py` 检查显式复用与曝光。脚本不能证明两个仓库任务在语义上真正独立，仍需人工抽查模板、解法和内容相似度。正式评审要先看冻结的任务、产物与必要证据，再看轨迹；M6 两臂需匿名评分。实现者自评必须标注，较强收益结论需要预先安排第三方复核。这些要求在[当前实施计划](../EvoAgent-项目设计与分阶段实现计划.md)和[评测索引](../evaluations/README.md)中有对应记录。

## 6. 发布、MCP 与真实任务质量的关系

[ReviewPage](../../frontend/src/pages/ReviewPage.tsx) 与 [Skill API](../../src/evoagent/api/routes/skills.py) 将来源、候选版本、报告和审核理由交给人决定。发布后检索只对新 Run 生效；旧 Run 的内容选择保持可追溯。MCP 目录审核是另一套外部工具准入流程，不能代替 Skill 效果评测。记忆确认也不能代替真实用户任务验收：它只证明一条事实被用户允许长期引用。

M7 发布级检查还要求正常任务、故障与越权样本、迁移、备份恢复、真实模型调用及人工审查共同过门槛。[m7_release_run.py](../../scripts/m7_release_run.py) 是发布集执行入口，[check_state_drift.py](../../scripts/check_state_drift.py) 防止产品变更后状态文档忘记更新。当前 M6 正式配对实验和 M7 的真实模型 24+8 发布集尚未完成，因而项目仍是 `0.4.0.dev0` 候选版；准确数字和限制以[当前状态](../当前状态.md)为准。

## 7. 把“经验”拆成四个不同的数据对象

一次修复任务结束后，系统不会把整个对话一股脑儿放进下次提示。至少有四种可延续的信息，各有来源和权威性：

| 对象 | 内容与来源 | 进入下次 Run 的条件 | 常见误读 |
| --- | --- | --- | --- |
| Session 历史 | 已提交的对话消息与结果 | 新 Task 创建时的历史截止点允许 | 页面上可见就必然进入模型窗口 |
| Memory | 用户可核对的长期事实 | 来源有效、用户确认、作用域匹配 | 模型推断也能直接变成事实 |
| Skill | 可复用的任务步骤、条件与风险说明 | 版本已发布、检索命中、工具兼容 | 被检索到就证明有收益 |
| Trace / EvalRun | 过去任务的过程与判分证据 | 满足来源资格后可供提炼或评测 | 任意成功轨迹都可当训练材料 |

这张表解释了为什么项目同时有 `sessions/`、`memory/`、`skills/`、`trace/` 和 `evals/`，它们不是五个名字不同的聊天记录。一次 Run 的上下文装配需要决定每类对象的选择、版本、预算及出处；第四册前述的“冻结”就是防止恢复时这些选择意外变化。若用户说“以后都记得这个偏好”，应走记忆提议/确认；若开发者想把多次修复归纳为方法，应走 Skill 来源审核和候选生成，不能借记忆确认绕过效果门槛。

## 8. 沿一条 Skill 候选追踪来源

假设 dev 任务多次出现“测试失败 → 读报错 → 精确编辑 → 用同一命令复测”。提炼候选前先检查每条来源 Run：它属于 TRAIN/dev 而非正式 holdout，Trace 与最终产物可读取，必要的评价和来源哈希齐全。`TraceEligibilityChecker` 判资格，`ProvenanceService.freeze()` 把可使用的来源冻结；生成器才据此构造草稿。若来源 Run 是 M6/M7 holdout，即使修复很精彩也不能回流为 Skill 提炼数据，否则下一轮就是从考题答案里提炼应试口诀。

候选的生成与发布也不是同一动作。`SkillDefinition` 包含触发条件、输入、步骤和风险；静态验证可以发现 schema 不合法、工具不兼容或步骤缺关键约束。审核页让人看到来源、版本差异、评测报告和发布理由。`SkillService.approve()`/`set_status()`/`rollback()` 管理版本状态，发布后的检索只影响**以后新建的 Run**。一条仍在运行的 Task 不能因为新 Skill 上线，就在恢复时改用新版步骤。

提炼来源和评分锚点是两套不同资料。前者是可追溯的任务轨迹，供生成候选；后者是评审某个样本是否做对的预注册判据。评分锚点不能从看过两臂结果后的优胜答案倒写；提炼来源也不能混进正式 holdout。两者都应避免把私人项目原文带到评测报告里。

## 9. 为什么一次“6/6 对 6/6”说明不了收益

配对实验的单位是**任务对**：在可比的冻结环境里，对同一题分别运行 baseline 和固定 Skill 版本。每对可能是两臂都过、两臂都不过、只有 baseline 过、只有 Skill 过。前两种对净差异的方向没有贡献；后两种才是配对二分类检验真正使用的失配。两个系统各 6/6，即使 Skill 臂看起来完美，仍可能只说明题太容易。

这给任务设计带来实际约束。先在 dev 样本估计失配率与最小有意义效应，再计算需要多少独立 holdout；如果预算只支持远小于计算值的样本，报告应写明能检出的效应量和“探索性”，不能把“不显著”译成“Skill 没用”。正式 holdout 在首次运行前入台账；看过结果再调 prompt 或 Skill，原样本就已曝光，只能降为 dev，下一次正式判定需要新样本。台账脚本可检查 ID、哈希和运行记录，语义上只是改名换皮的题还需人工抽查。

成功率也不是唯一指标。即便 Skill 臂多解出一题，还要看无关改动、命令与审批风险、用户目标是否真正达到、耗时、Token 与费用。人工评分应先看冻结任务和产物，再看必要证据；若评分人就是实现者，须标注自评，并按计划安排第三方复核。统计检验解决抽样不确定性，不能代替任务质量与安全边界审查。

## 10. 从一条个人任务反查四册

用户说：“把这个项目的失败测试修好，以后遇到同类错误也按这个方法做。”一条合理的处理链是：

1. **任务层**：创建有项目授权的 Session/Task；冻结项目、输入和历史；Worker 用租约领取。这里的目标还是一次具体修复，而不是立即训练 Skill。
2. **执行层**：模型先搜、读、运行测试，拿到真实失败；提出编辑与复测；每步经工具权限、审批、检查点和效果账本。若外部效果不明，先结清，不用“多试一次”掩盖不确定性。
3. **证据层**：检查同一命令前后退出码、diff、无关修改和用户要求；报告作为 Artifact 登记并可下载。只有 Task `completed` 或自然语言“已修复”都不够。
4. **进化层**：经许可的 dev 轨迹才可供 Skill 候选提炼；人审版本并用未见过的配对任务验证。若效果未证实，可以保留“机制具备、收益未证实”的状态，继续使用基础 Agent。

这条链说明**个人通用 Agent 的基本工作能力**与**Skill 自进化的效果证明**如何相接，也说明为何二者不能互相替代。阅读当前项目时，先沿可运行任务确认它能观察和改变环境，再沿来源与评测链判断经验是否真的改善后续任务。

## 11. 从整体重新读一遍项目

现在用一个问题检查是否形成了系统理解：“用户让 Agent 在 Windows 项目中修复测试，Skill 被检索命中，模型提出 PowerShell 命令，用户批准，命令失败后 Agent 修改两个文件并复测，最后写报告。”你应能沿四册回答：

1. Task 创建时冻结了哪几种身份和截止点？没有项目时工具清单怎样变化？
2. 命令在哪个操作系统运行，审批到底保护了什么，不能保护什么？
3. Worker 在第一次命令结果落账前崩溃时，为什么不能直接执行同一命令？
4. 两个文件的变更与可下载报告分别在哪个目录，哪些写入有原子保证？
5. `skill.selected`、Task `completed`、验收条件通过、M6 净收益、M7 发布通过分别需要什么证据？

能把这些问题连成一条因果链，才是读懂 EvoAgent 源码。遇到旧阶段章节里与当前行为冲突的句子，先核对当前源码与[当前状态](../当前状态.md)；旧章节保留在[历史手册](../archive/manual-legacy/README.md)供研究设计演进。

## 12. 源码精读：ContextBuilder、ContextPolicy、ContextStore 不是一件事

在 [core/context.py](../../src/evoagent/core/context.py)，ContextBuilder 负责**构造**消息：系统提示、目标、可选 Skill 文本、项目上下文和外部资料。它不决定这个 Run 应选中哪一个 Skill，也不负责在历史过长时裁剪。选择发生在持久化 Runner 的检索层，窗口检查发生在 [core/context_policy.py](../../src/evoagent/core/context_policy.py)。读这三者时可以问“谁给内容、谁定优先级、谁保存裁剪后的版本”。

AgentLoop 每一轮都会生成 `ModelRequest`。若启用 [runtime/context_store.py](../../src/evoagent/runtime/context_store.py)，先按上次修订准备可恢复的消息，再由 ContextPolicy 估算请求是否装得进窗口。模型输出过长时，ToolOutputStore 负责给模型截断版并保留全文产物；上下文策略又可对历史中的低优先级内容作裁剪/压缩。这两种“短文本”不是同一个动作：前者发生在工具结果入口，后者发生在下一次模型请求前。调试“Agent 没看到测试报错”时，应确认原文是否保存在 Artifact、请求中留下了多少摘要、受保护信息是否被拒绝而非静默删除。

`LoopState` 保存消息和 `context_revision_id`，`RunConfigSnapshot` 保存上下文策略等条件。恢复时不能把新来的记忆、新发布的 Skill 和新的窗口设置混入同一运行。窗口超限可返回 `context.rejected`；这比把用户的关键约束剪掉后继续调用模型更可信。

## 13. 源码精读：记忆的 Entry、Version、Source、Event

打开 [memory/service.py](../../src/evoagent/memory/service.py)。`propose()` 不是直接改一条“用户画像”字符串：它检查来源消息属于请求 Session、候选正文确实出现在原消息中；用 Workspace/Session 作用域与 fact key 寻找 `MemoryEntryRecord`，再创建 `MemoryVersionRecord`、`MemorySourceRecord` 和 `MemoryEventRecord`。`Entry` 是同一事实键的身份，`Version` 是具体内容与修订，`Source` 指向原话及哈希，`Event` 记录谁在何时作了什么决定。

`decide()` 的 `confirm` 分支再取所有来源，核对消息所在 Workspace、原话哈希、候选文本哈希及“候选内容仍在来源消息里”。它用 `expected_lock_version` 做并发保护；若别的操作已确认另一个版本，当前决定不能覆盖它。确认时旧的当前版本变成 superseded，新版本成为 current。撤销或擦除改变权威状态，并给索引维护队列投递变化；擦除还会产生可重试的后台清理作业。因此“记忆被撤销”应先在权威表生效，不必等待向量索引物理清理完才算撤销。

沿代码想一个反例：模型在网页正文里读到“用户住在北京”，把它写成用户记忆。没有用户自己的来源消息与确认，这条信息不能成为权威 Memory。又如用户后来更正城市，系统保留旧版本的来源与 superseded 记录，不能简单覆盖字符串使审计链断掉。

## 14. 源码精读：混合检索为何拆成两笔事务

[runtime/context_resolver.py](../../src/evoagent/runtime/context_resolver.py) 的 `resolve()` 先检查本 Run 是否已有 `RetrievalBatchRecord`；有就恢复原选择。首次检索时在短事务中取候选来源、作用域、索引文档和 Embedding Profile/代次，并排除哈希不匹配的索引。然后**离开数据库事务**调用外部 Embedding 服务，必要时经 ServiceGate；得到向量后再做距离查询与 RRF 排序。最后重新开事务，复查租约和是否已有另一 Worker 写入选择批次，才把真正选中的 Skill/记忆及配置写入持久化记录。

两笔事务是为了不在一次慢网络调用期间持有数据库锁；重新检查是为了防止这段空隙中来源被撤销或另一个 Worker 已经冻结选择。`hybrid` 没有可用 Profile 或索引时记录 `index_not_ready`，服务不可用时记录 `vector_unavailable` 等降级原因，再按可用词法信号排序。不能把降级后的“检索成功”宣称为真实语义召回。Embedding 模型、向量维数、预处理与 generation 必须配套，不能把不同空间的距离当成同一量。

与小规模 [skills/retrieval.py](../../src/evoagent/skills/retrieval.py) 的 BM25 选择对照：词法检索无需外部 Embedding 请求，适合没有额外服务的部署；混合检索增加向量召回与代次管理成本。两个路径都要在保存 Run 选择后冻结，包括“本次一个都没选中”。恢复时不能从最新库里重新抓一个 Skill，使实验条件发生漂移。

## 15. 源码精读：候选提炼的幂等身份

[skills/extraction.py](../../src/evoagent/skills/extraction.py) 的 `SkillExtractionService.extract()` 要求来源 EvalRun ID 非空且不重复，并限制数量；逐个通过 ProvenanceService 冻结资格与 Trace 哈希，然后调用候选生成器，交给 Validator 校验，M6 候选还须具备停止条件、审批点与反例注解。`SkillDefinition` 的规范 JSON 得到内容哈希；`extraction_key` 再由**排序后的来源 Trace 哈希**与定义哈希组合。相同来源、相同候选重复调用时返回已有草稿，不增生一个看似新版本。

新候选落库时，服务创建或寻找 Skill 身份，写一个 `DRAFT` 版本，再给每个来源写 `SkillSourceRecord`，最后追加 `skill.version_drafted` 事件。这个事务保存了“这个版本从哪来”的链条。生成器可以是 Mock，也可以调用模型，但模型生成出来的文字只是一份待验证草稿。`SkillService` 后续的人审、门槛、发布或回滚与 `extract()` 是不同操作；不能因提炼函数成功返回就说“Agent 已完成自进化”。

若要排查候选为何无法发布，沿四关找：来源是否合格；DSL/静态校验是否通过；比较实验与 QualityGate 是否满足冻结规则；人工决策是否明确。不要直接改数据库状态绕过中间证据，因为那会让新 Run 检索到没有可靠来源的步骤。

## 16. 源码精读：EvalCoordinator 怎样生成并收集配对运行

[evals/coordinator.py](../../src/evoagent/evals/coordinator.py) 的 `create_experiment()` 首先要求 Dataset 已 `FROZEN`、Skill 版本仍为 `DRAFT`，并且确有 HOLDOUT 样本；然后保存 Provider、模型、重复次数、代码版本的配置快照，调用 `_ensure_pairs()` 建立对照运行，候选转为 `EVALUATING`。实验本身也使用 owner、到期时间与 epoch 的租约，避免两个评测协调器同时发布或重复收集。

`run_once()` 不直接替模型回答题目，而是查找已终止但未判分的 EvalRun，逐个 `_validate_and_collect()`，再释放第二臂、标记配对可比性；全部运行有结果后才把实验置 `COMPLETED`。换言之，评测协调器管**实验进度与判据**，普通 Worker 仍执行实际 Agent Run。若某一臂模型配置、上下文、工具 manifest 或运行顺序发生差异，“两臂成功率”就不能被当成 Skill 的因果效应，需要在报告里标不可比或重新设计。

`MetricsCollector` 和 `QualityGate` 最后汇总成功、成本、耗时、错误与门槛，人工评审则核对机械指标看不见的无关修改和事实支持。旧版少量 6 对、12 对结果只能证明那几题上两臂表现接近，不能证明整体无收益。当前 M6/M7 的正式缺口仍在[当前状态](../当前状态.md)列明。

## 17. 用三个断点区分“有机制”和“有效果”

若要亲自审查一次 Skill 自进化链，先在 `SkillExtractionService.extract()` 落库前看 `source_trace_hash` 与候选内容哈希；再在 `ContextResolver.resolve()` 保存选择批次前看本 Run 选中的版本、工具兼容性和降级原因；最后在 `EvalCoordinator._validate_and_collect()` 看冻结样本实际是否通过。前两处最多证明**来源合格、选择正确**；第三处才开始提供效果数据。还需配对统计与人工审查，才能对“比没有 Skill 更好”作强结论。

## 18. 一条记忆从聊天到新 Run 的完整时序

设用户在 Session A 说“以后报告用中文”。来源消息先作为普通会话记录存在；记忆提议必须引用这条消息，候选内容也要在原文中逐字出现。`MemoryService.propose()` 创建 fact key 下的新版本，状态是 proposed；确认 API 调 `decide(..., action="confirm")` 后才把它设为 Entry 的 current version。索引维护稍后为可检索文本建立派生文档，但数据库中的 confirmed/source 记录始终是权威。

新建 Task T2 时，ContextResolver 只看 T2 的 Session/Workspace 作用域与创建时历史截止点，筛掉失效来源；被选中的 Memory 文本进入上下文并保存选择证据。用户若在 T2 运行中撤销这条记忆，新 Run 不应再选它；T2 在下一次请求前也需按来源有效性规则处理，而不能把已撤销版本继续当当前有效事实。注意这与“在 T2 完成的模型回答里把它引用成历史语句”不同：历史聊天本身不能被假装删除，权威记忆的复用才受确认/撤销约束。

读这段链时分别在 [memory/service.py](../../src/evoagent/memory/service.py)、[retrieval/sources.py](../../src/evoagent/retrieval/sources.py)、[runtime/context_resolver.py](../../src/evoagent/runtime/context_resolver.py) 找到来源验证、候选装入和选择落账。用 [test_memory_foundations.py](../../tests/integration/test_memory_foundations.py) 与 [test_hybrid_retrieval.py](../../tests/integration/test_hybrid_retrieval.py) 核对取消、作用域和降级情况。机械测试能证明数据不串号；它不能证明模型在每一篇报告里都正确遵守中文偏好。

## 19. 一条 Skill 从候选到运行时的完整时序

设通过 dev 轨迹提炼 `failing-test-fix-loop`。来源资格检查先证明每个 EvalRun 属于可提炼集合、Trace 可读且哈希固定；生成器输出的 DSL 要写清触发条件、读取失败信息、编辑时的前置条件、复测、停止条件与审批点。草稿版本有独立 `SkillVersionRecord`；QualityGate 和人工发布决定都针对**这个版本**，不是模糊的 Skill 名称。

发布后新 Task 的普通 Run 走 retrieval 模式，SkillRetrievalService 或 ContextResolver 按任务目标、工具兼容性和风险限制选择活动版本，并把选中版本 ID/哈希冻结进 Run。Provider 请求看见的是 SkillContextRenderer 渲染出的指导文本，模型仍可能不遵循；因此需在 Trace 中核对实际工具序列与结果。禁用或回滚后，**后来的 Run**应选新版/旧版或不选；既有 Run 的冻结选择不能被改写以美化实验。

对照 [test_skill_schema.py](../../tests/unit/test_skill_schema.py)、[test_skill_sourcing.py](../../tests/unit/test_skill_sourcing.py)、[test_skill_experiment.py](../../tests/unit/test_skill_experiment.py) 和 [test_skill_management_api.py](../../tests/integration/test_skill_management_api.py)，分别看 DSL、来源、实验隔离、人工状态变更。任何一个测试通过都不是整体收益结论：它们验证的是流水线的某一环。

## 20. 把配对结果写成能复核的四格表

配对评测可按每个样本的两个二值结果计数：

| 同一冻结任务 | Skill 成功 | Skill 失败 |
| --- | --- | --- |
| Baseline 成功 | 两臂都成功：难以辨别增益 | Skill 独失败：负向失配 |
| Baseline 失败 | Skill 独成功：正向失配 | 两臂都失败：难以辨别增益 |

若有 30 对，正向失配 4、负向失配 1，其余 25 对同结论，净成功率差是 3/30＝10 个百分点；但真正给配对检验提供信息的只有 5 对失配。不能用“30 对”三个字自动推断达到 80% 检出力。[skills/power.py](../../src/evoagent/skills/power.py) 用 dev 估计的失配率和目标效应反推所需 N；预算和独立 holdout 产能不足时应标探索性，并写本样本量能检出的最小效应。看过正式样本结果后修改 Skill，就需要新的未曝光样本；`evals/datasets/manifest.json` 与 [check_sample_ledger.py](../../scripts/check_sample_ledger.py) 用来防止显式复用。

这张四格表也提醒评审者先定义“成功”：对编程任务，可检查指定测试退出码与 diff，但还要有人看无关修改、是否遵守约束、解释是否准确；对资料任务，可机械检查引用 URL 来自已读正文，仍要人判断来源是否支持每条结论。若改变判分规则直到 Skill 臂更好，再算配对显著性，统计数值就失去预注册意义。

## 21. 逐字段读 `SkillDefinition`，理解它为何不是任意脚本

在 [skills/schema.py](../../src/evoagent/skills/schema.py)，`SkillDefinition` 包括名称、描述、触发词、输入定义、`preconditions`、步骤、停止条件、审批点、反例、成功标准和验证器。`InputDefinition` 限定基本类型，数组须写 item type，不能嵌套任意结构。`SkillPreconditions.allowed_tools` 与 `max_effective_risk` 指出运行这套方法所依赖的能力。步骤是带 `action` 判别字段的 `ToolStep` 或 `ModelStep`：前者声明某个工具与参数，后者给模型一段需完成的推理任务。`depends_on` 表达依赖，而不是让模型把每行 DSL 当可执行 Python。

M6 候选另外要求 `stop_conditions`、`approval_points`、`counterexamples`。例如“修复失败测试”若遇到用户未授权项目、命令结果未知或测试需要联网，应在适用条件或停止点里说明；不能因过去一次离线成功，就泛化为“任何仓库都按同一命令自动改”。Schema 本身还会检查审批点指向已有步骤、停止条件不重复。静态 Validator 再核对更深的语义与工具兼容性；即使全部通过，仍只是**结构上可审查**，不是运行时成功率。

跟读时留意版本哈希：候选定义的规范 JSON 算 content hash，Run 冻结选中版本的 ID 与内容哈希，QualityGate 再重算。这样“审核的是版本 A，发布时换成版本 B 的正文”会被发现。若发布后修正一个字，应新建版本和新的评测/审核链，而不是直接修改已发布版本的定义。

## 22. `QualityGate.evaluate()` 的检查顺序

[evals/gates.py](../../src/evoagent/evals/gates.py) 将每项检查记录为 `GateCheck(name, layer, passed, threshold, actual, evidence)`，最后生成带哈希的 `GateReport`。它先检查 Skill 定义仍满足静态契约、当前正文哈希等于登记哈希、实验配置哈希与 Dataset/Skill 绑定一致；然后检查独立来源数量、来源是否为已通过的 TRAIN Run，以及 Trace Artifact 是否可读且哈希相符。后续再检查实验运行与质量门槛。

这些步骤的先后体现一种证据逻辑：如果候选正文或实验配置已被改写，后面的成功率即使很好，也不能证明“我们当初冻结的那个版本更好”；如果来源来自 HOLDOUT，测出的效果会被训练污染；如果 Trace 文件损坏或不对应源 Run，就无法复核提炼依据。效率指标如 Token 和耗时可供人评估权衡，但正确性与安全属于硬门槛，不能用“更便宜”抵消越权或错误答案。

`GateReport.passed` 也不自动构成当前 M6 的统计显著收益。产品层的门禁检查一份实验是否符合其固定规则；当前计划对个人项目 Skill 还要求独立 holdout 规模、配对效应、盲评与第三方复核。源码手册既要解释门禁代码，也要说明它并未消除样本不足与人评偏差。

## 23. 本册的代码阅读与验证路线

可以把一次知识进化实验拆成五段，分别在代码和测试中定位：

| 阶段 | 从哪个函数/文件入手 | 应拿到的证据 |
| --- | --- | --- |
| 记忆产生 | `memory/service.py:propose/decide` | 原话消息、Version、Source、确认事件 |
| 检索装配 | `runtime/context_resolver.py:resolve` | 候选来源、Profile/代次、降级原因、冻结选择 |
| 候选提炼 | `skills/extraction.py:extract` | 合格 dev 来源、Trace 哈希、DRAFT 定义哈希 |
| 配对执行 | `evals/coordinator.py:create_experiment/run_once` | 冻结任务、两臂 Run、Validator 与可比性 |
| 发布决定 | `evals/gates.py:evaluate`、`skills/service.py:approve` | GateReport、人审理由、活动版本 |

若只是想验证 API 和数据不变量，可读 [test_memory_api.py](../../tests/integration/test_memory_api.py)、[test_hybrid_retrieval.py](../../tests/integration/test_hybrid_retrieval.py)、[test_eval_lifecycle.py](../../tests/integration/test_eval_lifecycle.py) 与 [test_skill_management_api.py](../../tests/integration/test_skill_management_api.py)。若要回答“它有没有给真实用户带来净收益”，这些测试远远不够；需要预注册任务、真实运行与人工审查。本册的目的就是让读者能指出**哪一层证据已经存在，哪一层还没有**。
