# 第二部分：执行内核与可靠性

[第一部分](01-系统全景与任务主线.md)沿一条任务走到 `AgentLoop`。这一册追问：为什么同一条工具调用在 Worker 重启后不会被随意重做？为什么浏览器刷新后还能看见原来的任务？答案不在单个“重试函数”里，而在**状态机、数据库事务、租约、检查点、审批和副作用账本**的配合中。

## 1. 分开两个运行时

[AgentRunner](../../src/evoagent/core/runner.py) 和 [AgentLoop](../../src/evoagent/core/loop.py) 是可注入 Provider、工具和事件出口的内核，CLI/离线测试也能使用。实际网页任务走 [PersistentAgentRunner](../../src/evoagent/runtime/persistent_runner.py)：它从数据库取 Task/Run，准备历史、项目上下文、Skill 与记忆，冻结运行配置，创建持久化事件和检查点，再调用同一个 Loop。这样核心循环不必理解 PostgreSQL 租约；持久化层也无需复制模型—工具逻辑。

一个循环迭代可以画成：

```text
读取未消费的用户补充要求
  → 构造模型请求与可用工具定义
  → 核对上下文预算及冻结来源
  → 模型给出完整回答或完整工具调用
  → 若有工具调用，先保存 assistant 决定
  → 校验参数、授权、审批与效果身份
  → 执行并保存结果
  → 继续下一轮；或返回最终回答
```

内核的 [Message / ToolCall / ToolResult / LoopState 契约](../../src/evoagent/core/models.py) 把每一步的数据形状固定下来。工具调用是结构化的名字、参数和 call ID，不能把模型输出的一段自然语言当成已经执行的命令。

## 2. 创建、领取、完成：数据库才决定状态

[TaskService](../../src/evoagent/tasks/service.py) 把 Task、首个 Run、goal 消息和入队事件一次提交。[JobWorker](../../src/evoagent/workers/main.py) 从 [JobLeaseManager](../../src/evoagent/tasks/lease.py) 领取工作；[状态机](../../src/evoagent/tasks/state_machine.py) 只允许显式列出的转换。常见状态并非简单的“运行/完成”二元组：`queued`、`running`、`waiting_user`、`retrying`、`recovering`、`completed`、`failed`、`cancelled` 等各有可进入和可退出的边。

Task 与 Run 的状态也不是同一个枚举。Run 还可终止为 `timeout`、`limit_reached`、`authorization_revoked`、`input_changed`；用户页面应显示能解释的最终原因。排队的下一条任务和运行中补充要求是两种不同操作：前者创建新的 Task，后者写入当前 Task 的持久化指令，并只在下一次 Loop 迭代边界进入模型上下文。

同一 Session 的历史有“创建时截止点”。[history_for_task](../../src/evoagent/sessions/service.py) 只能装入当时已存在且符合规则的历史；后来的消息不会倒灌到较早创建的 Task。评测 Run 使用独立历史入口，避免普通会话污染冻结样本。

## 3. 租约与 epoch：防止旧 Worker 回来写

多个 Worker 可竞争数据库队列。领取时租约给出 owner、到期时间和 epoch；[LeaseGuard](../../src/evoagent/tasks/lease_guard.py) 在写入事件、快照、效果、终态等执行事实前复查这三个条件。若 Worker A 停顿并失去租约，Worker B 领走任务，即使 A 后来恢复运行，它持有的旧 epoch 也不能继续提交事实。

Redis 的 [Wakeup](../../src/evoagent/workers/wakeup.py) 只是加速提醒；[Presence](../../src/evoagent/workers/presence.py) 为页面提供带有效期的在线信号；[ServiceGate](../../src/evoagent/workers/rate_limit.py) 管服务配额。它们不替代 PostgreSQL 的 Task、Run 和 Lease。`worker_status=ready` 也不能证明远端模型可用——只有实际请求能验证连通性。

读代码时注意一种竞态：A 完成工具后、写结果前失租。只检查“开始时有租约”不够，写事实的事务也要检查。另一个竞态是 A 失租后仍在执行外部命令；epoch 能拒绝它的数据库写入，却不能把已经发生的外部动作倒转。后者交给副作用账本处理。

## 4. 快照记录可恢复的决定

[PersistentCheckpointStore](../../src/evoagent/runtime/checkpoints.py) 保存 LoopState；它包含消息、已完成轮次、usage、重复调用指纹及配置哈希。恢复时先检查快照 schema 与运行配置是否兼容；[RunConfigSnapshot](../../src/evoagent/runtime/run_config.py) 绑定 Provider、模型、工具 manifest、权限策略、上下文策略、选中的 Skill 等，避免恢复时悄悄采用“现在的设置”。不兼容就明确失败，而不是生成一个看似继续、实际条件已变的新运行。

模型可能已经输出工具调用，Worker 在工具执行前退出。如果重启后重新问模型，它可能给出另一个 call ID 或略有不同的参数。[AgentLoop](../../src/evoagent/core/loop.py) 因此只在**完整模型响应**形成后保存 assistant 消息与 ToolCall；恢复时执行这份决定。半截流不能作为可执行工具调用。模型决定可重放，并不意味着工具副作用可重放，两者下一节分开判断。

上下文还有另一种恢复问题：长会话要裁剪或压缩。[ContextPolicy](../../src/evoagent/core/context_policy.py) 根据 [TokenCounter 与预算](../../src/evoagent/core/context_budget.py) 处理可丢内容；[ContextStore](../../src/evoagent/runtime/context_store.py) 保存可恢复的上下文修订和完整输出归档。受保护内容放不下时应拒绝请求；不能以偷偷删掉用户约束换取“模型调用成功”。Token 估算仍是估算，真实窗口必须按模型配置。

## 5. 工具执行不是一次函数调用

[ToolRegistry](../../src/evoagent/tools/registry.py) 决定模型在本 Run 中**看得见**哪些工具；[ToolExecutor](../../src/evoagent/tools/executor.py) 负责参数解析、运行限制、结果转换。持久化任务还经过 [PersistentToolMiddleware](../../src/evoagent/tools/effects.py)：每次调用先复查项目授权和冻结输入，再根据 [PermissionPolicy](../../src/evoagent/tools/policy.py) 决定拒绝、放行或等待审批，最后维护 ToolCall/ToolEffect 账本。

这个顺序很关键。Task 创建时可以冻结项目版本，但用户之后可能撤销；因此“冻结版本”必须与当前版本在**每次工具执行前**比较。若输入文件在任务中途改变，`input_changed` 明确终止，不拿另一份文件继续当原任务。命令、编辑等不同风险的工具还要经过各自参数检查；模型写“我已获准”没有效力。

待审批调用创建 Approval 记录并发出 `approval.required` 事件；[ApprovalService](../../src/evoagent/tools/approvals.py) 在用户决定时再次核对状态。审批决定有具体调用及绑定，不能由页面乐观地改变成“已执行”。对于同一任务中语义相同、可安全复用审批的工具，可以按工具和规范化参数找回决定；`run_command` 等不能简单按相同 argv 合并两次调用，否则“失败后用相同命令复测”会被误判为第一次结果。

### 5.1 ToolEffect 的三个重要状态

| 状态 | 已知事实 | 恢复时处理 |
| --- | --- | --- |
| 尚未执行 | 没有已开始的效果记录 | 经过当前授权与审批后可执行 |
| `COMMITTED` | 效果及结果已确认并落账 | 返回已保存结果，不重复写入 |
| `EXECUTING` / `UNKNOWN` | 可能已经作用于外部环境，结果尚不能证明 | 标为未知、等待人核对；不能自动重放 |

`UNKNOWN` 的正确问题是“外部到底发生了什么”，不是“模型还想不想重试”。用户核对文件或外部系统后，可按协议一次性确认 `committed:<结果>` 或在确认未生效时给出 `retry`。这解释了为何可靠性不能只靠 try/except：数据库事务无法回滚已经发出的外部命令。[RecoveryService](../../src/evoagent/runtime/recovery.py) 和工具账本一起约束这类决策。

## 6. 重试、预算与验收是三道不同的关

[RetryPolicy](../../src/evoagent/runtime/retry.py) 区分瞬时依赖故障与永久错误，限制尝试次数、退避和总耗时；Redis 不可用等 `dependency_unavailable` 会按可重试基础设施错误处理。命令执行已经产生不确定外部副作用时，重试策略还必须服从 ToolEffect 状态，不能为了“提高成功率”绕过未知结果。

[预算模块](../../src/evoagent/runtime/budget.py) 在付费模型调用前核对试跑/正式 scope、总额、单 Task 限额、价格和停止阈值；[BudgetedProvider](../../src/evoagent/workers/rate_limit.py) 为真实模型包装用量记录。预算拒绝是 `budget_exceeded`，与 Provider 限流、Redis 不可用是不同的原因。模型流异常后的已知 usage 也应尽量记账。Mock 不产生付费请求，因此不经过同一付费闸门。

最后的 [AcceptanceSpec](../../src/evoagent/tasks/acceptance.py) 可核对回答片段、成功工具和文件/哈希。它是**机械验收**：若设置“答复包含 391”，通过仅说明出现了 391，不说明推导正确；若没有条件，`completed` 只表示运行终止且有最终答复。开放目标、引用支持度和 Skill 收益仍需独立评测与人评，见[第四部分](04-知识进化与质量验证.md)。

## 7. 页面时间线为什么可信

运行时把重要转折写为事件。[PersistentEventSink](../../src/evoagent/trace/persistent_sink.py) 与 [TraceBundle](../../src/evoagent/trace/bundle.py) 让后台结果能够被查询；[SSE](../../src/evoagent/trace/sse.py) 向浏览器提供已提交事件。前端 [taskEvents](../../frontend/src/api/taskEvents.ts) 按事件游标续传和去重，[progress](../../frontend/src/pages/progress.ts) 将事件翻译成可读步骤。刷新后页面重新查询服务端事实，不依赖刷新前的进度条。

已提交事件流不是逐字模型输出；服务端报告 `completed` 不代表人工事实审查通过。页面应能同时展示“任务已完成”和“未配置独立验收”，避免把状态机正确误写成任务内容正确。

## 8. 用同一条失败测试观察两份账

假设模型调用 `run_command`，参数为 `python -m pytest -q`。命令返回退出码 1；模型据此调用 `edit_file`；随后又调用**同样参数**的 `run_command`，退出码变为 0。读这段轨迹时需要分开两份记录：

| 记录 | 回答的问题 | 第一次测试 | 第二次测试 |
| --- | --- | --- | --- |
| ToolCall | 模型本轮究竟提出了什么？ | 一条独立 call ID 和参数 | 另一条独立 call ID，参数可相同 |
| ToolEffect | 可能改变外部世界的动作发生了吗？ | 归于第一次调用 | 命令的去重身份含 call ID，不能借第一次结果 |
| ToolResult | Agent 应观察到什么？ | 退出码 1、stdout/stderr | 退出码 0、stdout/stderr |
| Run Event | 用户何时能看到状态？ | 提交后的调用/结果事件 | 提交后的第二组事件 |

把 ToolCall 和 ToolEffect 合成一张“缓存表”会产生严重错误：相同命令在不同时间执行可以给出不同结果。相反，对同一次调用的**恢复**又必须避免重复执行。`PersistentToolMiddleware.before()` 按工具是否有副作用、是否允许按规范参数去重、当前效果状态作决定；`after_success()` 才把可确认结果提交。读这两个函数时应区分“用户再次要求运行”与“Worker 重新尝试同一次运行”。

模型收到的是结构化 ToolResult，而不是网页上的绿色或红色图标。`run_command` 的退出码 1 表示测试失败的**有用观察**；若把它抛成“基础设施异常”交给通用重试，模型就看不到断言和堆栈，也无法决定修哪里。

## 9. 把四个崩溃点放到时间轴上

```text
模型完成工具决定 ── A ── 写检查点 ── B ── 记录 EXECUTING ── C ── 执行外部动作 ── D ── 记录 COMMITTED
```

- **A：决定尚未持久化。** 恢复后没有一条可信的完整 ToolCall；可能需要重新向模型请求。半截流绝不能当成已决定的命令。
- **B：决定已冻结，动作未开始。** 恢复直接使用检查点里的 ToolCall，不再请模型重新掷骰子；仍须复查当前授权、输入和审批。
- **C：账本写了 `EXECUTING`，但动作未必开始。** 没有外部完成证明，恢复把它视为 `UNKNOWN`，即使人猜测“可能没执行”也不能自动重放。
- **D：外部动作可能成功，账本还未提交。** 这是真正的“结果不明”窗口。数据库不可能与任意文件系统、命令或 MCP 服务组成一个原子事务，必须要求人对照外部事实结清。

这套设计提供的是**可说明的执行语义**，不是对整个外部世界的数学意义“恰好一次”。`COMMITTED` 可以跳过重复效果；`UNKNOWN` 明确保留不确定性。若用户确认已生效，就登记结果；若确认未生效，才可给一次 `retry`。把“未知”直接当失败并自动重试，容易重复付款、重复移动文件或重复发布。

## 10. 状态、原因和页面文案不能压成一个布尔值

一个任务至少有三层可观察结论：

1. **生命周期**：Task/Run 是排队、运行、等人、重试、完成还是终止。这由状态机与事务决定。
2. **终止原因**：失败可能是模型错误、预算超限、项目授权撤销、输入变化、用户取消、超时或工具的未知效果。这些原因决定能否自动重试、应让用户做什么。
3. **目标质量**：测试命令退出 0、文件哈希匹配、引用支持结论，分别由不同证据判定。生命周期 `completed` 不能替代质量判断。

例如用户撤销项目授权，先前已经完成的读取仍保留在 Trace；下一次工具调用的版本核对失败并写入拒绝事件。页面不能将其泛化为“模型失败，点击重试”，因为重试无法恢复授权。又如预算用尽发生在新模型请求前，已有工具效果不应消失；`budget_exceeded` 应与模型响应错误区分。读前端 `progress.ts` 时，可拿这些例子核对它是否仅在展示，还是误将文案当成后端事实。

## 11. 带着不变量找测试

源码的关键不变量可以变成具体测试问题：

| 不变量 | 最小故障注入 | 应看到的结果 |
| --- | --- | --- |
| 旧 Worker 不能提交事实 | A 失租、B 领取后 A 继续写 | A 被 epoch 拒绝；B 的记录不被覆盖 |
| 冻结决定不重问模型 | 在完整 ToolCall 检查点后杀 Worker | 恢复使用同一参数与 call ID |
| 未知效果不自动重做 | 在外部动作与结果落账之间杀 Worker | 进入人工结清，不产生第二次效果 |
| 补充要求不篡改既有动作 | 命令等待审批时追加要求 | 现有审批绑定不变；下一迭代才注入 |
| 刷新不丢执行历史 | SSE 断线后重新连接 | 根据事件 ID 续传，终态另行查询 |

测试目录里有内核单测、持久化任务与 Worker 恢复用例；先从被测函数名反查测试，避免只看某一个“全量 passed”数字。Mock 适合验证状态与故障时序；真实 Provider 和真实项目还需单独记录调用成本与任务质量。

## 12. 用故障时序检验理解

试着回答三个问题，并沿代码找证据：

1. Worker 在模型输出 `apply_patch` 后、工具开始前被杀：恢复从哪里取原 ToolCall？为什么不再问一次模型？
2. Worker 在项目文件写入后、账本提交前被杀：为什么状态可能是 `UNKNOWN`？用户要核对哪两个事实？
3. 同一条 `python -m pytest -q` 第一次退出 1，修代码后第二次退出 0：为什么两次调用的 ToolEffect 身份必须不同？

这些答案决定你能否理解系统的可靠性边界。接下来[第三部分](03-工具项目与安全边界.md)沿同一条任务检查实际文件、命令、网络和产物。

## 13. 源码精读：两个状态机并不是重复设计

打开 [tasks/state_machine.py](../../src/evoagent/tasks/state_machine.py)。`TaskStatus` 包括 `CREATED/QUEUED/RUNNING/WAITING_TOOL/WAITING_USER/RETRYING/PAUSED/RECOVERING` 与三种终态；`PersistentRunStatus` 没有 `CREATED/WAITING_TOOL`，却有 `TIMEOUT/LIMIT_REACHED/AUTHORIZATION_REVOKED/INPUT_CHANGED`。Task 表达用户目标在队列中的总体命运，Run 表达某次执行怎样结束。状态机把这层区别写成 `_TASK_TRANSITIONS` 和 `_RUN_TRANSITIONS`，再由 `ensure_task_transition()`、`ensure_run_transition()` 拒绝非法跳转。

例如 Run 以 `AUTHORIZATION_REVOKED` 终止时，Task 映射为 `CANCELLED`；Run 因 `INPUT_CHANGED` 终止，Task 映射为 `FAILED`。映射表在 [tasks/lease.py](../../src/evoagent/tasks/lease.py) 的 `_RUN_TO_TASK_TERMINAL`，不是前端随意翻译。Task 的 `WAITING_USER → QUEUED` 表示用户做出审批/答复后重新排队，让 Worker 重新领取；并非暂停中的旧 Python 协程在浏览器点击时直接恢复。研究“批准以后为什么还在等待”时，应同时检查 Approval 记录、Task 状态迁移和 Worker 领取。

状态机还让终态不可逆：`COMPLETED`、`FAILED`、`CANCELLED` 的后继集合为空。模型事后的一条晚到结果不能把已取消任务重新标成完成。但终态不可逆不等于外部副作用可撤回——一个已经启动的命令可能仍要在外部核对。

## 14. 源码精读：领取任务的 SQL 解决了哪些并发问题

`JobLeaseManager.claim_next()` 的查询并非普通 `SELECT LIMIT 1`。在 [tasks/lease.py](../../src/evoagent/tasks/lease.py) 中逐项看 `where`：只领取 `QUEUED`；重试时间已到；旧租约不存在或过期；普通任务与 Runtime Eval 的执行通道分开；同一 Session 中序号更早的任务若未终止，后继任务不能被领取。最后 `ORDER BY created_at, id`，用 `FOR UPDATE SKIP LOCKED` 让多个 Worker 并发争抢时跳过别人已锁住的行。

成功领取后同一事务里更新 Task/Run 状态、owner、到期时间、心跳、`lease_epoch` 和 `lock_version`，写 `worker.claimed` 事件，再提交并返回 `JobLease(task_id, run_id, owner, expires_at, attempt, epoch)`。这里 `epoch` 每次领取递增，是对老 Worker 的隔离栅栏；`attempt_count` 不因特定基础设施重试码消耗一次普通任务尝试。`heartbeat()` 先用 [LeaseGuard](../../src/evoagent/tasks/lease_guard.py) 验证同一 owner/epoch 与有效期，再延长租约。数据库时间用于比较，避免两台机器时钟偏差主导资格判断。

```text
Worker A 锁住候选 Task → 提交 lease(epoch=7) → 执行
                   A 暂停太久，租约到期
Worker B 领取同一 Task → 提交 lease(epoch=8) → 执行
A 恢复，带 epoch=7 写快照/效果/终态 → LeaseGuard 拒绝
```

这阻止旧 Worker **写数据库事实**，不是跨操作系统撤销 A 已经发出的外部效果。源码中需要 LeaseGuard 的地方不仅是最终 `complete()`，还包括事件、快照、效果和产物登记等写入路径。只在 Worker 开始时查一次租约会留下竞态。

## 15. 源码精读：`PersistentAgentRunner._handle_owned()` 的装配顺序

[persistent_runner.py](../../src/evoagent/runtime/persistent_runner.py) 的 `_handle_owned()` 是阅读网页任务的核心。它先以当前 Lease 加载 Task/Run 并检查 Run 所引用的记忆/Skill 等来源仍有效，再决定走普通 Skill 检索还是 `ContextResolver`。所得选择构成 `skill_context` 与哈希；随后创建 `RunConfigSnapshot`，记录 Provider、模型、提示词哈希、工具 manifest、权限策略、模型超时、上下文策略、选择的 Skill 版本等。`_persist_run_config()` 防止恢复后悄悄换一套条件。

然后创建 `PersistentEventSink` 和 `PersistentCheckpointStore`，尝试 `load_latest()`：

| 有无快照 | 初始消息怎样来 | 对恢复语义的影响 |
| --- | --- | --- |
| 无 | ContextBuilder 生成系统/当前目标消息，再按 Run 类型装入冻结历史 | 首次运行，有完整历史装配过程 |
| 有 | 直接从 `resume_state.messages` 继续，发 `recovery.completed` | 不重选另一段会话历史或另问模型已作的决定 |

接着 Runner 创建 `ToolExecutor`，同时装入 ServiceGate、租约检查、`ToolOutputStore` 和 `PersistentToolMiddleware`，再把 Provider、Registry、ContextStore、CheckpointWriter、运行中指令读取器交给 AgentLoop。审批要求被捕获并映射成 `WAITING_USER`；授权撤销和输入变化保留独立终态；普通 Loop 完成后才进入最终结果与机械验收处理。这个函数长，按上述装配段读比逐行背参数更容易看懂依赖关系。

## 16. 源码精读：快照的保存为什么必须与事件同事务

在 [runtime/checkpoints.py](../../src/evoagent/runtime/checkpoints.py)，`PersistentCheckpointStore.save()` 先用 LeaseGuard 和来源有效性检查，再写 `snapshot.saved` 事件，使用**该事件序号**创建 `RunSnapshotRecord`，最后一次 `unit.commit()`。如果先写事件后写快照分两次提交，页面可能声称“已保存”而恢复却找不到状态；反过来若只有快照没有事件，Trace 也无法解释运行前进到哪一步。

`load_latest()` 检查数据库快照版本等于当前期望版本，用 `LoopState.model_validate()` 检查正文结构；若快照引用的 ContextRevision 已不存在、属于别的 Run 或已擦除，则抛 `SnapshotCompatibilityError`。这不是普通可重试模型错误：恢复所依赖的旧条件已失效，应明确终止并让人处理。`AgentLoop` 还比较自己的配置哈希，防止相同快照被新的模型/工具环境解释出不同效果。

最重要的两个保存点在 [core/loop.py](../../src/evoagent/core/loop.py)：模型给出完整 ToolCall **后、执行前**保存 assistant 决定；工具结果加入消息后保存该轮完成状态。若在两点之间强杀，恢复会看到 assistant 消息末尾的 ToolCall，并先执行冻结的调用；若在第二点之后强杀，则从下一迭代继续。这个分界决定了第二次模型请求是否发生。

## 17. 源码精读：ToolExecutor 和效果中间件各管什么

在 [tools/executor.py](../../src/evoagent/tools/executor.py)，`execute()` 先按工具绑定处理服务配额和租约检查；`_execute()` 发 `tool.started`，从 Registry 取工具、验证参数、运行工具预检，调用可选中间件的 `before()`，再用 `asyncio.wait_for()` 执行。工具返回必须是字符串；过长结果由 OutputStore 保留全文并给模型截断版，必要时发来源事件。成功调用 `after_success()`，可恢复失败调用 `after_failure()`，再形成 ToolResult 与事件。只读安全工具可以并发，其他调用按原始顺序执行，避免两个写入工具竞争同一目录。

在 [tools/effects.py](../../src/evoagent/tools/effects.py)，`PersistentToolMiddleware.before()` 更关注**执行资格与副作用身份**：先复查项目授权及冻结输入，再由 PermissionPolicy 判断放行、拒绝或审批；在事务中写/找 ToolCall 和 Approval；有副作用时计算语义键，查看既有 ToolEffect。若 `COMMITTED`，复用已记结果；若 `EXECUTING/UNKNOWN`，转人工结清；否则标 `EXECUTING` 并交给 Executor 真正运行。`after_success()` 再落已确认结果。看这两个文件，应把“调用流程”和“恢复事实”分成两层理解。

尤其注意 `tool.dedupe_by_arguments`。部分工具可按规范参数复用审批或效果；`run_command` 明确设为 `False`，它的效果身份包含 call ID。同一命令在修复前后得到不同结果是正常工作流程，不能被“可靠性去重”误伤。

## 18. 源码精读：错误到底交给谁重试

`ProviderError`、工具错误、LeaseLost、取消和未知效果并不走同一个 `except`。Loop 将基础设施限流/依赖不可用的完整迭代先写检查点，再带错误码返回；[runtime/retry.py](../../src/evoagent/runtime/retry.py) 根据错误类型与次数决定重新排队。`budget_exceeded` 是停止原因，不是暂时再试一次会变好的服务限流。LeaseLost 意味着当前 Worker 已无资格，需要让新的 owner 接手；UNKNOWN 意味着**外部结果不明**，在此之前任何自动重试都可能重复动作。

读错误处理时沿四条线追踪：错误在哪一层被捕获、写了哪个事件、Run/Task 变成什么状态、用户需要做什么。只核对 HTTP 是否返回 200 或测试是否“passed”，很容易忽略实际任务被错误地继续、跳过或重新执行。

## 19. 一条 Task 从数据库到页面的逐字段对照

回到 [db/models.py](../../src/evoagent/db/models.py)。`TaskRecord` 的 `status` 是用户目标级状态，`cancel_requested` 允许控制请求先落库再由执行者看见；`lease_epoch` 解决所有权转移；`lock_version` 解决并发修改；`history_before_sequence` 和 `frozen_inputs` 冻结条件。`RunRecord` 的 `status`、`config_snapshot/config_hash`、`final_answer/error_code`、`next_event_sequence` 则属于一次执行。把 Task 与 Run 的列并排读，能看到数据库不是“为了加日志而加日志”，而是把运行边界具体化为可查询事实。

前端刷新时，先经 `GET /tasks/{id}` 得到 TaskResponse 与 latest Run，再接 SSE 事件游标。假设浏览器断线期间发生三件事：工具被批准、Worker 恢复、Run 失败。重新连接后，`taskEvents.ts` 会从上次事件 ID 续读已提交事件，终态通过 Task API 补查。它不能只重放浏览器内存的“工具进行中”动画；数据库事件有 Run ID 和序号，才能判断漏了哪一步。反过来事件流本身也不替代 Task/Run 终态表，因为连接可能在最后一条事件前断开。

## 20. 机械验收的源码边界

[tasks/acceptance.py](../../src/evoagent/tasks/acceptance.py) 的 `AcceptanceSpec` 只支持明确条件：`answer_contains`、`required_tools`、`required_files`。创建请求校验数量与相对路径格式，空条件不算合法验收。`check_acceptance()` 对回答做不区分大小写的片段检查；对工具查询本 Run **成功状态**的 ToolCall；对文件在 `artifact_root / run_id` 下核对存在、大小和可选 SHA-256。最后用 `all(checks)` 得到通过与逐项结果。

这个实现带来容易忽略的限制：`required_files` 查的是 **Run 产物根**，不是用户项目工作树；若用户只让 Agent 编辑 `src/foo.py`，把它写成 required_files 条件并不能证明项目编辑。`required_tools=["run_command"]` 只证明至少有该工具成功调用，不证明测试命令退出码为 0；必须进一步检查结构化 ToolResult、退出码和目标文件状态。`answer_contains=["已修复"]` 更只证明出现这几个字。源码手册要把这些判据说透，避免把便利检查误用成开放目标验收。

## 22. 审批恢复的一次事务

`PersistentToolMiddleware.before()` 认为一次调用需要用户决定时，保存 ToolCall/Approval，提交 `approval.required` 事件并抛 `ApprovalRequiredError`。`PersistentAgentRunner` 将它映射成 Run 的 `WAITING_USER`，Worker 释放执行位置。此时页面的按钮不是“继续当前函数”，而是调用 [ApprovalService.decide()](../../src/evoagent/tools/approvals.py) 写一笔新事务。

这个事务先锁定 Task、最新 Run 与 Approval，确保待决审批存在且任务未终止。对于 MCP 工具还核对冻结的执行绑定；对于 `ask_user`，批准时必须携带用户回答；对于 UNKNOWN 效果，只允许 `retry` 或 `committed:<结果>` 这类明确结清语义，不能用一个模糊的“同意”。批准/拒绝后，若任务再无其他待决审批，`WAITING_USER` 才会变成 `QUEUED`；服务追加 `approval.decided` 事件，提交后由 Worker 重新领取。

这个过程有意保留一个检查点：用户点击批准与 Worker 真正执行之间，项目可能被撤销、输入可能改变、MCP 绑定可能失效。批准不授予永久、无条件的执行能力，重新进入中间件时仍要核对当下事实。反过来，若任务已经终止，晚到的批准不能把它复活；`decide()` 会拒绝终态任务。

## 23. 预算与服务配额的先后关系

在 [workers/bootstrap.py](../../src/evoagent/workers/bootstrap.py) 的真实 Provider 路径，底层 Provider 先被 `GatedProvider` 包装，随后被 `BudgetedProvider` 包装；Mock 不经付费预算闸门。前者负责服务并发/配额和租约核对，后者负责试跑或正式 scope 的费用账本与总额。`EVOAGENT_BUDGET_SCOPE` 的 `trial` 与 `formal` 不是 UI 主题，而是费用统计与闸门的独立范围。

模型请求有三个不同的“停止”可能：上下文预算在 Provider 之前判断请求放不下；费用预算在发起付费调用前拒绝超额；Provider 真正发出请求后仍可能限流、断网或流中断。它们应留下不同的错误码、事件和已知 usage。若费用预算拒绝，不能因“网络没调用”就把它当成模型没有回答；若模型流中断但已有 usage，账本也应尽量记录已知花费，避免只统计成功请求。

这个区分对调试很实用：看到 `context.rejected`，去查 ContextPolicy 与窗口配置；看到 `budget_exceeded`，去查试跑/正式额度、单任务限额和价格；看到 `rate_limited` 或 `dependency_unavailable`，去查服务商/Redis 与重试策略。把三者统一显示为“模型不可用”，会让用户错误地反复重试并消耗更多钱。

## 24. 代码实验：同一操作在三个崩溃窗口的恢复

可以用“在项目里新建 `notes.txt`”设计一次可重复故障实验。准备一个空的临时 Git 项目，固定 ToolCall 的 `call_id`、路径、内容与 Run ID。每次从同一初始状态开始，分别在以下位置强杀 Worker，并记录数据库与文件系统：

| 强杀位置 | 检查点 | ToolEffect | 文件 | 恢复后的合理行为 |
| --- | --- | --- | --- | --- |
| 模型响应完成前 | 无完整工具决定 | 无 | 无 | 可重新请求模型，不得执行半截参数 |
| 完整 ToolCall 已保存、效果未开始 | 有 assistant 决定 | 无 | 无 | 用原 ToolCall，经当前授权后执行 |
| 效果标 `EXECUTING`、文件可能落盘 | 有 assistant 决定 | `EXECUTING`/`UNKNOWN` | 有或无 | 停止自动重放，让人核对实际文件 |
| 结果已记 `COMMITTED`、本轮快照未保存 | 有 assistant 决定 | `COMMITTED` | 有 | 复用结果，补齐工具消息/检查点 |

第三行最考验设计：文件**不存在**也不能单凭一次 `Path.exists()` 就立刻认定“可以重试”，因为外部动作可能写到别处、写了一半、或产生了网络副作用。对 `notes.txt` 这种可核对文件，人能结合目标哈希确认是否已生效；对任意命令或 MCP 调用，往往需要外部日志。代码里的 `retry` 是一次性授权，不是默认自动循环。

结合 [test_lease_fencing.py](../../tests/integration/test_lease_fencing.py) 和 [test_project_edit_ledger.py](../../tests/integration/test_project_edit_ledger.py) 读，可以把“旧 Worker 不能写账本”和“未知外部效果不重做”区分开：前者由 epoch 与数据库事务解决，后者靠 ToolEffect 和人工结清。两者缺一都会使恢复语义不可信。

## 25. 一张操作表贯通 Task、Run、Lease 和事件

| 用户或系统动作 | Task/Run 变化 | Lease 变化 | 应留下的证据 |
| --- | --- | --- | --- |
| 用户提交目标 | `QUEUED/QUEUED` | 无 | goal 消息、`task.queued` |
| Worker 领取 | `RUNNING/RUNNING` | owner、到期、epoch 更新 | `worker.claimed` |
| 工具需人批准 | `WAITING_USER/WAITING_USER` | 当前执行停下 | ToolCall、Approval、`approval.required` |
| 人批准且无其他待决项 | `QUEUED/QUEUED` | 等新领取 | `approval.decided` 与决定内容 |
| 可重试依赖错误 | `RETRYING` 后重排队 | 旧租约结束 | 错误码、下一次尝试时间 |
| 模型给最终答复 | `COMPLETED/COMPLETED` 或验收失败终态 | 释放 | Run 答复、事件、验收逐项结果 |

这张表是阅读导航，不代替 [state_machine.py](../../src/evoagent/tasks/state_machine.py) 中完整合法边集合；例如取消、暂停、授权撤销和输入变化有各自分支。遇到实际状态与表不符，先用 Task/Run ID 查数据库，再按 Run 事件序号找最后一条已提交事实，而不是猜测前端是否缓存了旧数据。
