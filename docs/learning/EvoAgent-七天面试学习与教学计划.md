# EvoAgent 七天面试学习计划

> 作为学生的学习指导与教师的教学指导。以当前项目的实际实现为依据，覆盖系统全貌，重点深入核心设计。每天暂按 3～4 小时安排，根据实际掌握情况调整。

## 一、学习目标

七天后，能够独立介绍项目、画出整体架构、讲清任务执行过程，解释关键设计的原理、取舍与故障处理，并应对连续追问。

不以读完全部源码为目标，也不局限于简历上的内容。学习深度分为三层：

- **全局理解**：知道主要模块解决什么问题、彼此如何配合。
- **核心深入**：讲透执行循环、任务恢复、权限与副作用、Skill 评测。
- **面试表达**：用自己的话解释实现、设计理由、证据与限制。

## 二、七天总体安排

| 时间 | 学习主题 | 重点内容 | 学习成果 |
| --- | --- | --- | --- |
| 第一天 | 项目定位与整体架构 | 使用场景、能力边界；前端、API、数据库、Redis、Worker 的职责；Session、Task、Run 等核心对象；一条任务的完整链路 | 能画架构图，用两分钟介绍项目 |
| 第二天 | Agent 执行内核 | 模型—工具循环、Provider、ToolRegistry、工具执行、流式响应、预算与停止条件 | 能写循环伪代码，解释模型和宿主程序的分工 |
| 第三天 | 持久化与故障恢复 | 任务状态机、数据库事务、任务领取、Lease、心跳、epoch、检查点与分类重试 | 能推演多 Worker 竞争、进程崩溃与接管恢复 |
| 第四天 | 工具执行与安全 | 项目授权、文件读写、命令执行、审批、副作用账本、不同运行模式的隔离边界 | 能解释越权防护，以及外部动作结果未知时如何处理 |
| 第五天 | 上下文、记忆与检索 | 上下文预算与压缩、记忆提取与撤销、混合检索、Skill 检索；概览 MCP 接入 | 能区分上下文、记忆和 Skill，说明信息如何进入任务 |
| 第六天 | Skill 评测与工程验证 | Skill 提炼、配对评测、留出集、质量门禁、发布回滚；事件追踪、SSE、部署与排障概览 | 能解释如何验证效果，区分已实现、已验证与尚未验证 |
| 第七天 | 整合与模拟面试 | 项目介绍、核心难点、方案取舍、故障推演、扩展问题；查漏补缺 | 形成项目讲述稿与重点问答，完成两轮模拟面试 |

前端细节、全部工具实现和历史迁移不平均投入时间，按理解主线或面试追问的需要补读。

## 三、学习与教学方法

**最高原则：让学生真正明白。** 例子是教学的主要手段，不是讲完抽象概念后的附加内容。不设置分数、排名或过关压力；复述与追问只用于发现理解卡点，并帮助教师改进讲法。七天安排服务于理解，不能为赶进度而跳过必要解释。

每个主题按同一流程推进：

**具体场景 → 原理讲解 → 关键源码 → 故障推演 → 闭卷复述 → 面试追问。**

### 1. 先理解问题，再理解实现

围绕“读取项目、运行测试、修复代码、复测并交付结果”这一场景串联知识。先回答为什么需要某个模块，再解释它如何实现，避免只记术语和类名。

每个重要概念先给一个足够具体的小例子，写清谁在做什么、先后发生什么、数据或状态怎么变化，再从例子中提炼原理。必要时用生活类比建立直觉，但要说明类比的边界，最后回到真实代码。

例如讲租约时，先演示“Worker A 领取任务后卡住，租约过期，Worker B 接管，随后 A 又恢复”的完整过程，再解释心跳和 epoch 为什么需要；讲副作用时，先演示“文件已经改了，数据库还没记成功，进程就退出”，再讲为什么不能直接重试。

同一知识点可以用“没有这个机制会怎样 / 加上之后怎样”、正常与失败、两个容易混淆的方案做对比。学生没明白时，教师应换例子、拆小步骤或画图，而不是重复术语或要求背结论。

### 2. 按问题读源码

以源码地图和现有手册为导航，只跟读当课的关键入口、状态变化和异常分支，结合相关测试理解行为。教师负责核对当前实现，不要求学生预先通读代码。

### 3. 正常流程与失败流程一起学

每个核心机制至少分析一个失败场景，例如 Worker 崩溃、租约过期、工具执行后落库失败。通过改变条件检验理解，而不只记住正常调用顺序。

### 4. 用复述代替被动阅读

每学完一个模块，学生关掉资料，用自己的话说明：

- 它解决什么问题？
- 当前项目怎么做？
- 为什么这么设计，有什么代价？
- 出错时怎么办，有什么限制？
- 有什么代码、测试或运行证据？

教师先听回答，再纠错和追问；不能以“已经讲过”代替“学生已经掌握”。这里不是考试，不打分；学生也可以边画图边解释、用自己的例子回答。发现卡点后回到具体例子继续讲，直到能理解因果关系。

### 5. 每天回顾，及时补缺

每天开始先复述前一天的重点，结束时记录已经掌握和仍然卡住的内容。理解不足时换例子、补基础、重画流程；优先保证核心内容，压缩拓展内容，不盲目赶进度。

## 四、教学分工

**教师负责**：主动组织课程，把具体例子和逐步推演作为主要教学方式，选择必要源码，解释基础，设计帮助理解的练习和追问，纠正误解，并根据实际理解情况调整后续教学。理解优先于打分、术语记忆和计划进度。

**学生负责**：完成指定的短片段阅读、画图或推演，主动指出不理解的位置，进行闭卷复述，并保留自己的错题和疑问。

教学中始终区分项目能力、个人实际贡献和已经掌握的知识；不编造开发经历、性能数据或效果结论。

**设计与实现的标注规则：** 讲解改造方案中的未实现能力时，标题、示例和项目讲述稿必须标注“（设计，未实施）”。代码存在但没有实际验证的能力标注“已实现，验证范围见证据”；只有对应的测试/运行记录支持时才称已验证。主线以当前源码为准，新方案可用于讨论取舍，不作为已完成开发经历。教师随实施进度核对并更新标注。

## 五、最终保留的学习成果

1. 一张整体架构图与一条任务执行时序。
2. 一份 Agent 循环伪代码与核心故障处理笔记。
3. 一份重点问答与薄弱项清单。
4. 30 秒、2 分钟和 5 分钟三个版本的项目介绍。
5. 一份项目已验证能力与实际限制的简短说明。

判断是否掌握的标准是：能够不看资料解释原因，并在场景改变后推导出合理答案。七天结束后如仍有薄弱项，应如实保留并继续补齐。
