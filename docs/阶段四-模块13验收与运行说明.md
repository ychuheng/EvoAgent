## 1. 启动与入口

在仓库根目录执行：

```powershell
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend run build
.venv\Scripts\alembic.exe upgrade head
.venv\Scripts\evoagent-api.exe
```

默认 API 地址为 `http://127.0.0.1:8000`，管理入口为 `http://127.0.0.1:8000/ui/`。开发时执行 `pnpm --dir frontend run dev`，Vite 将 `/api` 代理到本地 8000 端口。若 API 使用其他端口，调整开发代理。前端需先构建，再启动 API，应用工厂才会挂载已有的 dist 目录。

前端构建基路径固定为 `/ui/`，构建命令会校验生成的 JS/CSS 链接及文件是否存在。部署后不仅要检查 `/ui/` 返回 200，还要确认页面实际渲染出导航；仅有 HTML 而静态资源返回 404 会表现为空白页。

阶段四数据库、Redis、任务 Worker 与维护 Worker 启动方法沿用[模块 11～12 运行说明](阶段四-模块11至12验收与运行说明.md)。删除任务需要 `evoagent-maintenance-worker` 执行；只启动 API 时，页面能看到 pending，但不能把它当作清理完成。

## 2. Memory 管理流程

1. 输入 Session ID，读取该 Session 和同 Workspace 共享作用域中的所有记忆版本。
2. 选择事实，核对内容、状态、revision、lock_version、scope、过期时间、内容哈希、置信度方法。
3. 查看来源 message_id/source_hash/locator 与审计 action/actor/reason。同一事实存在多个版本时，候选旁提示核对冲突；页面不自动选择“看起来更新”的版本。
4. proposed 可以确认或拒绝；proposed/confirmed 可以撤销。操作携带读取到的 expected_lock_version，后端继续执行来源验证和状态机校验。
5. 如需内容清理，执行“撤销并清理内容”。成功响应只证明决定已提交；界面从详情重新取得 maintenance_job_id，再查询任务状态。
6. pending/running 表示尚未确认完成；failed 显示错误码、尝试次数、下次重试时间，可显式重试；通过“刷新事实”重新读取任务与内容。completed 与内容清理结果由后端提供。

收到 409 时保留服务端事实，不把状态改为 confirmed/revoked；页面提示版本或状态冲突，要求刷新后重新审核。查询新 Session 时清除旧详情，避免把旧作用域的数据显示为新作用域的结果。页面不缓存内容到 localStorage。

确认、撤销和清理接口仍是可信本地管理入口，模型没有确认权限。页面不提供记忆提取/提议编辑表单；这两个生产入口继续使用模块 3～5 API。已撤销记录仍可查看审计，物理清理不等于删掉审计记录。

## 3. MCP 管理流程

### 3.1 注册和连接配置

页面只注册预设 launch_profile_id 或 endpoint_profile_id，不能输入任意命令、URL 或密钥。新注册项默认 enabled=false、执行未激活；名称、传输与 Profile 均由后端契约检查。需要凭据的部署沿用服务端配置和已有 API，页面只显示“已配置引用”，不回显引用名或凭据值。

启用/禁用连接配置通过 PUT 携带配置 lock_version。配置更新会使旧目录不能继续被当作当前目录，必须重新发现和审核。只启用连接并不等于允许工具调用。

### 3.2 发现、审核和激活

选择 Server 后同时读取目录和进程健康观察。可以浏览每个目录 revision、content_hash、差异、工具说明、输入/输出 Schema 和远端 annotations。说明文字按 React 普通文本渲染，不执行远端 HTML。

每个工具使用该目录内 lock_version 最大的审核记录。人工选择 risk/effect，填写审核人和理由；写副作用配 R0/R1 时禁止批准，后端仍是最终校验方。拒绝沿用既有风险和副作用并记录理由。旧目录只读，不能从页面审核或激活。

激活携带 Server 配置版本、execution_version 和 catalog_id。工具已批准不意味着 Server 已激活，Server 激活也不绕过逐工具审核、Policy、Approval 和 Effect。页面显示当前目录 execution_enabled；请求是否最终可执行仍取决于运行时完整验证链。

### 3.3 排空、卸载和健康

“排空调用”提交 draining，阻止新调用并等待在途调用退出；页面不声称所有在途任务已经结束。“卸载执行能力”提交 disabled，撤销执行能力并触发连接清理，保留 Server、目录和审核记录。它不是删除数据库中的 Server 历史。

健康观察独立展示每个 instance_id 的 state、config_version、expires_at 和 error_code。没有观察表示未知，stale 不是 ready；Server 的 enabled/active 也不能替代健康事实。当前页面采用显式刷新，不自动轮询或宣称实时状态。

## 4. 上下文证据与新增 API

新增 `GET /api/v1/runs/{run_id}/context`。返回：

| 字段 | 来源及语义 |
| --- | --- |
| run_id/status/error_code | 持久化 Run 事实 |
| config_hash | 已冻结配置哈希；未冻结时为 null |
| policy | 冻结 context_policy 中 mode/version/budget/counter/strict 白名单 |
| max_output_tokens | 冻结请求输出上限；未记录时为 null |
| revisions | 按 revision 升序的 ID、父引用、输入/策略哈希、Artifact ID、estimate、时间 |

查询不存在的 Run 返回 404。旧 Run 或尚未冻结的 Run 可返回空 policy、空 revisions；这不是查询失败，也不是“压缩成功”的证据。接口不展开完整 config_snapshot、原始消息、修订摘要正文或 Artifact URI。

页面以窗口、输出预留、安全余量、输入上限四格展示预算，输入上限仅在三个配置数值均存在时按 `context_window - output_tokens - safety_margin` 计算。修订 before/after 是本地估算证据，不能代替 Provider usage。

检索部分复用 `GET /runs/{run_id}/retrieval`，显示配置、generation、degraded、selected_count，以及逐来源的哈希、rank、omission_reason 和检索 evidence。明确区分：

- `retrieval_batch_not_found`：没有冻结批次，不能当作零命中。
- 已冻结且 selections 为空：没有候选命中。
- 有候选但 selected_count 为 0：可能全部被预算或策略省略，展示具体原因。
- 其他错误：显示读取失败，不把 500/网络错误转换成空结果；上下文成功结果仍可查看。
